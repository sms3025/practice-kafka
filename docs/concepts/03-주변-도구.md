# 03. 주변 도구: Fluent Bit, Kafka UI, ClickHouse, Grafana (그리고 Elasticsearch/Kibana와의 비교)

Kafka 자체는 "메시지를 안전하게 쌓아두고 꺼내주는" 일만 한다. 로그 파이프라인이 되려면 앞에서 로그를 긁어오는 도구, 뒤에서 저장하고 보여주는 도구, 그리고 중간을 들여다보는 도구가 필요하다. 이 문서는 그 도구들이 각각 무엇이고 왜 이 프로젝트에 들어왔는지를 정리한다.

## 전체 그림

```
장비 로컬 .log 파일 ──Fluent Bit(에이전트)──HTTP──▶ Spring 수집 서버 ──▶ Kafka ──▶ Spring 컨슈머 ──▶ ClickHouse ◀── Grafana / 자체 대시보드
                                                                     ▲
                                                                  Kafka UI (들여다보기)
```

## Fluent Bit: 장비 쪽에서 로그를 긁어 보내는 에이전트

Fluent Bit은 C로 작성된 경량 로그 수집기다. 메모리 수 MB로 동작하도록 설계되어 임베디드 장비, 컨테이너 사이드카, IoT 게이트웨이처럼 자원이 빠듯한 곳에 깔린다. 명세서가 "1,000대 이상의 차량/장비"에 이 도구를 지정한 이유가 그것이다. 각 장비에 Java 애플리케이션을 띄울 수는 없지만 Fluent Bit은 띄울 수 있다.

동작은 설정 파일 하나로 정의되는 파이프라인이다. `[INPUT]`이 데이터를 읽고(파일 tail, syslog, systemd, TCP 등), `[FILTER]`가 가공하며(파싱, 필드 추가, 샘플링), `[OUTPUT]`이 내보낸다(HTTP, Kafka, Elasticsearch, S3 등 수십 종). 이 프로젝트에서는 `tail` 입력으로 `docker/devices/*.log`를 읽어 `http` 출력으로 Spring에 보낸다. 명세서의 "설정 기반 수집"이란 코드를 짜는 것이 아니라 이 설정 파일을 장비 종류별로 맞춰 배포한다는 뜻이다.

Fluent Bit이 "무손실 전송"을 어떻게 달성하는지가 학습 포인트다. 세 가지 장치가 있다. `DB` 옵션은 파일별로 어디까지 읽었는지를 SQLite에 기록해, 에이전트가 재시작돼도 이어서 읽는다. `storage.type filesystem`은 아직 못 보낸 레코드를 메모리가 아닌 디스크에 두어 프로세스가 죽어도 남긴다. `Retry_Limit False`는 수집 서버가 2xx를 줄 때까지 무한 재시도한다. 이 셋을 합치면 "보냈는데 응답을 못 받은" 묶음이 다시 전송되는 **at-least-once** 보장이 된다. 같은 줄이 두 번 도착할 수 있으므로, 명세서가 `offset`을 멱등키 구성 요소로 요구하는 것이다.

같은 장치가 유량 제어도 맡는다. 장비가 보내는 양이 수집 서버의 처리량을 잠깐 넘으면, 서버가 429나 503으로 거절하고 Fluent Bit이 디스크 버퍼에 들고 기다렸다가 다시 보낸다. 장비와 서버 사이의 완충이 장비 디스크에 있는 셈이다. 재시도 간격은 `[SERVICE]`의 `scheduler.base`와 `scheduler.cap`으로 정한다. 간격이 지수적으로 늘고 무작위로 흩어지므로 1,000대가 같은 순간에 다시 몰려오지 않는다. 장비 디스크는 작으므로 `[OUTPUT]`의 `storage.total_limit_size`로 버퍼 상한을 두고, 넘치면 오래된 묶음부터 버린다. 유입량이 계속 처리량보다 많으면 버퍼는 시간만 벌어 줄 뿐이다. 그때는 gzip 압축(Step 5), `grep` 필터로 노이즈 줄 버리기, `throttle` 필터로 장비별 속도 상한 두기, 수집 서버 수평 확장으로 대응한다. 지금 저장소의 설정에는 재시도 간격과 버퍼 상한이 기본값이고, 수집 서버도 과부하 때 빨리 거절하지 않는다. 이 부분은 Step 5의 신뢰성 실험에서 다룬다.

**무손실 장치에도 빈틈이 있었다 (Step 4+ 실측, 2026-10-19).** 두 가지를 측정 중에 찾았다. 첫째, 부하가 끝난 뒤에도 에이전트마다 청크 몇 개(수백 줄)가 디스크 버퍼에 남아 재시작하기 전까지 보내지지 않았다. 잃지는 않았지만 저장소에는 늦게 도착한다. `[SERVICE]`의 `storage.metrics on`을 켜면 `http://localhost:2020/api/v1/storage`가 청크 수를 보여 주고, `/api/v1/metrics`의 `input.records`(읽은 줄)와 `output.proc_records`(보낸 줄)의 차이로 남은 양을 잴 수 있다. 둘째, 4.2.8의 `tail`은 재시작해 DB에서 이어 읽을 때 `Offset_Key` 값을 실제 파일 위치가 아니라 0부터 다시 센다(5.1.4에서는 고쳐져 있다). 그러면 `offset`으로 만든 멱등키가 재시작 전의 다른 줄과 겹쳐, 저장소의 중복 제거가 서로 다른 줄을 지운다. 위 문단의 "이 셋을 합치면 at-least-once"는 맞지만, 그 위에 얹는 멱등키는 에이전트의 버전과 재시작까지 따져야 한다(`../study/11-적재-경로-비교.md` 6절).

Fluent Bit 자체는 Kafka 출력 플러그인도 갖고 있어 Spring을 거치지 않고 바로 Kafka에 쓸 수도 있다. 명세서가 굳이 HTTP → 수집 서버를 두는 이유는 (1) 1,000대 장비가 Kafka 브로커 주소와 프로토콜을 직접 아는 것보다 HTTP 엔드포인트 하나만 아는 것이 망분리 환경에서 관리하기 쉽고, (2) 정규화(시각, device_id 추출)와 인증, 필터링을 중앙에서 통제하기 위해서다. Step 2의 결과 문서에서 둘을 비교한다.

## Kafka UI (Kafbat): Kafka 안을 들여다보는 창

Kafka는 CLI 도구(`kafka-topics.sh` 등)만 제공하고 GUI가 없다. Kafka UI는 브로커에 붙어 상태를 웹으로 보여주는 오픈소스 도구다. 원래 Provectus라는 회사가 만들었고, 2024년부터 커뮤니티 포크인 Kafbat이 이어받아 유지한다. 이 프로젝트에서는 http://localhost:8085 에서 연다.

학습 중 자주 보게 될 화면은 네 곳이다. **Brokers**에서는 브로커 수와 각 브로커가 리더로 맡은 파티션 수를 본다(3브로커 단계에서 브로커를 죽이면 여기 숫자가 바뀐다). **Topics → app-logs → Messages**에서는 실제 메시지의 키, 값(JSON), 파티션, 오프셋, 타임스탬프를 본다. 메시지를 눈으로 보는 것이 직렬화 설정이 맞는지 확인하는 가장 빠른 방법이다. **Topics → app-logs → Consumers**에서는 어떤 컨슈머 그룹이 이 토픽을 읽고 있는지, 각 파티션을 그룹 내 어느 멤버가 맡았는지, 그리고 **lag**(마지막 메시지 오프셋 − 커밋된 오프셋, 즉 아직 안 읽은 메시지 수)을 본다. lag이 계속 늘면 컨슈머가 생산 속도를 못 따라가는 것이다. **Consumers** 메뉴에서는 그룹 전체를 한눈에 보고, 필요하면 오프셋을 리셋해 "처음부터 다시 읽기"를 시킬 수도 있다.

Kafka UI는 Kafka의 내부 토픽 `__consumer_offsets`를 읽어 lag을 계산한다. UI가 보여주는 모든 정보는 브로커가 이미 갖고 있는 메타데이터이며, UI가 없어도 CLI로 전부 볼 수 있다. 편의 도구일 뿐 파이프라인의 일부가 아니다.

## ClickHouse: 로그를 쌓고 빠르게 집계하는 저장소

ClickHouse는 Yandex에서 만든 **열 지향(column-oriented) 분석용 데이터베이스**다. PostgreSQL이나 MySQL 같은 행 지향 DB는 레코드 한 건을 통째로 저장하고 "주문 1234번의 모든 정보"를 꺼내는 데 강하다. 반면 열 지향 DB는 같은 컬럼의 값들을 연속으로 저장해 "지난 한 시간 동안 device_id별 ERROR 건수"처럼 수억 행에서 몇 개 컬럼만 훑는 집계 쿼리에 강하다. 로그 조회·대시보드는 거의 전부 후자 유형이다.

로그 저장소로 ClickHouse가 선택되는 구체적 이유는 세 가지다. 첫째, **압축비**가 매우 높다. 같은 컬럼의 값들은 서로 비슷하므로(level 컬럼은 INFO가 대부분, timestamp는 단조 증가) 10~20배 압축이 흔하다. 명세서가 산출물로 "저장효율(압축비)" 비교를 요구하는 배경이다. 둘째, **삽입 처리량**이 높다. MergeTree 엔진은 데이터를 작은 파트로 받아 백그라운드에서 병합하므로, 초당 수십만 행을 받아낸다. 단, 한 건씩 INSERT하면 파트가 폭증해 오히려 느려지므로 수천 건씩 묶어 넣어야 한다. Kafka 컨슈머에서 배치 리스너를 쓰는 이유가 여기 있다. 셋째, **TTL**로 명세서의 보존 정책("N일 후 압축 보관, M일 후 삭제")을 테이블 정의에 선언할 수 있다.

ClickHouse에는 **Kafka 테이블 엔진**이라는 기능이 있어 Spring 컨슈머 없이 ClickHouse가 직접 Kafka 토픽을 구독해 적재할 수도 있다. 연습 프로젝트에서는 Step 4+에서 두 방식을 모두 해보고, Kafka 없이 수집 서버가 바로 넣는 직접 적재와도 비교한다. Spring 컨슈머 방식은 적재 전 가공과 실패 처리를 코드로 통제할 수 있고, Kafka 엔진 방식은 코드가 없어 단순하지만 디버깅이 어렵다.

**Kafka 테이블 엔진과 비동기 INSERT (Step 4+에서 실측).** Kafka 테이블 엔진은 데이터를 저장하지 않는 "큐 테이블"(`ENGINE = Kafka`)과, 큐가 넘긴 묶음을 변환해 저장 테이블에 넣는 구체화 뷰(MATERIALIZED VIEW) 한 쌍으로 쓴다. 묶음을 넘기는 주기가 기본 7.5초(`kafka_flush_interval_ms`)라 part가 매우 적은 대신 저장이 몇 초 늦다. 상태는 `system.kafka_consumers`로 본다. 비동기 INSERT(`async_insert=1`)는 작은 INSERT를 ClickHouse가 서버 메모리의 버퍼에 모았다가 한 part로 쓰는 기능이다. 버퍼는 50~200ms마다(25.8은 스스로 조절) 비워진다. `wait_for_async_insert=1`이면 버퍼가 실제로 기록된 뒤에 응답하므로 유실이 없고, 대신 요청마다 그만큼 기다린다. 장비 100대 × 초당 60줄 × 10분을 같은 입력으로 넣었을 때 새 part는 직접 적재 55,838개, 비동기 INSERT 1,669개, Kafka 경유(Spring 적재 컨슈머) 1,192개, Kafka 테이블 엔진 77개였고, 저장 지연 p50은 0.8초, 1.0초, 1.1초, 4.8초였다(2026-10-19, `../result/benchmark-ingest-path.md`).

SQL을 쓰므로 진입 장벽이 낮다. `SELECT device_id, countIf(level='ERROR') FROM logs WHERE event_time > now() - INTERVAL 1 HOUR GROUP BY device_id` 같은 쿼리가 그대로 동작한다. 다만 UPDATE/DELETE가 느리고 트랜잭션이 없다는 점에서 일반 DB와 다르며, 로그처럼 "쓰고 나면 안 바꾸는" 데이터에만 맞다.

**part와 병합 (Step 4에서 손으로 확인).** MergeTree 계열 테이블은 INSERT 한 번마다 디스크에 part(컬럼별 파일이 든 폴더) 하나를 만들고, 백그라운드에서 작은 part를 큰 part로 합친다. 1행이든 10만 행이든 INSERT 한 번은 part 하나이므로, 잘게 자주 넣으면 part가 쌓여 병합이 밀리고 결국 INSERT가 거부된다("Too many parts"). `system.parts`에서 지금의 part를, `system.part_log`에서 생성·병합 이력을 본다(`../study/08-ClickHouse-기초.md`). ReplacingMergeTree는 병합할 때 정렬 키가 같은 행을 하나만 남겨, 멱등키로 중복을 지우는 데 쓴다(`../study/09-ClickHouse-적재와-멱등키.md`).

압축비는 실제로 쟀다(2026-10-19, `../result/benchmark-storage.md`). 대외비 생성기 로그 351,327행이 기본 LZ4로 21.6MB(한 행 61.4바이트, 압축 전의 0.159), ZSTD(9)로 10.0MB(한 행 28.5바이트, 0.074)였다. 원문 텍스트 파일(59.4MB)보다도 작다. 위 문단의 "10~20배"는 컬럼 형식으로 펼친 크기(136.0MB) 대비로는 LZ4 6배, ZSTD(9) 14배였다.

## Grafana: 저장소 위에 얹는 대시보드

Grafana는 여러 데이터 소스(ClickHouse, Prometheus, Elasticsearch, PostgreSQL 등)에 쿼리를 보내 시계열 그래프, 표, 게이지로 그려주는 오픈소스 대시보드다. 명세서는 "자체 대시보드 제작"을 필수로, Grafana를 "운영 보조"로 두었다. 연습 프로젝트에서 Grafana를 쓰는 목적은 두 가지다. ClickHouse에 데이터가 제대로 들어갔는지 빠르게 확인하는 것, 그리고 자체 대시보드를 만들 때 "어떤 쿼리로 어떤 그래프를 그려야 하는지"의 견본을 얻는 것이다. Grafana 패널 하나는 결국 SQL 한 줄과 시각화 유형의 조합이므로, 여기서 만든 쿼리를 나중에 TypeScript 대시보드의 API로 옮기면 된다.

Step 4에서 데이터 소스와 대시보드를 화면에서 만들지 않고 파일(provisioning)로 넣었다(`docker/grafana/`). 누가 띄워도 같은 화면이 나오고, 컨테이너를 지워도 사라지지 않는다. ClickHouse 데이터 소스는 기본 내장이 아닌 플러그인(`grafana-clickhouse-datasource`)이라 첫 기동 때 인터넷에서 받는다. 망분리 환경에서는 플러그인 파일을 미리 넣어야 한다. 패널 쿼리는 `../study/10-대시보드.md`에 있다.

## 왜 Elasticsearch + Kibana가 아닌가

처음에 저장소로 Elasticsearch + Kibana를 고려했다. ELK 스택이라 불리는 이 조합은 로그 수집의 사실상 표준이었고 지금도 널리 쓰인다. Elasticsearch는 역색인 기반 **전문 검색 엔진**이라 "raw 본문에 'watchdog reset'이 포함된 로그"를 찾는 데 탁월하고, Kibana는 그 위에서 검색·필터·시각화를 한 화면에서 제공한다.

그럼에도 명세서가 ClickHouse를 지정한 이유는 로그 저장의 비용 구조에 있다. Elasticsearch는 모든 필드에 역색인을 만들므로 디스크 사용량이 원본의 1배 안팎이거나 더 크고, JVM 힙 메모리를 많이 요구한다. ClickHouse는 압축이 강해 디스크가 수 분의 1이고, 집계 쿼리가 훨씬 빠르며, 망분리 오프라인 환경에서 설치·운영이 단순하다(단일 바이너리). 대신 전문 검색은 ClickHouse가 약했는데, 최근 버전에서 텍스트 인덱스가 추가되어 격차가 줄었다. 정리하면 "자유 텍스트 검색이 주 용도"면 Elasticsearch, "대용량 적재·집계·장기 보관이 주 용도"면 ClickHouse가 유리하며, 1,000대 장비의 로그를 예지보전 데이터셋으로 축적하려는 이 프로젝트는 후자에 가깝다.

| 관점 | Elasticsearch + Kibana | ClickHouse + Grafana |

| 데이터 모델 | 문서(JSON) + 역색인 | 열 지향 테이블 + SQL |
| 강점 | 전문 검색, 유연한 스키마 | 집계 속도, 압축비, 삽입 처리량 |
| 약점 | 디스크·메모리 비용, 집계 느림 | 전문 검색 상대적 약세, 행 단위 갱신 부적합 |
| 조회 언어 | Query DSL / KQL | SQL |
| 운영 (오프라인) | JVM, 클러스터 설정 복잡 | 단일 바이너리, 설정 단순 |
| 이 프로젝트 | 비교·벤치마크 대상 | 주 저장소 (명세서 지정) |

이 비교 자체가 명세서 산출물("기술 스택 비교·선정 결과 및 근거")의 일부가 되므로, ClickHouse 단계에서 같은 데이터를 넣고 디스크 사용량과 쿼리 시간을 실측해 이 표를 수치로 채우는 것을 목표로 한다.
