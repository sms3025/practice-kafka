PRACTICE KAFKA / 그림으로 읽는 개념 사전

로그 한 줄이 Kafka를
지나가는 동안 생기는 일

가상 장비 VH-0001이 “연습 작업 시작”을 기록했다. 이 한 줄을 따라가면 프로듀서, 브로커, 토픽, 파티션, 오프셋, 컨슈머 그룹이 연결된다.

이 자료는 저장소의 코드 구조를 바탕으로 그린 개념 모형이다. 모든 로그와 수치는 학습용으로 만든 예시이며, 실행 화면이나 성능 측정 결과가 아니다. Docker 없이 브라우저에서 열 수 있다.

01 / 전체 데이터 흐름

Kafka는 중간에서 로그를 보관한다

Fluent Bit은 파일을 읽고, Spring 수집 서버는 로그를 공통 형식으로 바꾼다. 서버 안의 프로듀서가 Kafka에 쓰고, 컨슈머가 Kafka에서 읽는다. 프로듀서와 컨슈머는 별도 제품 이름이 아니라 클라이언트의 역할 이름이다.

장비 로그 파일VH-0001 / demo.log
→
Fluent Bit새 줄 + 경로 + 파일 위치
→
Spring 수집 서버HTTP 수신 → 정규화 → 발행

위의 Spring 수집 서버가 프로듀서 역할로 아래의 Kafka에 발행한다.

Kafka 브로커app-logs 토픽의 파티션에 저장
→
컨슈머현재: 콘솔에 출력
→
ClickHouse → GrafanaStep 4 예정: 저장 → 조회·시각화



실제 코드에서는 수집 서버와 컨슈머가 같은 Spring 프로세스 안에 있다. 그림은 책임을 나누어 그렸다. POST /ingest/fluentbit는 Kafka 발행 성공을 확인한 뒤 200을 반환한다. 이 응답이 ClickHouse 적재 완료를 뜻하지는 않는다.





02 / 토픽을 열어 보면
하나의 토픽, 세 개의 기록 줄
브로커는 Kafka 서버 프로세스다. 그 안의 토픽 app-logs는 로그를 분류하는 이름이고, 실제 기록은 세 파티션에 나뉘어 쌓인다. 브로커 한 대에도 파티션 여러 개를 둘 수 있다.



키는 “어느 줄에 쓸까”를 정한다
이 프로젝트의 키는 device_id다. 기본 키 기반 분배에서 파티션 수와 분배 방식이 유지되면 같은 키는 같은 파티션으로 간다. 서로 다른 키도 같은 파티션에 들어갈 수 있다. 파티션 수를 늘리면 같은 키의 목적지가 달라질 수 있다.
오프셋은 “그 줄의 몇 번째인가”다
p0@1과 p1@1은 다른 위치다. 따라서 Kafka 레코드는 (토픽, 파티션, 오프셋)으로 구분한다. 파티션 안의 기록 순서는 보장되지만, 파티션 사이의 전체 순서는 보장되지 않는다. 기록 순서가 장비의 발생 시각 순서와 항상 같지는 않다.


키(key): VH-0001
값(value): { "device_id": "VH-0001", "message": "연습 작업 시작", ... }
부가 정보: 타임스탬프, 헤더
브로커가 부여한 위치: topic=app-logs, partition=0, offset=2  (가정)


JSON은 값의 직렬화 형식이다. Kafka가 JSON 내용을 분석해서 장비를 분류하는 것이 아니라, 프로듀서가 별도로 넘긴 키로 파티션을 고른다.



03 / 컨슈머 그룹
같은 그룹은 나누고, 다른 그룹은 따로 읽는다
세 파티션에 총 6건이 있다고 가정한다. log-printer 그룹의 컨슈머 수를 바꾸면 누가 어느 파티션을 맡는지 볼 수 있다. 아래 배치는 가능한 예시이며 실제 할당 결과는 할당 전략에 따라 달라진다. 컨슈머는 poll()로 읽어 간다.




그룹 A · log-printer
그룹 B · stats-demo 가상 예시
파티션 0 → 통계 컨슈머 S1 · 2건
파티션 1 → 통계 컨슈머 S1 · 2건
파티션 2 → 통계 컨슈머 S1 · 2건
그룹 A가 읽어도 그룹 B가 읽을 데이터는 사라지지 않는다. B는 자신의 소비 위치로 같은 6건을 읽을 수 있다.


파티션 3개라면 이 토픽에 대해 한 그룹에서 동시에 파티션을 맡는 컨슈머는 최대 3개다. 그룹 구성원이 바뀌면 리밸런스로 담당이 재조정되고 소비가 지연될 수 있다. 중단 범위는 그룹 프로토콜과 할당 방식에 따라 다르다. 현재 저장소는 log-printer 하나를 사용한다.





04 / 읽기와 커밋
책은 그대로 두고, 책갈피만 옮긴다
파티션 0에 4건이 남아 있다. “한 건 처리”는 읽고 업무 처리를 마친 상황을 단순화한 버튼이다. “커밋”은 다음에 읽을 위치를 Kafka에 저장한다. 커밋 전에 재시작하면 이미 처리한 메시지를 다시 만날 수 있다.




처리 후 다음 읽기 위치 0
그룹의 커밋 위치 0






커밋 값이 2라면 “0과 1은 처리했으니 다음에는 2부터 읽는다”는 뜻이다. 이 값은 그룹·토픽·파티션별로 관리되며 내부 토픽 __consumer_offsets에 저장된다. 위의 0은 이미 유효한 커밋이 있다고 가정한 초기값이다.


실제 Kafka의 position은 poll로 반환한 다음 위치라서 업무 처리 완료보다 앞설 수 있다. 이 모형은 한 건씩 읽고 처리하는 상황이다. 실제 Spring 리스너의 커밋 시점은 컨테이너의 ack 모드와 오류 처리 설정이 정한다. 현재 코드를 수동 커밋 방식으로 바꾼 것은 아니다.


왜 earliest인데 처음부터 안 읽을까?
유효한 커밋이 있으면 그 위치로 돌아간다. auto-offset-reset=earliest는 커밋이 없거나 유효하지 않을 때 남아 있는 가장 이른 위치를 고른다. 새 그룹은 기존 그룹의 책갈피를 공유하지 않는다.
offset이라는 이름이 두 번 나온다
JSON의 offset=128은 원본 파일의 바이트 위치다. Kafka 헤더의 offset=2는 파티션 내 위치다. 같은 파일 줄이 재전송되면 파일 위치는 같아도 Kafka 위치는 새로 부여될 수 있다. 저장소의 멱등키는 (device_id, source, offset)이며, 여기의 offset은 파일 위치다.





05 / Kafka를 사이에 두는 이유
쓰는 속도와 읽는 속도를 분리한다
학습용 한 턴에 프로듀서가 4건을 쓰고 컨슈머가 최대 2건을 처리·커밋한다고 가정한다. 컨슈머를 멈춰도 Kafka 발행은 계속된다. 다시 읽으면 쌓인 것을 따라잡는다. 아래 숫자는 성능 측정값이 아니다.


프로듀서0건 발행
→
Kafka에 남은 기록0건
→
컨슈머0건 처리




이 단순 모형에서 lag = 로그 끝 위치 − 커밋 위치다. 처리해도 Kafka의 기록 수는 줄지 않는다. 실제 보존은 retention 설정과 세그먼트 정리에 따른다. 보존 한도나 디스크 용량을 넘기면 무한히 기다려 주지 못하므로, Kafka를 넣는 것만으로 무손실이 보장되지는 않는다.


Kafka 자체가 멈추면 프로듀서도 계속 성공할 수 없다. 이 프로젝트는 Fluent Bit의 버퍼와 재시도로 앞단을 받친다. Kafka에는 기록됐지만 HTTP 응답을 받지 못하면 같은 묶음이 다시 전송될 수 있어, 최종 저장 단계에서 중복을 다루어야 한다.



06 / 리스너와 KRaft
첫 접속 주소와 안내받는 주소
bootstrap.servers는 첫 문의 주소다. 클라이언트는 브로커에서 “이 파티션의 리더는 이 주소에 있다”는 메타데이터를 받고 해당 주소에 접속한다. 그래서 클라이언트가 실제로 접근할 수 있는 주소를 광고해야 한다.
설정을 바꿔 가며 접속 단계를 따라가려면 리스너 그림 자료를 연다.


Windows 호스트의 Spring 앱
Spring 앱→localhost:9092
호스트용 리스너가 localhost:9092를 알려 준다. Docker의 포트 매핑을 통해 브로커로 간다.
Docker 안의 Kafka UI
Kafka UI→kafka:19092
컨테이너 내부용 리스너가 kafka:19092를 알려 준다. 여기서 localhost는 Kafka UI 컨테이너 자신이므로 브로커 주소가 될 수 없다.


KAFKA_LISTENERS              = 접속을 받는 주소
KAFKA_ADVERTISED_LISTENERS   = 클라이언트에게 알려 주는 주소
KAFKA_PROCESS_ROLES         = broker,controller
broker는 메시지를 저장·전달하고, controller는 브로커·토픽·리더 같은 메타데이터를 관리한다. KRaft는 이 관리에 Kafka 자체의 Raft 기반 합의를 사용한다. 현재는 한 노드가 두 역할을 겸하는 학습 구성이다. CONTROLLER 리스너는 메타데이터 관리 통신용이며 앱이 로그를 보내는 주소가 아니다.



07 / 디스크와 복제
뒤에 추가하고, 파일 단위로 정리한다
app-logs-0 / 파티션 디렉터리
세그먼트 A과거 기록 · 닫힌 파일
세그먼트 B과거 기록 · 닫힌 파일
활성 세그먼트 C새 기록 → 끝에 추가
파티션 로그는 여러 세그먼트 파일과 인덱스로 구성된다. 활성 파일이 크기·시간 조건에 도달하면 새 파일로 넘어간다. cleanup.policy=delete에서는 보존 시간·크기 조건에 따라 오래된 세그먼트를 정리한다. 메시지를 읽었다고 지우거나, 각 메시지가 정확히 N일 되는 순간 개별 삭제하는 방식이 아니다. compaction 정책은 키별 최신 상태를 남기는 별도 방식이다.


복제는 파티션을 다른 브로커에 복사하는 것이다 Step 6 미리보기
브로커 A · 리더파티션 0 원본 역할
→
브로커 B · 팔로워파티션 0 복제본
+
브로커 C · 팔로워파티션 0 복제본
그림의 화살표는 데이터 복사 방향이다. 팔로워는 각각 리더에서 가져온다. 프로듀서는 리더에 쓰고, 팔로워가 따라온다. 충분히 동기화된 복제본 집합이 ISR이다. acks=all은 현재 ISR의 확인을 기다리고, min.insync.replicas=2는 ISR이 최소 2개여야 쓰기를 받아들이게 한다. 항상 브로커 3대 전체가 응답해야 한다는 뜻은 아니다.
현재 설정은 파티션 3개, 복제 계수 1, 브로커 1대다. 파티션 3개가 백업 3개를 뜻하지 않는다. acks=all을 사용해도 다른 브로커에 복사본이 생기지는 않는다.

브라우저에서 해 보는 실습
  1. 1절에서 다음 구간을 눌러 원문이 어떤 JSON과 Kafka 위치로 바뀌는지 따라간다.
  2. 3절에서 컨슈머 수를 1 → 3 → 4로 바꾼다. 네 번째가 일하지 않는 이유를 설명한다.
  3. 4절에서 “한 건 처리” 두 번 → 커밋 없이 재시작한다. 다시 읽는 위치를 확인한다. 같은 실습을 커밋 후 반복한다.
  4. 5절에서 컨슈머를 멈추고 세 턴 발행한다. 재개한 뒤 발행 없이 소비해 lag이 줄어도 기록은 남는지 확인한다.


스스로 설명할 수 있는가?
파티션 0의 offset 1과 파티션 1의 offset 1은 같은 메시지인가?
아니다. 오프셋은 각 파티션 안에서만 위치를 나타낸다. 토픽·파티션·오프셋을 함께 봐야 한다.
다른 그룹이 같은 로그를 읽으면 복사본이 한 벌 더 저장되는가?
아니다. 같은 파티션 데이터를 각자 읽는다. 그룹마다 커밋 위치가 따로 있을 뿐이다. 복제는 별도 개념이다.
처리 성공 직후, 커밋 직전에 장애가 나면 어떻게 되는가?
마지막 커밋 위치부터 읽으므로 처리한 레코드를 다시 처리할 수 있다. 외부 저장소 쓰기는 멱등하게 설계해야 한다.
같은 장비가 같은 파티션에 들어가면 시각순 정렬도 자동인가?
아니다. Kafka는 파티션에 기록된 순서를 보장한다. 여러 전송 경로, 지연, 재전송 등으로 발생 시각과 도착 순서가 다를 수 있다.


실제 Kafka UI로 이어지는 실습은 06 실습 워크북 B3~B5를 따른다. 이 페이지의 모형은 실제 Kafka에 접속하지 않는다.
