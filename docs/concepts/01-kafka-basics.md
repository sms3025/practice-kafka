# 01. Kafka 핵심 개념

그림부터 보고 싶으면 [로그 한 줄로 보는 Kafka 기초](01-kafka-basics.html)를 브라우저로 연다. 가상 로그의 이동, 파티션과 그룹의 관계, 커밋 전 장애에 따른 재처리, 소비 지연을 버튼으로 확인할 수 있다. 실제 Kafka 실행 결과가 아닌 학습용 모형이다.

## Kafka는 무엇인가

Kafka는 **분산 이벤트 로그(distributed commit log)** 다. 메시지 큐처럼 보이지만 본질은 "추가만 되는(append-only) 로그 파일을 여러 서버에 나눠 저장하고, 누구든 원하는 위치부터 읽게 해주는 시스템"이다. 전통적인 메시지 큐(RabbitMQ 등)는 메시지를 소비자가 가져가면 지워지지만, Kafka는 메시지를 소비 여부와 상관없이 설정한 보존 기간(기본 7일) 동안 디스크에 그대로 둔다. 그래서 같은 데이터를 여러 소비자가 각자의 속도로 읽을 수 있고, 장애가 나면 되감아서 다시 읽을 수도 있다.

대용량 로그 처리에 Kafka가 쓰이는 이유는 여기에 있다. 로그는 "쓰기는 폭발적이고 순서가 있으며 여러 곳(검색 엔진, 알림, 통계)에서 동시에 읽어야 하는" 데이터인데, Kafka의 구조가 정확히 이 패턴에 맞는다. 디스크에 순차 쓰기만 하므로 초당 수십만 건도 일반 하드웨어로 처리한다.

## 용어

**브로커(Broker)** 는 Kafka 서버 프로세스 하나다. 여러 브로커가 모여 클러스터를 이룬다. 클라이언트는 `bootstrap.servers`에 적힌 브로커 중 하나에 접속해 클러스터 전체의 메타데이터(어떤 토픽의 어떤 파티션이 어느 브로커에 있는지)를 받아온 뒤, 실제 데이터는 해당 브로커에 직접 보내거나 받는다.

브로커는 스레드가 아니라 **서버 프로그램 한 벌**이다. MySQL 서버나 Redis 서버를 떠올리면 가깝다. 이 저장소에서 `docker compose up`으로 뜨는 `kafka` 컨테이너 안의 Java 프로세스 하나가 곧 브로커 하나다. 브로커가 하는 일은 세 가지로 요약된다. 네트워크 포트를 열고 클라이언트 요청을 받는다. 받은 메시지를 자기 디스크의 파티션 파일 끝에 붙인다. 컨슈머가 요청하면 디스크에서 읽어 돌려준다. 브로커 안에서도 요청 처리용 스레드가 여러 개 돌지만, 그것은 브로커의 내부 구현일 뿐이다. 반대로 Spring 앱은 브로커가 아니다. Spring 앱 안의 `KafkaTemplate`과 `@KafkaListener`는 브로커에 접속하는 **클라이언트**이며, 브로커 입장에서 보면 DB 서버에 붙는 애플리케이션과 같은 위치다. 토픽과 파티션은 데이터를 어떻게 나눠 담을지에 대한 논리적 구조이고, 브로커는 그 데이터를 실제로 디스크에 들고 있으면서 요청에 답하는 서버다. "파티션 0은 브로커 1에 있다"는 말은 "파티션 0의 파일이 브로커 1 서버의 디스크에 있고, 브로커 1이 그 파티션의 요청을 처리한다"는 뜻이다.

**토픽(Topic)** 은 메시지를 분류하는 논리적 이름이다. 이 프로젝트에서는 `app-logs` 하나를 쓴다. 데이터베이스의 테이블에 비유되지만, 테이블과 달리 레코드를 수정하거나 조건 검색할 수 없고 뒤에 붙이고 앞에서부터 읽을 뿐이다. 토픽은 보통 데이터의 종류나 용도로 나누며, INFO·ERROR 같은 로그 레벨로 나누지 않는다. 레벨별로 토픽을 쪼개면 같은 장비의 로그가 여러 토픽에 흩어져 장비 단위 순서를 잃고, 레벨별 조회는 적재 후 DB의 `WHERE level = 'ERROR'`가 더 잘하기 때문이다. 이 프로젝트에서 레벨은 메시지 안의 `level` 필드다. 토픽을 따로 두는 것은 성격이 다른 데이터(장비 메트릭, 알람 이벤트), 처리 실패 메시지를 모으는 DLT(Step 5), 보관 기간이나 접근 권한이 달라야 하는 데이터다.

**파티션(Partition)** 은 토픽을 물리적으로 쪼갠 단위이며, 각 파티션은 하나의 append-only 로그다. 파티션은 Kafka에서 **병렬성의 단위**이자 **순서 보장의 단위**다. 순서는 파티션 안에서만 보장되고 토픽 전체에서는 보장되지 않는다. 파티션이 3개면 컨슈머 그룹 안에서 최대 3개의 컨슈머가 동시에 읽을 수 있다. 4번째 컨슈머는 놀게 된다.

**오프셋(Offset)** 은 파티션 안에서 메시지의 위치를 나타내는 0부터 증가하는 정수다. 읽기·업무 처리·커밋은 별개다. 컨슈머 그룹은 재시작 후 이어 읽을 위치를 브로커의 내부 토픽 `__consumer_offsets`에 커밋한다. 예를 들어 오프셋 0과 1을 처리했다면 다음에 읽을 위치인 2를 커밋한다. 처리 후 커밋 전에 장애가 나면 이미 처리한 메시지를 다시 읽을 수 있다. JSON의 `offset`은 원본 파일의 바이트 위치이며 Kafka 오프셋과 다르다.

**메시지(Record)** 는 키(key), 값(value), 타임스탬프, 헤더로 이뤄진다. 키는 선택 사항이지만 중요하다. 기본 키 기반 분배는 키의 해시(murmur2)로 파티션을 고르므로, **파티션 수와 분배 방식이 유지되면 같은 키는 같은 파티션**에 간다. 이 프로젝트는 `device_id`를 키로 사용해 같은 장비의 로그를 한 파티션에 모은다. 보장되는 것은 파티션에 기록된 순서이며, 장비의 발생 시각순 정렬을 자동으로 해주는 것은 아니다. 파티션 수를 늘리면 키의 목적지가 달라질 수 있다. 키가 없으면 기본 설정에서 sticky 방식으로 분산되므로 같은 장비가 같은 파티션에 모인다는 보장은 없다.

**프로듀서(Producer)** 는 메시지를 쓰는 클라이언트, **컨슈머(Consumer)** 는 읽는 클라이언트다. 둘 다 브로커 입장에서는 그냥 TCP 클라이언트이며, 브로커는 컨슈머에게 메시지를 밀어주지(push) 않는다. 컨슈머가 `poll()`로 당겨간다(pull). 그래서 컨슈머는 자기 속도로 읽을 수 있고, 느린 컨슈머가 브로커를 막지 않는다.

**컨슈머 그룹(Consumer Group)** 은 같은 `group.id`를 가진 컨슈머들의 집합이다. 그룹 안에서는 파티션을 나눠 갖고(한 파티션은 그룹 내 한 컨슈머에만 할당), 그룹이 다르면 서로 독립적으로 전체 메시지를 받는다. "같은 로그를 Elasticsearch에도 넣고 통계도 내고 싶다"면 그룹을 두 개 만들면 된다. 그룹 구성원이 바뀌면(컨슈머 추가/종료/장애) 파티션을 다시 나누는 **리밸런스(rebalance)** 가 일어나며, 이 동안 해당 그룹은 잠시 소비를 멈춘다.

## KRaft 모드

Kafka는 원래 클러스터 메타데이터(브로커 목록, 토픽 설정, 리더 선출)를 ZooKeeper라는 별도 시스템에 저장했다. Kafka 3.x부터 Raft 합의 알고리즘을 자체 구현한 **KRaft** 가 도입되었고, Kafka 4.0부터는 ZooKeeper가 완전히 제거되었다. 이제 브로커 중 일부(또는 전부)가 **컨트롤러(controller)** 역할을 겸해 메타데이터를 관리한다.

이 프로젝트의 단일 브로커 설정에서 `KAFKA_PROCESS_ROLES=broker,controller`는 "이 노드가 데이터 저장도 하고 메타데이터 관리도 한다"는 뜻이다(combined 모드). 운영 환경에서는 컨트롤러 전용 노드 3개 + 브로커 노드 N개로 분리하는(isolated 모드) 것이 권장된다. 공부할 때는 combined로 충분하다.

## 리스너(Listener) 설정이 복잡한 이유

docker-compose에서 `KAFKA_LISTENERS`, `KAFKA_ADVERTISED_LISTENERS`가 여러 개인 것은 Kafka의 접속 방식 때문이다. 클라이언트는 먼저 bootstrap 서버에 붙은 뒤, 브로커가 **"나한테 접속하려면 이 주소로 와"라고 알려주는(advertise) 주소**로 다시 접속한다. 컨테이너 안에서는 `kafka:19092`가 맞지만 호스트에서는 `localhost:9092`가 맞으므로, 접속 경로마다 다른 주소를 광고하도록 리스너를 둘 이상 둔다. 이걸 잘못 잡으면 "bootstrap은 되는데 실제 전송이 타임아웃" 나는 전형적인 증상이 생긴다.

한 줄로 줄이면 `KAFKA_LISTENERS`는 브로커가 **열어 둔 출입문**(어느 포트에서 받는가)이고, `KAFKA_ADVERTISED_LISTENERS`는 그 문으로 들어온 손님에게 **나눠 주는 명함**(다음부터 어느 주소로 오라)이다. 둘은 `PLAINTEXT`, `PLAINTEXT_HOST` 같은 이름표로 짝지어진다. 접속 흐름을 단계별로 따라가는 설명은 [study/01 4절](../study/01-환경과-프로젝트-구조.md)에 있다. 설정을 바꿔 가며 어느 단계에서 끊기는지 직접 보려면 [리스너 HTML](01-kafka-listeners.html)을 브라우저로 연다.

## 메시지는 어떻게 저장되는가

파티션은 브로커 디스크에서 디렉터리 하나(`app-logs-0`, `app-logs-1`, ...)이며, 그 안에 세그먼트 파일(`00000000000000000000.log`)과 인덱스 파일이 있다. 메시지는 세그먼트 끝에 순차적으로만 쓰이고, 세그먼트가 일정 크기(기본 1GB)나 시간에 도달하면 새 세그먼트로 넘어간다. 보존 정책(`retention.ms`, `retention.bytes`)은 오래된 세그먼트 파일을 통째로 삭제하는 식으로 동작한다. 순차 I/O와 OS 페이지 캐시, zero-copy 전송 덕분에 Kafka는 디스크 기반인데도 메모리 큐에 가까운 처리량을 낸다.

## 복제(Replication) 미리보기

파티션은 여러 브로커에 복제될 수 있다(`replication.factor`). 복제본 중 하나가 **리더(leader)** 이고 모든 읽기/쓰기는 리더가 처리한다. 나머지 **팔로워(follower)** 는 리더를 따라 복사한다. 리더와 충분히 동기화된 복제본 집합을 **ISR(In-Sync Replicas)** 라 한다. 프로듀서의 `acks=all`은 "ISR 전부가 받았을 때 성공으로 친다"는 뜻이며, `min.insync.replicas`와 조합해 "복제본 최소 2개에 기록되지 않으면 실패로 처리"하는 내구성 보장을 만든다. 단일 브로커에서는 복제가 없으므로 이 설정들이 의미가 없고, Step 6에서 3브로커로 가면 실제 동작을 볼 수 있다.

## 브로커가 여러 대일 때 부하가 나뉘는 원리

브로커를 늘려 얻는 것은 복제만이 아니다. 쓰기와 읽기 트래픽도 브로커들에 나뉜다. 다만 앞단에 트래픽 분배기(로드 밸런서)가 따로 있는 것은 아니다. **파티션마다 리더가 따로 있고, 리더들이 여러 브로커에 흩어져 있으며, 클라이언트는 각 파티션의 리더 브로커와 직접 통신한다.** 이 구조 자체가 트래픽을 나눈다.

파티션 6개, 브로커 3대, `replication.factor=2`인 토픽을 예로 든다. Kafka는 토픽을 만들 때 리더를 브로커들에 고르게 배치한다.

```
            브로커 1     브로커 2     브로커 3
파티션 0    [리더]       [팔로워]
파티션 1                 [리더]       [팔로워]
파티션 2    [팔로워]                  [리더]
파티션 3    [리더]                    [팔로워]
파티션 4    [팔로워]     [리더]
파티션 5                 [팔로워]     [리더]
```

쓰기는 이렇게 나뉜다. 프로듀서는 메시지 키(`device_id`)의 해시로 파티션을 정하고, 메타데이터에서 그 파티션의 리더 브로커를 찾아 **그 브로커로 바로** 보낸다. 장비 키가 파티션 6개에 고르게 퍼지면 쓰기도 브로커마다 대략 1/3씩 들어간다. 프로듀서는 브로커별로 배치를 따로 모아 동시에 보낸다.

읽기도 같은 원리다. 컨슈머는 자기가 맡은 파티션의 리더 브로커에 직접 fetch 요청을 보낸다. 그래서 읽기 트래픽도 리더 분포를 따라 나뉜다. 결국 **키 → 파티션 → 리더 브로커**로 이어지는 결정이 디스크 쓰기, 네트워크, CPU 부하를 브로커별로 나눈다.

이 구조에는 세 가지 조건이 따른다. 첫째, 파티션 수가 브로커 수보다 적으면 나눌 수 없다. 파티션이 1개면 리더도 하나라서 브로커가 3대여도 한 대만 일한다. 둘째, 키가 한쪽에 몰리면(hot key) 소용없다. 특정 장비 하나가 로그를 압도적으로 쏟으면 그 장비의 파티션과 리더 브로커만 바빠진다. 셋째, 팔로워도 리더에게서 복제본을 계속 가져오므로 브로커 사이에 복제 트래픽이 추가로 생긴다. 브로커가 죽었다 살아나면 리더가 남은 브로커들에 몰릴 수 있는데, Kafka는 원래 지정된 리더(preferred leader)로 주기적으로 되돌려 균형을 맞춘다(`auto.leader.rebalance.enable`, 기본 켜짐). Step 6에서 3브로커를 띄우면 Kafka UI의 토픽 화면에서 파티션별 리더 브로커 번호를 직접 볼 수 있다.

## 리밸런스와 그룹 프로토콜

그룹의 멤버가 바뀌면(컨슈머 합류, 정상 종료, 하트비트가 끊긴 컨슈머 제거) 파티션을 다시 나눈다. 이것이 리밸런스다. 나누는 방식은 둘이다.

| | classic (클라이언트 기본값) | consumer (KIP-848, Kafka 4에서 정식) |
|---|---|---|
| 누가 할당을 정하나 | 그룹의 리더 컨슈머가 할당 전략(`partition.assignment.strategy`)으로 | 브로커의 그룹 코디네이터가 |
| 바뀔 때 | 기본 전략(Range)에서는 모든 컨슈머가 파티션을 전부 내려놓고 다시 받는다(eager) | 옮겨야 할 파티션만 하트비트 주기마다 조금씩 옮긴다 |
| 이 저장소의 실측 (2026-10-19, `study/07`) | 합류 때 그룹 전체가 약 40ms 멈춤 | 합류 때 6개 중 3개만 옮겨지고, 옮겨진 것은 5~7초 쉼 |

컨슈머가 말없이 죽으면 브로커는 `session.timeout.ms`(기본 45초) 동안 하트비트를 기다린 뒤에야 그 컨슈머를 빼고 리밸런스한다. 그동안 그 파티션은 아무도 읽지 않는다. 정상 종료는 떠난다고 알리므로 바로 리밸런스된다(실측 약 1.4초 대 44초).

## 이 프로젝트에서 한 번에 외울 것

토픽은 파티션으로 나뉘고, 파티션 안에서만 순서가 보장되며, 같은 키는 같은 파티션에 간다. 컨슈머는 그룹 단위로 파티션을 나눠 갖고, 그룹이 다르면 전부 다시 받는다. 소비 위치는 오프셋이며 커밋해야 기억된다. 이 네 문장이면 Step 1~2의 모든 현상을 설명할 수 있다.
