# 03. 프로듀서 설정 실험 (워크북 C절, `study/03`)

`application.properties`의 producer 설정을 하나씩 바꾸고, 같은 부하를 보내 무엇이 달라지는지 잰다. 설정 설명은 `../study/03-Producer-깊게.md` 3절에 있다. 여기서는 측정을 "같은 조건에서 공정하게" 하는 방법과 각 실험에서 볼 숫자를 다룬다.

시작 전 상태: 02 파일을 마쳐 컨테이너 다섯과 앱이 떠 있다. 앱은 계속 00 파일 0-3의 단계 인자로 띄운다. 이 파일의 설정 실험도 `application.properties`를 고치는 대신 Program arguments 끝에 `--키=값`을 붙였다 떼는 식으로 할 수 있다(예: `--spring.kafka.producer.properties[linger.ms]=0`).

## C0. 측정 준비

**왜 하는가.** 측정값이 설정 말고 다른 이유로 흔들리면 비교가 안 된다. 흔들리게 만드는 원인은 셋이다.

첫째는 콘솔 로그다. 지금 설정은 프로듀서 발행 성공 로그(DEBUG)와 컨슈머 로그(INFO)를 메시지마다 한 줄씩 찍는다. 2만 건이면 4만 줄이다. 특히 발행 성공 로그는 프로듀서의 Sender 스레드가 콜백 안에서 찍으므로, 콘솔이 느리면 전송 자체가 느려진다(`study/03` 1절 심화 단락의 콜백 이야기다). 둘째는 첫 호출이다. 앱이 막 떴을 때는 메타데이터 조회, 연결 수립, JIT 컴파일이 첫 호출에 몰린다. 셋째는 우연이다. 한 번만 재면 PC의 다른 작업에 따라 값이 튄다.

**할 것.**

1. `application.properties`의 로깅 부분에서 두 줄을 아래처럼 바꾼다. 위 줄은 값만 바꾸고, 아래 줄은 새로 넣는다. 이 상태가 C절 내내 기준이다.

```properties
logging.level.com.practice.kafka.producer=INFO
logging.level.com.practice.kafka.consumer=WARN
```

2. 앱을 재시작한다.
3. 명령 터미널에 아래 함수 세 개를 붙여 넣고 Enter를 누른다. 함수는 **그 터미널 탭이 열려 있는 동안만** 살아 있다. 탭을 새로 열었으면 다시 붙여 넣는다.

```powershell
# Actuator 에서 프로듀서 지표 하나를 읽는다
function M($name) { (Invoke-RestMethod "http://localhost:8080/actuator/metrics/$name").measurements[0].value }
# 브로커 디스크에서 app-logs 파티션 폴더 셋의 크기 합(KB)
function Size { (docker exec kafka sh -c "du -sk /var/lib/kafka/data/app-logs-*" | ForEach-Object { [int]($_ -split "\s+")[0] } | Measure-Object -Sum).Sum }
# 워밍업 1회 후 2만 건씩 3회 보내고, 가운데 값과 지표를 한 줄로 보여 준다
function Run-C {
    $url = "http://localhost:8080/api/logs/generate?count=20000&devices=200"
    Invoke-RestMethod -Method Post $url | Out-Null
    $req0 = M "kafka.producer.request.total"; $kb0 = Size
    $ms = 1..3 | ForEach-Object { (Invoke-RestMethod -Method Post $url).elapsedMs }
    $req1 = M "kafka.producer.request.total"; $kb1 = Size
    [pscustomobject]@{
        elapsedMs     = ($ms | Sort-Object)[1]
        requests      = [int](($req1 - $req0) / 3)
        recordsPerReq = [math]::Round((M "kafka.producer.records.per.request.avg"), 1)
        batchBytes    = [int](M "kafka.producer.batch.size.avg")
        compression   = [math]::Round((M "kafka.producer.compression.rate.avg"), 2)
        diskKB        = [int](($kb1 - $kb0) / 3)
    }
}
```

4. `Run-C`를 쳐서 한 번 돌려 본다. 1분 안쪽이면 끝난다.

**보여야 하는 것.** 여섯 칸짜리 결과. 각 칸의 뜻은 다음과 같다.

| 칸 | 뜻 | 어디서 오는가 |
|---|---|---|
| elapsedMs | 2만 건이 모두 브로커 ack를 받기까지 걸린 시간. 3회 중 가운데 값 | `generate` 응답 |
| requests | 2만 건을 보내는 데 쓴 요청 수(1회분) | `kafka.producer.request.total`의 증가분 ÷ 3 |
| recordsPerReq | 요청 하나에 실린 평균 레코드 수 | `kafka.producer.records.per.request.avg` |
| batchBytes | 파티션별 배치 하나의 평균 크기(바이트) | `kafka.producer.batch.size.avg` |
| compression | 압축 후 크기 ÷ 압축 전 크기. 1이면 압축 안 함 | `kafka.producer.compression.rate.avg` |
| diskKB | 2만 건이 브로커 디스크에서 차지한 크기(1회분) | `du`로 잰 파티션 폴더 크기의 증가분 ÷ 3 |

`avg`가 붙은 지표는 최근 1분 안팎의 평균이라서 `Run-C` 직후에 읽어야 이번 실험의 값이 된다. 함수가 바로 읽으므로 신경 쓰지 않아도 된다. 지표 이름 목록은 http://localhost:8080/actuator/metrics 에서 볼 수 있다. 여기 쓰는 `kafka.producer.*`는 Spring Boot가 Kafka 클라이언트의 내부 지표를 Actuator로 옮겨 준 것이다.

**안 될 때.** `M`이 404 오류를 내면 앱이 아직 한 건도 발행하지 않아 지표가 없는 것이다. `Run-C`의 워밍업 호출이 지나면 생긴다. `Size`가 0이나 오류를 내면 kafka 컨테이너 이름이 `kafka`인지 `docker ps`로 본다.

## C1~C6. 설정 하나씩 바꿔 재기

**왜 하는가.** 처리량과 지연, 요청 수와 배치 크기가 설정에 따라 어떻게 움직이는지 숫자로 본다. 한 번에 **하나만** 바꾸고, 끝나면 되돌린 뒤 다음 것으로 간다.

**할 것.** 실험마다 같은 네 단계를 반복한다.

1. `application.properties`에서 아래 표의 설정 한 줄을 바꾸고 저장한다.
2. 앱을 재시작한다.
3. 명령 터미널에서 `Run-C`를 친다.
4. 결과 여섯 칸을 워크북 C절 표에 옮기고, 1에서 바꾼 줄을 기준값으로 되돌린다.

| 실험 | 바꿀 줄 (기준값 → 실험값) |
|---|---|
| C1 기준 | 바꾸지 않는다 |
| C2 | `spring.kafka.producer.properties[linger.ms]=5` → `0` |
| C3 | `spring.kafka.producer.properties[linger.ms]=5` → `50` |
| C4 | `spring.kafka.producer.batch-size=16384` → `1024` |
| C5 | `spring.kafka.producer.acks=all` → `1` |
| C6 | 파일에 압축 설정 줄이 없다. `linger.ms` 줄 바로 아래에 `spring.kafka.producer.compression-type=lz4`를 새로 넣고, 끝나면 지운다 |

**보여야 하는 것.** C1 기준값의 예시로, 2026-10-15에 이 PC에서 C0의 로그 레벨을 바꾸기 **전**(발행 성공 DEBUG 로그가 켜진 상태)에 `Run-C`를 돌린 결과가 있다.

```
elapsedMs     : 1292
requests      : 145
recordsPerReq : 134.9
batchBytes    : 15682
compression   : 1
diskKB        : 6271
```

`batchBytes`가 `batch.size`(16,384) 바로 아래다. 배치가 거의 꽉 찬 채로 나갔다는 뜻이다. `generate`는 2만 건을 한꺼번에 버퍼에 밀어 넣으므로 `linger.ms`(5ms)를 기다리기 전에 배치가 찬다. 요청 하나에는 파티션 셋의 배치가 함께 실리므로 `recordsPerReq`는 배치 하나에 든 레코드 수의 세 배쯤이 된다. 레코드 하나가 디스크에서 약 310바이트를 차지한다(6,271KB ÷ 2만 건).

C0의 로그 설정으로 바꾼 뒤의 기준값은 2026-10-19에 아래처럼 나왔다. 요청 수와 디스크 크기는 그대로인데 `elapsedMs`가 1,292에서 168로 줄었다. 메시지마다 콘솔에 한 줄씩 찍는 것이 전송 시간을 여덟 배 가까이 늘리고 있었다는 뜻이다. C2~C6은 이 값과 비교한다.

```
elapsedMs     : 168
requests      : 146
recordsPerReq : 123.5
batchBytes    : 13511
compression   : 1
diskKB        : 6273
```

C2~C6의 숫자는 직접 재서 채운다. 아래는 재기 전에 세운 예상이고, 괄호 안은 2026-10-19에 같은 절차로 잰 결과다. 숫자를 먼저 보지 말고 직접 잰 뒤에 맞춰 본다.

- C2 `linger.ms=0`: 기다리지 않고 준비되는 대로 보내므로 배치가 덜 찬 채로 나갈 수 있다. `requests`가 늘고 `batchBytes`가 줄어든다. 다만 몰아치는 부하에서는 Sender가 바쁜 동안 버퍼에 쌓이므로 차이가 작을 수 있다. (예상대로였다. `requests` 187, `batchBytes` 10,048, `elapsedMs` 154)
- C3 `linger.ms=50`: 몰아치는 부하에서는 배치가 50ms 전에 차므로 요청 수와 배치 크기는 C1과 비슷할 것이다. 다만 2만 건의 끝부분처럼 덜 찬 배치는 50ms를 다 기다린 뒤에 나가므로 전체 시간은 늘 수 있다. `linger.ms`가 진짜 힘을 쓰는 것은 메시지가 띄엄띄엄 올 때다(04 파일의 Fluent Bit 경로처럼 1초마다 몇 건씩). (`requests` 145, `batchBytes` 15,301로 C1과 같았고, `elapsedMs`는 311로 C1의 두 배 가까이 됐다. 처음에는 "C1과 비슷할 것"이라고만 예상했는데 시간은 비슷하지 않았다)
- C4 `batch-size=1024`: 배치 하나에 레코드가 서너 건밖에 안 들어간다. `requests`가 몇 배로 늘고 `elapsedMs`도 크게 늘 것이다. (`requests` 2,869로 약 20배, `recordsPerReq` 7.0, `elapsedMs` 895)
- C5 `acks=1`: 브로커가 하나뿐이라 리더 = 전체 복제본이다. C1과 거의 같아야 한다. (`elapsedMs` 171, `requests` 147로 같았다)
- C6 `lz4`: `compression`이 1보다 작아지고 `diskKB`가 그 비율 안팎으로 줄어든다. 로그는 같은 키 이름과 비슷한 문장이 반복되어 잘 줄어든다. (`compression` 0.22, `diskKB` 6,273 → 949. 압축된 배치에 레코드가 더 많이 들어가 `requests`도 54로 줄었다)

**생각해 볼 것.** C5에서 차이가 없는 이유를 `acks`의 정의로 설명한다. 차이가 생기려면 무엇이 필요한가? (Step 6) C2와 C3에서 차이가 작았다면, `generate`가 아닌 어떤 부하에서 차이가 커질지 말해 본다.

## C7. 키를 빼면 장비의 로그가 흩어진다

**왜 하는가.** 키가 있으면 같은 장비는 언제나 같은 파티션에 간다. 키를 빼면 무엇이 깨지는지 본다.

**할 것.**

1. `src/main/java/com/practice/kafka/producer/LogEventProducer.java`의 `send` 메서드에서 키 자리를 `null`로 바꾼다.

```java
        return kafkaTemplate.send(topic, null, event)     // 원래: event.deviceId()
```

2. 앱을 재시작하고 장비 3대 몫 300건을 보낸다.

```powershell
Invoke-RestMethod -Method Post "http://localhost:8080/api/logs/generate?count=300&devices=3"
```

3. Kafka UI → Topics → app-logs → Messages에서 `dev-0001`을 검색한다. 결과의 Partition 열을 본다.
4. 1에서 바꾼 것을 `event.deviceId()`로 되돌리고 앱을 재시작한다.

**보여야 하는 것.** 방금 보낸 `dev-0001`의 메시지가 둘 이상의 파티션에 흩어져 있다. 검색 결과에는 C1~C6에서 키를 붙여 보낸 `dev-0001`도 섞여 나오는데, 그것들은 모두 한 파티션에 있고 Key 칸이 `dev-0001`이다. 이번 것은 Key 칸이 비어 있으니 그것만 본다. 2026-10-19에는 키 없이 보낸 `dev-0001` 97건이 파티션 0에 19건, 1에 23건, 2에 55건으로 나뉘었다. 키 없는 메시지는 sticky 방식으로 한 파티션에 배치 크기(16KB, 약 50건)만큼 붙다가 다음 파티션으로 넘어가기 때문이다. 같은 장비의 로그가 여러 파티션에 나뉘면 컨슈머 여럿이 나눠 읽을 때 장비 단위 순서가 깨진다.

**안 될 때.** 앱 콘솔에 `Missing header 'kafka_receivedMessageKey'`와 `Backoff ... exhausted`가 쏟아지면 2026-10-15에 고치기 전 코드다. 그 코드는 컨슈머가 키 헤더를 필수로 받는데, 키 없이 보낸 메시지에는 그 헤더가 아예 없다. 그러면 예외가 나고, 에러 핸들러가 10번 시도한 뒤 메시지를 건너뛴다. `LogEventConsumer`의 `@Header(... RECEIVED_KEY ...)`에 `required = false`가 있는지 본다. "처리 못 한 메시지를 건너뛰면 사실상 유실"이라는 이 문제는 Step 5의 Dead Letter Topic이 다룬다.

## C8. Kafka가 멈춘 동안의 발행

**왜 하는가.** B2의 질문, 즉 "202를 받았으면 기록된 것인가"에 실험으로 답한다. 브로커가 사라지면 `send()`가 어떻게 실패하는지 본다. 04 파일 D5(같은 장애를 Fluent Bit 경로로 겪는 것)와 짝을 이룬다.

**할 것.**

1. C0의 로그 레벨은 그대로 둬도 된다. 실패 로그는 ERROR라서 보인다.
2. 명령 터미널에서 Kafka를 멈추고, 바로 한 건을 보내며 걸린 시간을 잰다.

```powershell
docker stop kafka
$sw = [Diagnostics.Stopwatch]::StartNew()
try { Invoke-RestMethod -Method Post -Uri http://localhost:8080/api/logs -ContentType 'application/json' -Body '{"deviceId":"dev-0098","raw":"2026-10-12 14:03:21.123 [ERROR] sent while kafka is down"}' | Out-Null; "응답: 성공" } catch { "응답: $($_.Exception.Message)" }
"걸린 시간: $([int]$sw.Elapsed.TotalSeconds)초"
```

3. 응답을 기다리는 동안 앱 콘솔을 본다.
4. 응답이 오면 Kafka를 다시 띄운다. kafka가 healthy가 된 뒤 Kafka UI Messages에서 이 메시지의 본문 `sent while kafka is down`을 검색한다. `dev-0098`로 찾으면 안 된다. C1~C6의 `generate`가 장비 200대 몫(`dev-0001`~`dev-0200`)을 보냈으므로 `dev-0098` 메시지는 이미 수천 건 있다.

```powershell
docker start kafka
```

**보여야 하는 것.** 2026-10-15 실측이다. 요청이 **60초 동안 응답 없이 멈춰 있다가** 500 오류로 끝났다. 터미널에 `응답: ...500...`과 `걸린 시간: 60초`가 찍힌다(오류 문구는 PowerShell 버전과 언어 설정에 따라 다르다). 그동안 앱 콘솔에는 프로듀서와 컨슈머가 `Connection to node -1 (localhost/127.0.0.1:9092) could not be established` 경고를 반복해 찍는다. 60초가 되면 아래가 나온다.

```
ERROR ... o.s.k.support.LoggingProducerListener : Exception thrown when sending a message with key='dev-0098' ...
org.apache.kafka.common.errors.TimeoutException: Topic app-logs not present in metadata after 60000 ms.
```

Kafka를 다시 띄운 뒤에도 `sent while kafka is down`은 없다. 이 메시지는 사라졌다. 호출자는 500을 받았고, 다시 보낼 주체가 없다. 2026-10-19 재현에서도 61초 뒤 500, 같은 `TimeoutException`, 검색 결과 0건으로 같았다.

왜 202로 즉시 돌아오지 않았는가. Kafka 4 클라이언트는 알던 브로커가 모두 끊기면 메타데이터(토픽의 파티션과 리더 정보)를 버리고 `bootstrap-servers`부터 다시 시작한다(`metadata.recovery.strategy=rebootstrap`, 4.0부터 기본값). 브로커가 하나뿐이니 멈추는 즉시 이 상태가 된다. `send()`는 레코드를 어느 파티션에 넣을지 정해야 버퍼에 담을 수 있는데, 메타데이터가 없으니 요청 스레드에서 `max.block.ms`(기본 60초)까지 기다리다 예외를 던진다. `study/03`의 "send()는 버퍼에 넣고 즉시 반환한다"는 메타데이터가 있을 때의 이야기다.

**생각해 볼 것.** 이 60초 동안 요청 스레드는 붙잡혀 있다. 장비 1,000대가 동시에 보내는 수집 서버라면 Tomcat의 요청 스레드(기본 200개)가 어떻게 될까? 수집 서버가 Kafka 장애를 더 빨리 알아채고 거절하려면 어떤 설정을 줄여야 할까? (Step 5에서 다룬다) 반대로, 같은 장애에서 Fluent Bit 경로의 로그는 유실되지 않는다. 04 파일 D5에서 그 차이를 확인한다.

## 다 됐으면
