# 08. 적재 경로 비교 (워크북 I절, Step 4+, `study/11`)

같은 장비 로그를 네 경로로 동시에 ClickHouse에 넣고, INSERT가 만든 part 수, 저장까지의 지연, ClickHouse가 멈췄을 때의 복구, 다시 넣기(재처리)를 비교한다. 설명은 `../study/11-적재-경로-비교.md`에 있다.

```
                 ┌─ fluent-bit ──────────▶ /ingest/fluentbit ─▶ Kafka ─┬─▶ 앱 적재 컨슈머 ─────────▶ app_logs
장비 로그 파일 ──┤                                                     └─▶ Kafka 테이블 엔진 ─▶ 구체화 뷰 ─▶ app_logs_kafka_engine
(같은 파일)      ├─ fluent-bit-direct ───▶ /ingest/direct ───────────────────────────────────────────▶ app_logs_direct
                 └─ fluent-bit-direct-async ▶ /ingest/direct?async=true ─────────────────────────────▶ app_logs_direct_async
```

시작 전 상태: 07 파일을 마쳤다. 앱은 꺼 둔다. 이 파일은 앱을 `--app.compare.enabled=true`로 띄운다. 직접 적재 엔드포인트(`/ingest/direct`)와 비교 통계(`/api/compare/stats`)는 이 인자가 있어야 열린다.

비교는 네 경로가 같은 출발선에 서야 의미가 있으므로 I0에서 모든 볼륨을 지우고 시작한다. 07 파일까지 쌓은 데이터는 사라진다.

## I0. 준비

**왜 하는가.** 비교용 에이전트 둘(compose의 `compare` 프로필)과 비교 테이블 넷을 빈 상태에서 띄운다.

**할 것.**

1. 앱이 떠 있으면 정상 종료하고, 모두 지운 뒤 `compare` 프로필로 띄운다.

```powershell
docker compose -f docker/docker-compose.yml --profile compare down -v
Remove-Item -Recurse -Force docker\devices\sim, docker\devices\OHT-* -ErrorAction SilentlyContinue
docker compose -f docker/docker-compose.yml --profile compare up -d --wait
```

2. 앱 터미널에서 jar를 만들고 띄운다. 로그 인자 셋은 07 파일 H6과 같은 이유로 붙인다(초당 6,000줄을 콘솔에 찍으면 비교가 콘솔 속도 비교가 된다).

```powershell
$env:JAVA_HOME = "C:\Program Files\JetBrains\IntelliJ IDEA 2026.1.4\jbr"; .\gradlew.bat bootJar
& "$env:JAVA_HOME\bin\java.exe" -jar build\libs\practice-kafka-0.0.1-SNAPSHOT.jar --app.compare.enabled=true --logging.level.com.practice.kafka.producer=INFO --logging.level.com.practice.kafka.consumer=WARN --logging.level.com.practice.kafka.ingest=INFO
```

3. 앱 콘솔에 `clickhouse-sink: partitions assigned`가 나오면(토픽이 생겼다는 뜻) 명령 터미널에서 비교 테이블을 만들고, 100줄로 네 경로가 모두 이어졌는지 본다.

```powershell
docker exec clickhouse clickhouse-client --user app --password app --queries-file /compare/01-tables.sql
Invoke-RestMethod -Method Post "http://localhost:8080/api/logs/simulate?lines=100"; Start-Sleep -Seconds 10
docker exec clickhouse clickhouse-client --user app --password app --query "SELECT (SELECT count() FROM logs.app_logs), (SELECT count() FROM logs.app_logs_kafka_engine), (SELECT count() FROM logs.app_logs_direct), (SELECT count() FROM logs.app_logs_direct_async)"
```

**보여야 하는 것.** `docker ps`에 fluent-bit-direct, fluent-bit-direct-async가 더해져 컨테이너가 일곱이다. 마지막 쿼리가 `100	100	100	100`(2026-10-19 확인). `Invoke-RestMethod http://localhost:8080/api/compare/stats`는 직접 적재 두 경로가 각각 INSERT 20번 남짓(장비 파일 수만큼)으로 100행을 넣었다고 보여 준다.

**안 될 때.** 넷째 값(async)만 0이면 앱의 `app.clickhouse.max-connections`나 ClickHouse 쪽 오류를 앱 콘솔에서 본다. 둘째 값(Kafka 테이블 엔진)만 0이면 `SELECT * FROM system.kafka_consumers FORMAT Vertical`의 `exceptions.text`를 본다. 앱이 토픽을 만들기 전에 01-tables.sql을 돌렸으면 엔진이 토픽을 못 찾아 기다리고 있을 수 있다. fluent-bit-direct 로그의 `read error, check permissions: /var/log/devices/sim/*.log`는 폴더가 아직 없어서 나오는 것이라 무시해도 된다.

## I1. 평시 부하 10분

**왜 하는가.** 장비 100대가 1대당 초당 60줄(OHT 차량의 peak 강도)을 10분 동안 쓸 때, 같은 360만 줄이 경로마다 part를 몇 개 만들고 얼마나 늦게 저장되는지 본다.

**할 것.**

1. 부하를 건다. 기본값이 장비 100대, 1대당 초당 60줄, 600초다.

```powershell
Invoke-RestMethod -Method Post "http://localhost:8080/api/logs/simulate/start"
```

2. 도는 동안 active part 수를 몇 번 본다(선택).

```powershell
docker exec clickhouse clickhouse-client --user app --password app --query "SELECT table, count() FROM system.parts WHERE database = 'logs' AND active GROUP BY table ORDER BY table"
```

3. 10분이 지나 `GET /api/logs/stats`의 `simulatorRunning`이 `False`가 되고 네 테이블의 행 수가 `simulatorWritten`(100줄 + 360만 줄)과 같아지면 비교 쿼리를 돌린다.

```powershell
docker exec clickhouse clickhouse-client --user app --password app --format PrettyCompactMonoBlock --queries-file /compare/02-compare.sql
Invoke-RestMethod http://localhost:8080/api/compare/stats | ConvertTo-Json
Invoke-RestMethod http://localhost:8080/api/sink/stats
```

**보여야 하는 것.** 2026-10-19 실측. 도는 동안 active part는 직접 적재가 최대 62개, 나머지는 12개 이하였다. 비교 쿼리의 2번 표(part와 병합)는 아래와 같았다.

```
tbl                    new_parts  rows_per_part  merges  merge_read_x  merge_seconds
app_logs                    1192           3020     229          4.59           14.4
app_logs_direct            55838             64    5393         15.86          197
app_logs_direct_async       1669           2157     335          6.18           23.8
app_logs_kafka_engine         77          46751      13          1.67            5.3
```

4번 표(저장 지연)는 Kafka 경유 p50 1,107ms / p99 2,319ms, 직접 적재 843 / 1,878, 비동기 987 / 2,195, Kafka 테이블 엔진 4,833 / 9,142였다. 5번 표(앱이 보낸 INSERT의 응답)는 Kafka 경유 p50 10ms, 직접 적재 22ms, 비동기 186ms다. 병합이 끝난 뒤의 디스크 크기는 넷 다 121.5~121.8MiB로 같다. 이 숫자를 읽는 법은 `study/11` 4절이다.

1번 표의 `rows`가 `simulatorWritten`보다 조금 적고 더 늘지 않으면 아래 "안 될 때"를 본다.

**안 될 때.** 10분이 지나도 테이블 하나 이상의 행 수가 `simulatorWritten`보다 수백 줄 적은 채 멈춰 있을 수 있다. 2026-10-19에는 세 에이전트 모두에서 그랬다(242줄, 507줄, 160줄). 그 경로의 Fluent Bit 지표에서 `input.records`(읽은 줄)와 `output.http.0.proc_records`(보낸 줄)를 비교해 차이가 같으면, 그 줄들은 에이전트의 디스크 버퍼에 청크로 남아 있다. `docker restart fluent-bit fluent-bit-direct fluent-bit-direct-async`로 재시작하면 2초 안에 들어온다. 다만 재시작한 Fluent Bit 4.2.8은 그 뒤에 읽는 줄의 `offset`을 0부터 다시 매긴다(`study/11` 6절). I2는 그 상태에서 하게 되므로 I2의 멱등키 수가 쓴 줄 수보다 줄어든다.

## I2. ClickHouse가 3분 멈추면

**왜 하는가.** 저장소가 멈췄을 때 경로마다 로그가 어디서 기다리고, 다시 켜면 얼마 만에 따라잡는지 본다.

**할 것.** I1에 이어서 한다. 부하를 8분 걸고 2분째에 멈췄다가 5분째에 켠다. 명령 터미널에서 시각을 적어 가며 친다.

```powershell
Invoke-RestMethod -Method Post "http://localhost:8080/api/logs/simulate/start?seconds=480"
Start-Sleep -Seconds 120; docker stop clickhouse; (Get-Date).ToString('HH:mm:ss')
Start-Sleep -Seconds 90
Invoke-RestMethod http://localhost:8080/api/sink/stats                     # lag 이 쌓인다
Invoke-RestMethod http://localhost:8080/api/compare/stats | ConvertTo-Json  # 직접 적재의 failures(500)가 는다
(Invoke-RestMethod http://localhost:2021/api/v1/storage).input_chunks.'tail.0'.chunks   # 직접 적재 에이전트에 쌓인 청크
Start-Sleep -Seconds 90; docker start clickhouse; (Get-Date).ToString('HH:mm:ss')
```

다시 켠 뒤 10초마다 네 테이블의 행 수를 보며, 켜기 직전의 `simulatorWritten`을 넘는 시각을 경로마다 적는다.

```powershell
docker exec clickhouse clickhouse-client --user app --password app --query "SELECT (SELECT count() FROM logs.app_logs), (SELECT count() FROM logs.app_logs_kafka_engine), (SELECT count() FROM logs.app_logs_direct), (SELECT count() FROM logs.app_logs_direct_async)"
```

**보여야 하는 것.** 2026-10-19 실측. 멈춘 동안 적재 컨슈머의 `lag`은 최대 1,121,952까지 쌓였고 `failures`는 1초마다 늘었다(모두 156). 수집 서버의 `receivedFromFluentBit`은 멈추지 않고 늘었다. 직접 적재 두 경로는 수집 서버가 500을 9,802번, 11,621번 돌려줬고, 에이전트의 청크가 최대 1,810개, 2,054개까지 쌓였다. 다시 켠 뒤 켜기 직전까지 쓰인 줄을 다 저장하기까지 Kafka 테이블 엔진 17~22초, Kafka 경유 22~28초, 직접 적재 둘은 33~39초였다. 같은 키에 같은 줄이 두 번 들어간 진짜 중복은 네 경로 모두 0이었다.

**안 될 때.** 직접 적재 경로가 몇 분이 지나도 따라잡지 못하면 Fluent Bit의 재시도 간격이 늘어난 것이다. 이 실습의 에이전트는 상한을 60초로 줄여 두었다(`fluent-bit-direct.conf`의 `scheduler.cap`). 다 따라잡은 뒤에도 수백 줄이 모자라면 I1의 "안 될 때"와 같다.

**생각해 볼 것.** 멈춘 3분 동안 경로마다 로그는 어디서 기다렸는가? 실제로는 장비 1,000대가 각자 기다린다. 그 디스크가 차면 어떻게 되는가?

## I3. 다시 넣기 (재처리)

**왜 하는가.** Kafka를 거치면 지난 로그를 저장소에 다시 넣을 수 있다는 것을 본다. 파서를 고쳤거나 테이블을 새로 만들었을 때 쓰는 방법이다.

**할 것.** 앱을 정상 종료하고, 적재 컨슈머 그룹의 오프셋을 처음으로 되돌린 뒤 다시 띄운다.

```powershell
Invoke-RestMethod -Method Post http://localhost:8080/actuator/shutdown -ContentType application/json
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --group clickhouse-sink --topic app-logs --reset-offsets --to-earliest --execute
# 앱을 I0 의 명령으로 다시 띄우고, lag 이 0 이 될 때까지 기다린다
Invoke-RestMethod http://localhost:8080/api/sink/stats
docker exec clickhouse clickhouse-client --user app --password app --query "SELECT count(), (SELECT count() FROM logs.app_logs FINAL), uniqExact(device_id, source, offset) FROM logs.app_logs"
```

**보여야 하는 것.** 오프셋을 되돌리는 명령이 파티션 여섯 개의 `NEW-OFFSET 0`을 찍는다. 앱이 뜨면 토픽의 모든 메시지를 다시 넣는다. 2026-10-19에는 6,480,100행이 INSERT 353번(한 번에 약 18,400행)으로 82초 만에 들어갔다. `count()`는 두 배 가까이(12,888,502) 됐지만 `FINAL`과 고유 멱등키 수는 다시 넣기 전과 같았다(6,434,439). 같은 키를 다시 넣었으므로 저장소가 접는다. `log-printer`, `log-stats` 그룹은 오프셋을 건드리지 않았으므로 아무것도 다시 읽지 않는다.

**생각해 볼 것.** 직접 적재 경로에서 같은 일을 하려면 무엇이 필요한가? Kafka의 보존 기간(기본 7일)이 지난 로그는 어떻게 다시 넣는가?

## I4. 정리

비교 테이블을 지우면 ClickHouse 안의 Kafka 컨슈머도 멈춘다. 비교 에이전트 둘은 프로필을 붙여 내린다.

```powershell
docker exec clickhouse clickhouse-client --user app --password app --queries-file /compare/99-drop.sql
docker compose -f docker/docker-compose.yml --profile compare stop fluent-bit-direct fluent-bit-direct-async
```

앱은 정상 종료한다. 다음에 앱을 띄울 때는 `--app.compare.enabled=true`를 빼도 된다.
