# 06. 파티션과 컨슈머 그룹 (워크북 G절, `study/07`)

파티션을 6개로 늘리고, 앱을 두 개 띄워 파티션이 나뉘고 다시 모이는 순간을 콘솔 시각으로 본다. 설명은 `../study/07-파티션과-리밸런스.md`에 있다.

시작 전 상태: 04 파일까지 마쳐 컨테이너가 떠 있다. 앱은 꺼 둔다. 이 파일에서는 앱을 두 개 띄우므로 IntelliJ 대신 jar를 직접 실행하는 방법을 쓴다(IntelliJ로 하려면 실행 구성을 복제해 Program arguments에 `--server.port=8081`을 넣으면 된다).

이제 00 파일 0-3의 단계 인자 셋 중 둘(파티션 3, 스레드 1)은 빼고 하나만 남긴다. `--app.sink.enabled=false`다. 앱 둘이 그룹에 드나들 때 적재 컨슈머 그룹(`clickhouse-sink`)까지 리밸런스되면 콘솔이 복잡해지고, 적재 컨슈머가 처음 붙는 순간(쌓여 있던 메시지가 한꺼번에 ClickHouse로 가는 것)은 07 파일 H6에서 따로 보기 때문이다. 아래 명령에는 이 인자가 들어 있다. IntelliJ를 쓰면 Program arguments를 이 한 개로 바꾼다.

터미널 셋을 쓴다. **앱 A 터미널**, **앱 B 터미널**, **명령 터미널**이다. 셋 다 프로젝트 루트에서 연다. 앱 터미널 둘에는 먼저 아래 두 줄을 붙여 넣는다.

```powershell
$env:JAVA_HOME = "C:\Program Files\JetBrains\IntelliJ IDEA 2026.1.4\jbr"
$java = "$env:JAVA_HOME\bin\java.exe"
```

명령 터미널에서 jar를 한 번 만든다.

```powershell
$env:JAVA_HOME = "C:\Program Files\JetBrains\IntelliJ IDEA 2026.1.4\jbr"; .\gradlew.bat bootJar
```

## G1. 파티션 늘리기

**왜 하는가.** 설정의 파티션 수(6)가 브로커의 실제(3)보다 크면 앱이 뜰 때 늘린다. 그 순간과 결과를 본다.

**할 것.**

1. 앱 A 터미널에서 앱을 띄운다.

```powershell
& $java -jar build\libs\practice-kafka-0.0.1-SNAPSHOT.jar --app.sink.enabled=false
```

2. 명령 터미널에서 토픽을 본다.

```powershell
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic app-logs
```

**보여야 하는 것.** 앱 A 콘솔(2026-10-19 실측):

```
KafkaAdmin : Topic 'app-logs' exists but has a different partition count: 3 not 6, increasing if the broker supports it
log-printer: partitions assigned: [app-logs-0, app-logs-1]
log-printer: partitions assigned: [app-logs-2, app-logs-3]
log-printer: partitions assigned: [app-logs-4, app-logs-5]
```

토픽 설명의 첫 줄에 `PartitionCount: 6`. 이미 6개였다면 `increasing` 줄은 나오지 않는다. 사이사이에 `log-stats: partitions assigned` 줄도 섞여 나온다. 2026-10-19에 00 파일부터 깨끗하게 다시 했을 때도 같은 줄이 나왔다.

**안 될 때.** `increasing` 대신 오류가 나면 브로커가 떠 있는지(`docker ps`) 본다. Git Bash에서 `docker exec`를 치면 `/opt/...` 경로가 바뀌어 실패한다. PowerShell을 쓴다.

**생각해 볼 것.** 늘린 직후 같은 장비의 로그가 왜 다른 파티션으로 갈 수 있는가?

## G2. 스레드별 할당

**왜 하는가.** `concurrency=3`이 실제로 컨슈머 셋을 만들고 파티션을 둘씩 나눴는지 확인한다.

**할 것.** 명령 터미널에서:

```powershell
Invoke-RestMethod http://localhost:8080/api/logs/assignments | ConvertTo-Json -Depth 4
```

**보여야 하는 것.** 그룹마다 client.id 셋, 각자 파티션 둘. 2026-10-19 실측:

```json
{"log-printer":{"consumer-log-printer-1":[0,1],"consumer-log-printer-2":[2,3],"consumer-log-printer-3":[4,5]},
 "log-stats":{"consumer-log-stats-4":[0,1],"consumer-log-stats-5":[2,3],"consumer-log-stats-6":[4,5]}}
```

Kafka UI → Consumers → log-printer 에서도 멤버 셋과 각자의 파티션이 보인다.

**안 될 때.** 빈 목록이면 앱이 막 떠서 할당 전이다. 몇 초 뒤 다시 부른다. 한 그룹에서 스레드 하나만 빈 목록이고 나머지 둘이 셋씩 가진 모습도 잠깐 보일 수 있다. 2026-10-19 재현에서 `log-stats`가 `[0,1,2]`, `[]`, `[3,4,5]`였다가 3초 뒤 둘씩으로 다시 나뉘었다. 세 스레드 중 하나가 첫 할당이 끝난 뒤에 그룹에 들어와 리밸런스가 한 번 더 일어난 것이다. compose가 브로커의 `group.initial.rebalance.delay.ms`를 0으로 두어(학습 중 기다리지 않으려고) 늦게 온 멤버를 기다려 주지 않는다.

## G3. 그룹 간 브로드캐스트

**왜 하는가.** 그룹이 다르면 같은 메시지를 따로 전부 받는다는 것을 숫자로 본다.

**할 것.**

```powershell
$s0 = Invoke-RestMethod http://localhost:8080/api/logs/stats
Invoke-RestMethod -Method Post "http://localhost:8080/api/logs/generate?count=1000&devices=50"
Start-Sleep -Seconds 4
$s1 = Invoke-RestMethod http://localhost:8080/api/logs/stats
"log-printer +{0}, log-stats +{1}" -f ($s1.consumed - $s0.consumed), ($s1.statsTotal - $s0.statsTotal)
$s1.statsByLevel
```

**보여야 하는 것.** `log-printer +1000, log-stats +1000`. 앱 A 콘솔에는 `[consume #...]` 줄이 1,000개 찍히고(log-printer), log-stats는 아무것도 찍지 않는다. `statsByLevel`은 INFO가 가장 많고 DEBUG, WARN, ERROR 순이다.

`$s0.statsTotal`은 0이다. 앱이 막 떴고, `log-stats` 그룹은 B절부터 앱과 함께 떠서 그때그때 커밋해 왔으므로 새로 읽을 과거분이 없다. 반대로 그룹이 처음 생기는 순간이라면 쌓여 있던 메시지를 처음부터 다 읽는다. 앞선 검증(2026-10-19, 이 그룹이 없던 코드로 실습을 하다가 처음 띄운 경우)에서는 `$s0.statsTotal`이 121,403이었다. 처음 생기는 그룹이 과거분을 한꺼번에 읽는 모습은 07 파일 H6의 `clickhouse-sink`에서 직접 본다.

**생각해 볼 것.** 처음 생긴 그룹이 과거 메시지까지 읽는 것은 어떤 설정 때문인가? 원하지 않으면 무엇을 바꾸는가?

## G4. 두 번째 앱 합류

**왜 하는가.** 그룹에 컨슈머가 늘 때 파티션이 다시 나뉘는 순간(리밸런스)을 본다.

**할 것.**

1. 앱 B 터미널에서:

```powershell
& $java -jar build\libs\practice-kafka-0.0.1-SNAPSHOT.jar --app.sink.enabled=false --server.port=8081
```

2. 앱 A 콘솔에서 `partitions revoked`와 `partitions assigned` 줄의 시각을 본다.
3. 명령 터미널에서 두 앱의 할당과, 1,000건이 어떻게 나뉘는지 본다.

```powershell
Invoke-RestMethod http://localhost:8080/api/logs/assignments | ConvertTo-Json -Depth 4 -Compress
Invoke-RestMethod http://localhost:8081/api/logs/assignments | ConvertTo-Json -Depth 4 -Compress
$a0 = Invoke-RestMethod http://localhost:8080/api/logs/stats; $b0 = Invoke-RestMethod http://localhost:8081/api/logs/stats
Invoke-RestMethod -Method Post "http://localhost:8080/api/logs/generate?count=1000&devices=50"; Start-Sleep -Seconds 4
$a1 = Invoke-RestMethod http://localhost:8080/api/logs/stats; $b1 = Invoke-RestMethod http://localhost:8081/api/logs/stats
"log-printer: A +{0}, B +{1}" -f ($a1.consumed - $a0.consumed), ($b1.consumed - $b0.consumed)
```

**보여야 하는 것.** 앱 A 콘솔(2026-10-19 실측). 세 스레드가 같은 순간에 파티션을 **전부** 내려놓고 하나씩 다시 받는다.

```
15:19:44.177 log-printer: partitions revoked: [app-logs-0, app-logs-1]
15:19:44.177 log-printer: partitions revoked: [app-logs-4, app-logs-5]
15:19:44.177 log-printer: partitions revoked: [app-logs-2, app-logs-3]
15:19:44.190 log-printer: partitions assigned: [app-logs-3]
15:19:44.190 log-printer: partitions assigned: [app-logs-5]
15:19:44.191 log-printer: partitions assigned: [app-logs-1]
```

앱 B 콘솔에는 15:19:44.217에 나머지 셋(0, 2, 4)이 들어온다. 1,000건은 `A +436, B +564`처럼 둘로 나뉜다(합이 1,000이면 된다). 어느 파티션이 누구에게 가는지는 매번 다를 수 있다. 깨끗한 환경에서 다시 한 2026-10-19 재현에서는 A가 16:52:10.133~.164에 여섯 개를 내려놓고 .174에 0, 2, 4를, B가 .192에 1, 3, 5를 받았고, 1,000건은 `A +578, B +422`로 나뉘었다.

**생각해 볼 것.** A가 계속 읽을 파티션까지 내려놓았다가 다시 받은 이유는 무엇인가? 그동안 무슨 일이 멈췄는가?

## G5. 정상 종료와 강제 종료

**왜 하는가.** 컨슈머가 떠난다고 말하고 가는 것과 말없이 사라지는 것의 차이를 시간으로 잰다.

**할 것.**

1. 정상 종료. 명령 터미널에서:

```powershell
(Get-Date).ToString('HH:mm:ss.fff'); Invoke-RestMethod -Method Post http://localhost:8081/actuator/shutdown -ContentType application/json
```

앱 A 콘솔에서 6개를 다시 받는 시각을 본다.

2. 앱 B를 G4처럼 다시 띄우고, 이번에는 강제로 죽인다.

```powershell
(Get-Date).ToString('HH:mm:ss.fff'); Stop-Process -Id (Get-NetTCPConnection -LocalPort 8081 -State Listen).OwningProcess -Force
```

앱 A 콘솔을 1분 동안 지켜본다.

**보여야 하는 것.** 2026-10-19 실측. 정상 종료는 B가 15:23:25.599에 파티션을 내려놓고 A가 15:23:27.040에 6개를 받았다(약 1.4초). 강제 종료는 15:20:36.277에 죽였고 A가 15:21:20.414에야 6개를 받았다(약 44초). 그 44초 동안 B가 맡던 파티션의 메시지는 Kafka에 쌓이기만 했다. 같은 날 깨끗한 환경에서 다시 했을 때는 정상 종료 0.2초(B 내려놓음 16:52:27.996, A 받음 16:52:28.219), 강제 종료 45.6초(16:52:45.862에 죽이고 16:53:31.448에 받음)였다. 정상 종료는 1초 안팎, 강제 종료는 45초 안팎이라는 차이가 핵심이다.

**안 될 때.** `shutdown`이 415(Unsupported Media Type)로 실패하면 `-ContentType application/json`을 빠뜨린 것이다. PowerShell은 본문 없는 POST에 Actuator가 받지 않는 형식을 붙인다. 404면 jar를 이 단계의 코드로 다시 만들지 않은 것이다(`bootJar`).

**생각해 볼 것.** 44초는 어디서 온 숫자인가? 줄이면 무엇이 좋아지고 무엇이 나빠지는가?

## G6. 컨슈머가 파티션보다 많을 때

**왜 하는가.** 파티션 수가 병렬의 상한이라는 것을 눈으로 본다.

**할 것.** 앱 B를 스레드 6개로 띄운다.

```powershell
& $java -jar build\libs\practice-kafka-0.0.1-SNAPSHOT.jar --app.sink.enabled=false --server.port=8081 --spring.kafka.listener.concurrency=6
```

명령 터미널에서 B의 할당을 본다.

```powershell
Invoke-RestMethod http://localhost:8081/api/logs/assignments | ConvertTo-Json -Depth 4 -Compress
```

**보여야 하는 것.** 그룹 컨슈머는 9개(A 3 + B 6)인데 파티션은 6개다. B의 스레드 중 셋은 빈 목록이다(2026-10-19 실측).

```json
{"log-printer":{"consumer-log-printer-1":[0],"consumer-log-printer-2":[2],"consumer-log-printer-3":[4],
 "consumer-log-printer-4":[],"consumer-log-printer-5":[],"consumer-log-printer-6":[]}, ...}
```

## G7. (선택) 새 그룹 프로토콜

**왜 하는가.** Kafka 4의 새 프로토콜에서 리밸런스가 어떻게 달라지는지 본다. 지금 몰라도 다음 단계에 지장이 없다.

**할 것.** 두 앱을 모두 정상 종료한 뒤, 둘 다 아래 인자를 붙여 차례로 띄운다(B는 포트도 붙인다).

```powershell
& $java -jar build\libs\practice-kafka-0.0.1-SNAPSHOT.jar --app.sink.enabled=false "--spring.kafka.consumer.properties[group.protocol]=consumer"
```

**보여야 하는 것.** B가 들어올 때 A 콘솔에 `revoked`가 6개 전부가 아니라 일부(2026-10-19에는 1, 4, 5번)만 찍힌다. 그 파티션은 5초쯤 뒤 B 콘솔에 `assigned`로 나타난다. 나머지는 멈추지 않는다. 깨끗한 환경에서 다시 했을 때도 1, 4, 5번이 16:54:22.846~26.004에 하나씩 넘어가 B에 16:54:27.548에 들어왔다. A가 혼자 뜰 때도 한 스레드가 여섯 개를 다 받았다가 다른 두 스레드에게 넷을 넘기는 과정이 콘솔에 보인다. 끝나면 두 앱을 정상 종료하고, 다음부터는 이 인자 없이 띄운다.
