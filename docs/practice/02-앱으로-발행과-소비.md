# 02. 앱으로 발행과 소비 (워크북 B절, Step 1)

이제 Spring 앱이 프로듀서와 컨슈머 역할을 한다. REST로 한 건을 보내 정규화 → 발행 → 소비가 한 바퀴 도는 것을 보고, 앱을 껐다 켜며 "컨슈머 그룹이 어디까지 읽었는지 기억한다"는 것을 확인한다.

시작 전 상태: 01 파일을 마쳐 컨테이너 셋이 떠 있고 토픽이 비어 있다. 앱은 꺼져 있다.

## B0. 그림으로 먼저 보기

**왜 하는가.** 실제 Kafka로 들어가기 전에 오프셋, 커밋, 컨슈머 그룹이 어떻게 움직이는지 장난감 모형으로 손에 익힌다. 이 모형은 실제 Kafka에 연결하지 않는다.

**할 것.** 탐색기에서 `docs/concepts/01-kafka-basics.html`을 더블클릭해 브라우저로 연다.

1. 3절에서 컨슈머 수를 1 → 3 → 4로 바꾼다. 파티션 3개를 컨슈머들이 어떻게 나눠 갖는지 본다.
2. 4절에서 "두 건 처리 → 커밋 없이 재시작 → 다시 처리"를 한다. 처음 상태로 돌린 뒤 "두 건 처리 → 커밋 → 재시작"과 비교한다.
3. 5절에서 "컨슈머 정지 → 세 턴 발행 → 재개 → 발행 없이 소비"를 한다.

**보여야 하는 것.** 네 번째 컨슈머는 맡을 파티션이 없어 대기한다. 커밋 전에 재시작하면 같은 메시지를 다시 처리한다. 소비해도 Kafka에 쌓인 기록 수는 줄지 않는다.

**생각해 볼 것.** 커밋 위치가 2이면 다음에 읽을 오프셋은 무엇인가? 로그 파일의 offset(바이트 위치)과 Kafka의 offset(파티션 안 순번)은 무엇이 다른가?

## B1. 앱 기동

**왜 하는가.** 앱이 뜰 때 세 가지가 일어난다. `KafkaTopicConfig`가 `app-logs` 토픽(파티션 3)을 만들고, 리스너 컨테이너가 `log-printer` 그룹으로 접속하고, 그룹이 세 파티션을 이 컨슈머에게 맡긴다. 이 세 번째가 "읽을 준비가 됐다"는 신호다.

**할 것.** IntelliJ에서 `PracticeKafkaApplication`을 실행한다(00 파일 0-3). 터미널을 쓰면 새 탭에서 `JAVA_HOME`을 잡고 `.\gradlew.bat bootRun`을 친다.

**보여야 하는 것.** 앱 콘솔에 아래 세 줄이 순서대로 나온다(2026-10-14 실측, 앞부분 시각과 PID는 매번 다르다).

```
... o.s.boot.tomcat.TomcatWebServer          : Tomcat started on port 8080 (http) with context path '/'
... c.p.kafka.PracticeKafkaApplication       : Started PracticeKafkaApplication in 2.627 seconds
... o.s.k.l.KafkaMessageListenerContainer    : log-printer: partitions assigned: [app-logs-0, app-logs-1, app-logs-2]
```

Kafka UI → Topics에 `app-logs`가 생기고, 눌러 보면 Partitions가 3이다. 앱 콘솔 검색(Ctrl+F)으로 `partitions assigned`를 찾으면 빠르다.

**안 될 때.** `Connection to node -1 (localhost/127.0.0.1:9092) could not be established`가 반복되면 Kafka가 안 떠 있다(`docker compose -f docker/docker-compose.yml ps`). `Port 8080 was already in use`면 앱이 이미 하나 떠 있다. IntelliJ Run 창의 다른 탭이나 다른 터미널의 bootRun을 끈다.

## B2. 한 건 발행

**왜 하는가.** 원문 한 줄이 `LogEvent`로 정규화되어 Kafka에 들어가고 컨슈머가 꺼내는 한 바퀴를 본다. 응답 본문이 정규화 결과라서 `LogNormalizer`가 무엇을 했는지 바로 보인다.

**할 것.** 명령 터미널에서 친다.

```powershell
Invoke-RestMethod -Method Post -Uri http://localhost:8080/api/logs -ContentType 'application/json' -Body '{"deviceId":"dev-0001","raw":"2026-10-12 14:03:21.123 [ERROR] NullPointerException at OrderService.create"}' | ConvertTo-Json
```

끝의 `| ConvertTo-Json`은 응답을 JSON 모양 그대로 보여 달라는 뜻이다. 빼면 PowerShell이 표 모양으로 보여 준다.

**보여야 하는 것.** 응답(2026-10-14 실측):

```json
{
  "device_id": "dev-0001",
  "source": "manual://dev-0001.log",
  "event_time": "2026-10-12T05:03:21.123Z",
  "collected_at": "2026-10-14T08:48:47.302681400Z",
  "offset": -1,
  "raw": "2026-10-12 14:03:21.123 [ERROR] NullPointerException at OrderService.create",
  "category": null,
  "level": "ERROR",
  "message": "NullPointerException at OrderService.create"
}
```

세 군데를 본다. `event_time`은 원문의 14:03(한국 시각)이 05:03Z(UTC)로 바뀌었다. `offset`이 -1인 것은 파일에서 읽은 줄이 아니기 때문이다. `device_id`는 source의 파일 이름 부분에서 왔다.

앱 콘솔에는 두 줄이 나온다. 위는 프로듀서의 발행 성공 콜백(DEBUG), 아래는 컨슈머다.

```
... LogEventProducer  : 발행 성공 key=dev-0001|manual://dev-0001.log|-1 -> topic=app-logs partition=2 offset=0
... LogEventConsumer  : [consume #1] p2@0 key=dev-0001 | event_time=2026-10-12T05:03:21.123Z level=ERROR file_offset=-1 | NullPointerException at OrderService.create
```

`p2@0`은 파티션 2의 오프셋 0이라는 뜻이다. `dev-0001`은 해시 결과로 언제나 파티션 2에 간다. Kafka UI → Topics → app-logs → Messages에서 같은 메시지의 값(JSON)을 본다.

**안 될 때.** 응답이 500이고 콘솔에 `InvalidPathException: Illegal char <:>`가 있으면 2026-10-15에 고치기 전 코드다. `LogNormalizer.deviceIdFrom`이 아직 `Paths.get`으로 파일 이름을 자르고 있는지 본다. Windows는 `manual://`의 `:`를 경로 문자로 받지 않는다.

**생각해 볼 것.** 응답 코드는 202(Accepted)다. 200과 무엇이 다른가? 이 응답을 받은 시점에 메시지가 브로커에 기록됐다고 말할 수 있는가? (답은 C8에서 직접 확인한다)

## B3. 1,000건 발행

**왜 하는가.** 부하 생성기 `LogGenerator`가 장비 50대 몫의 무작위 로그 1,000건을 Fluent Bit을 거치지 않고 Kafka에 바로 넣는다. 걸린 시간 `elapsedMs`는 1,000건이 **모두 브로커 ack를 받을 때까지**의 시간이다. C절에서 이 숫자를 기준으로 설정을 비교한다.

**할 것.**

```powershell
Invoke-RestMethod -Method Post "http://localhost:8080/api/logs/generate?count=1000&devices=50"
```

**보여야 하는 것.** `requested 1000`, `devices 50`, `elapsedMs`가 담긴 응답. 2026-10-14에 이 PC에서 151ms가 나왔다. 앱 콘솔에 발행 성공 1,000줄과 consume 1,000줄이 쏟아진다.

이어서 Kafka UI → Topics → app-logs → Messages 탭 위쪽 검색 칸에 `dev-0007`을 넣고 찾는다. 나온 메시지들의 Partition 열이 모두 같은 숫자인지 본다. 다른 장비 ID 하나로 한 번 더 해 본다.

**생각해 볼 것.** `elapsedMs`를 워크북 B3 빈칸에 적는다. 두세 번 더 보내 보면 첫 번째가 가장 느린 경우가 많다. 왜 그럴까? (힌트: 처음 한 번만 하는 일. C절의 측정 방법에서 다룬다)

## B4. 앱을 껐다 켜도 다시 읽지 않는다

**왜 하는가.** 컨슈머 그룹은 파티션마다 "어디까지 처리했는가"(커밋 오프셋)를 Kafka에 저장한다. 앱이 재시작해도 그 다음부터 읽는다. 이것이 장애 후 이어서 처리하는 장치다.

**할 것.**

1. 앱을 끈다. Kafka UI → Consumers → `log-printer`를 연다. 파티션별 표에서 커밋된 오프셋(Current offset 또는 Committed offset)과 끝 오프셋(End offset), Lag을 본다.
2. 같은 내용을 CLI로도 본다.

```powershell
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group log-printer
```

3. 앱을 다시 켠다. `partitions assigned`가 나온 뒤 앱 콘솔에 consume 줄이 새로 찍히는지 본다. `Invoke-RestMethod http://localhost:8080/api/logs/stats`도 친다.

**보여야 하는 것.** 1·2에서 파티션 0, 1, 2 모두 CURRENT-OFFSET과 LOG-END-OFFSET이 같고 LAG이 0이다. 앱이 꺼져 있으니 CLI 출력 첫 줄에 `Consumer group 'log-printer' has no active members.`가 붙는다. 3에서 consume 줄은 새로 나오지 않고, stats는 `consumed 0`이다. 이 카운터는 앱 메모리에 있어 재시작하면 0부터 센다. 이전 1,001건을 다시 읽지 않았다는 뜻이다.

**생각해 볼 것.** `application.properties`에 `auto-offset-reset=earliest`(처음부터 읽기)라고 적혀 있는데 왜 처음부터 안 읽는가? 이 설정은 언제 쓰이는가?

## B5. 새 그룹은 처음부터 읽는다

**왜 하는가.** B4의 답을 실험으로 확인한다. 커밋 오프셋은 그룹마다 따로 저장된다. 처음 보는 그룹에는 커밋이 없으니 `auto-offset-reset`이 쓰인다.

**할 것.**

1. 앱을 끈다.
2. `src/main/resources/application.properties`에서 아래 줄을 찾아 그룹 이름 끝에 `-2`를 붙이고 저장한다.

```properties
app.kafka.consumer-groups.printer=log-printer-2
```

3. 앱을 켠다. 콘솔이 잠잠해지면 stats를 친다. 토픽에 쌓인 메시지 수도 센다.

```powershell
Invoke-RestMethod http://localhost:8080/api/logs/stats
docker exec kafka /opt/kafka/bin/kafka-get-offsets.sh --bootstrap-server localhost:9092 --topic app-logs
```

4. 앱을 끄고 2번을 `log-printer`로 되돌린 뒤 다시 켠다.

**보여야 하는 것.** 3에서 콘솔에 consume 줄이 지금까지 보낸 메시지 수만큼 다시 쏟아진다. stats의 `consumed`는 `kafka-get-offsets` 출력(`app-logs:파티션:끝오프셋` 세 줄)의 끝 오프셋을 더한 값과 같다. Kafka UI → Consumers에 `log-printer`와 `log-printer-2` 두 그룹이 보인다. 4에서 원래 그룹으로 돌아가면 아무것도 다시 읽지 않는다.

**생각해 볼 것.** 같은 토픽을 그룹 둘이 각자 전부 읽었다. 이 성질을 실제 프로젝트에서 어디에 쓸 수 있는가? (저장용 적재기와 통계·이상 탐지용 컨슈머를 따로 두는 경우를 떠올린다. Step 3에서 실제로 해 본다)
