# 01. 환경과 프로젝트 구조

## 1. 설치할 것

**Docker Desktop**은 Kafka, Kafka UI, Fluent Bit(나중에 ClickHouse, Grafana)을 컨테이너로 띄우는 데 쓴다. 설치 후 `docker compose version`이 출력되면 된다. Windows에서는 WSL2 백엔드를 권장한다.

**JDK 17 이상 하나**는 Gradle을 실행하기 위해 필요하다. 프로젝트가 요구하는 Java 25는 따로 설치하지 않아도 된다. `settings.gradle`의 foojay 플러그인이 `build.gradle`의 `languageVersion = 25`를 보고 JDK 25를 `~/.gradle/jdks/`에 자동으로 내려받아 컴파일과 실행에 쓴다. 즉 "Gradle을 띄울 JDK"와 "프로젝트를 컴파일할 JDK"가 다르며, 전자만 손으로 설치한다. IntelliJ에서는 File → Project Structure → SDK가 17 이상이면 되고, Gradle 설정(Settings → Build Tools → Gradle)에서 "Gradle JVM"도 17 이상으로 잡는다.

**Python 3.8 이상**은 기업 제공 로그 생성기(`ohtsim.pyz`)를 돌리는 데만 필요하다. 05장 전까지는 없어도 된다.

**Git**은 당연히 필요하다.

## 2. 폴더 구조와 각 파일이 하는 일

하나의 Spring Boot 앱이 수집 서버(ingest)와 컨슈머(consumer)를 동시에 맡고 있다. 실제 프로젝트에서는 둘을 별도 서비스로 나누는 것이 보통이지만, 학습 단계에서는 한 프로세스에서 발행과 소비를 동시에 보는 것이 이해에 유리하다. Step 3에서 앱을 두 개 띄워 분리의 효과를 본다.

## 3. build.gradle 읽기

```groovy
plugins {
    id 'java'
    id 'org.springframework.boot' version '4.1.1'        // bootRun, bootJar 태스크와 의존성 버전 관리
    id 'io.spring.dependency-management' version '1.1.7'
}
java { toolchain { languageVersion = JavaLanguageVersion.of(25) } }   // 이 JDK 로 컴파일·실행
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-webmvc'   // REST 컨트롤러
    implementation 'org.springframework.boot:spring-boot-starter-validation'
    implementation 'org.springframework.boot:spring-boot-starter-kafka'    // spring-kafka + kafka-clients + 자동 설정
    implementation 'org.springframework.boot:spring-boot-starter-actuator' // /actuator/health
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
    testImplementation 'org.springframework.kafka:spring-kafka-test'       // @EmbeddedKafka
}
```

`spring-boot-starter-kafka` 하나가 세 가지를 가져온다. Apache 공식 Java 클라이언트(`kafka-clients`), 그 위에 Spring 식 추상화를 얹은 `spring-kafka`, 그리고 `application.properties`의 `spring.kafka.*`를 읽어 빈을 만들어주는 Spring Boot 자동 설정이다. 우리가 `KafkaTemplate`이나 리스너 컨테이너를 직접 `@Bean`으로 만들지 않는 이유가 이것이다.

Spring Boot 4부터 웹 스타터 이름이 `spring-boot-starter-web`에서 `spring-boot-starter-webmvc`로 바뀌었다(옛 이름도 아직 동작한다). 인터넷 자료 대부분은 3.x 기준이라 이름이 다를 수 있다.

## 4. docker-compose.yml 읽기

컨테이너 세 개를 띄운다. 각 설정의 의미를 줄 단위로 보자.

### kafka

```yaml
image: apache/kafka:4.2.2
ports: ["9092:9092"]
environment:
  KAFKA_NODE_ID: 1
  KAFKA_PROCESS_ROLES: "broker,controller"
  KAFKA_CONTROLLER_QUORUM_VOTERS: "1@kafka:29093"
```

Kafka 4.x는 ZooKeeper 없이 **KRaft** 모드로만 동작한다. 브로커 중 일부가 "컨트롤러"를 겸해 클러스터 메타데이터(토픽 목록, 파티션 리더 등)를 Raft 합의로 관리한다. `PROCESS_ROLES=broker,controller`는 이 노드 하나가 둘 다 한다는 뜻이고, `QUORUM_VOTERS`는 컨트롤러 투표자 목록(노드 1, 주소 kafka:29093)이다. 단일 노드라 혼자 투표한다.

```yaml
  KAFKA_LISTENERS: "PLAINTEXT://:19092,PLAINTEXT_HOST://:9092,CONTROLLER://:29093"
  KAFKA_ADVERTISED_LISTENERS: "PLAINTEXT://kafka:19092,PLAINTEXT_HOST://localhost:9092"
```

Kafka 입문자가 가장 많이 막히는 부분이다. Kafka 클라이언트는 처음에 `bootstrap-servers`에 적힌 주소로 접속한 뒤, 브로커가 **"나에게 오려면 이 주소로 와"라고 알려주는(advertised) 주소**로 다시 접속한다. 그런데 컨테이너 안에서 브로커에 가려면 `kafka:19092`가 맞고, 호스트(내 PC)에서 가려면 `localhost:9092`가 맞다. 그래서 리스너를 두 개 두고, 어느 포트로 들어왔느냐에 따라 다른 주소를 광고한다. Kafka UI는 컨테이너 네트워크에 있으므로 `kafka:19092`로, Spring 앱은 호스트에 있으므로 `localhost:9092`로 붙는다. 이걸 잘못 잡으면 "bootstrap은 성공했는데 메시지 전송이 타임아웃" 나는 전형적인 증상이 생긴다.

```yaml
  KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
  KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
  KAFKA_AUTO_CREATE_TOPICS_ENABLE: "false"
```

Kafka는 컨슈머 오프셋 등을 자기 내부 토픽에 저장하며 그 복제 계수 기본값이 3이다. 브로커가 1개뿐이면 만들 수 없어 컨슈머 그룹이 동작하지 않으므로 1로 내린다. 토픽 자동 생성은 끈다. 오타 난 토픽 이름으로 메시지를 보내면 조용히 새 토픽이 생기는 사고를 막기 위해서다. 토픽은 코드(`KafkaTopicConfig`)나 CLI로 명시적으로 만든다.

### kafka-ui

`ghcr.io/kafbat/kafka-ui` 이미지에 `KAFKA_CLUSTERS_0_BOOTSTRAPSERVERS: kafka:19092`를 주어 브로커에 붙인다. 호스트 포트 8085로 연다(8080은 Spring 앱이 쓴다). `depends_on: condition: service_healthy`는 kafka의 healthcheck가 통과한 뒤 뜨라는 뜻이다.

### fluent-bit

```yaml
volumes:
  - ./fluent-bit/fluent-bit.conf:/fluent-bit/etc/fluent-bit.conf:ro
  - ./devices:/var/log/devices:ro
extra_hosts: ["host.docker.internal:host-gateway"]
```

`docker/devices` 폴더를 컨테이너 안 `/var/log/devices`에 읽기 전용으로 마운트한다. 이 폴더가 "차량의 로컬 디스크"다. Fluent Bit은 여기서 읽어 `host.docker.internal:8080`(컨테이너에서 호스트 PC를 가리키는 이름)으로 보낸다. 즉 IntelliJ로 띄운 Spring 앱이 받는다.

## 5. application.properties 읽기

설정은 세 묶음이다. `spring.kafka.*`는 Spring Boot가 읽어 Kafka 클라이언트를 만들고, `app.*`는 우리가 정의해 `@Value`로 주입받으며, `logging.*`는 로그 레벨이다. 각 항목 옆 주석에 의미를 적어두었으므로 파일을 직접 열어 읽는 것이 가장 좋다. 03장과 04장에서 producer, consumer 항목을 하나씩 실험한다.

한 가지 주의할 문법이 있다. `spring.kafka.consumer.properties[spring.json.trusted.packages]=...`처럼 대괄호를 쓰는 이유는 키 이름 자체에 점이 들어 있기 때문이다. 대괄호 없이 쓰면 Spring이 `spring.json.trusted.packages`를 네 단계 중첩 키로 해석해 버린다.

## 6. 실행 방법

### 터미널

```bash
docker compose -f docker/docker-compose.yml up -d     # 인프라
docker compose -f docker/docker-compose.yml ps        # kafka 가 healthy 인지
./gradlew bootRun                                      # Windows: gradlew.bat bootRun
```

### IntelliJ

프로젝트를 열면 Gradle이 자동 import된다. `PracticeKafkaApplication`의 main을 실행하거나 Gradle 탭에서 `bootRun`을 실행한다. 실행 구성의 **Working directory가 프로젝트 루트**여야 한다. `app.simulator.dir=docker/devices/sim` 같은 상대 경로가 거기 기준이기 때문이다. IntelliJ 기본값은 프로젝트 루트라 보통 문제없다.

`http/*.http` 파일을 열면 각 요청 왼쪽에 실행 버튼이 생긴다. curl 대신 이것을 쓰면 편하다.

### 기동 로그에서 확인할 것

정상 기동 시 세 가지 로그가 순서대로 나온다. (1) `KafkaAdmin`이 토픽을 만들거나 이미 있음을 확인하는 로그, (2) 컨슈머가 그룹에 참여하는 `(Re-)joining group`, (3) `partitions assigned: [app-logs-0, app-logs-1, app-logs-2]`. (3)이 나오면 컨슈머가 세 파티션을 모두 맡아 읽을 준비가 된 것이다.

## 7. 자주 나는 오류

| 증상 | 원인과 해결 |
|---|---|
| `Connection to node -1 (localhost/127.0.0.1:9092) could not be established` | Kafka 컨테이너가 안 떠 있다. `docker compose ps`로 확인하고 `up -d` |
| bootstrap은 되는데 전송이 `TimeoutException` | `ADVERTISED_LISTENERS`가 잘못됐거나 다른 호스트에서 접속 중. 4절 리스너 설명 참고 |
| `UnknownTopicOrPartitionException` | 토픽이 없다. 자동 생성을 꺼뒀으므로 `KafkaTopicConfig`의 `NewTopic` 빈이 있는지, 토픽 이름 오타가 없는지 확인 |
| `InvalidReplicationFactorException: Replication factor: 3 larger than available brokers: 1` | 단일 브로커인데 `app.kafka.topics.app-logs.replicas=3`. 1로 |
| 컨슈머 로그에 `The class 'X' is not in the trusted packages` | `spring.json.trusted.packages`에 LogEvent 패키지가 없다 |
| 메시지가 안 들어오는데 오류도 없다 | 다른 groupId가 이미 커밋한 오프셋 이후만 읽는 중. Kafka UI → Consumers에서 lag 확인. 처음부터 다시 읽으려면 groupId 를 바꾸거나 UI 에서 오프셋 리셋 |
| Fluent Bit 로그에 `connection refused` 반복 | Spring 앱이 안 떠 있다. 앱을 띄우면 밀린 것을 보낸다(정상) |
| Fluent Bit이 파일을 안 읽는다 | 경로 패턴(`fluent-bit.conf`의 `Path`)과 실제 폴더 구조가 맞는지, `docker exec fluent-bit ls /var/log/devices` 로 마운트 확인 |
| Gradle 이 JDK 25 를 못 받는다 | 회사 프록시 환경이면 `gradle.properties`에 `systemProp.https.proxyHost` 설정, 또는 Temurin 25 를 직접 설치 |
| 컨테이너를 지웠는데 옛 메시지가 남아 있다 | `down -v` 로 볼륨까지 지워야 Kafka 데이터가 사라진다 |

2. 토픽 자동 생성을 끈 상태에서 `KafkaTopicConfig`를 지우고 앱을 띄우면 어떤 오류가 어디서 나는가? (직접 해 보라)
