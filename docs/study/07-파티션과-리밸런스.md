# 07. 파티션과 리밸런스: 나눠 읽는 단위와 그것을 다시 나누는 순간

04장에서 컨슈머 그룹과 리밸런스를 말로 설명했다. 이 장은 그것을 직접 돌려 본다. 파티션을 3개에서 6개로 늘리고, 리스너 하나가 컨슈머 스레드 3개를 띄우게 하고, 앱을 하나 더 띄웠다가 끄며 파티션이 어떻게 다시 나뉘는지 시각까지 잰다. 두 번째 컨슈머 그룹(`log-stats`)을 붙여 그룹이 다르면 같은 메시지를 따로 받는다는 것도 확인한다. 실행 절차는 `../practice/06-파티션과-컨슈머그룹.md`, 단계 기록은 `../result/step3-파티션-컨슈머그룹.md`에 있다.

## 1. 왜 파티션 수가 중요한가

파티션은 Kafka가 일을 나누는 가장 작은 단위다. 한 그룹 안에서 파티션 하나는 컨슈머 하나만 읽는다. 그래서 파티션 수가 곧 "한 그룹이 동시에 일할 수 있는 컨슈머 수의 상한"이다. 파티션이 3개면 컨슈머를 10개 띄워도 3개만 일하고 7개는 논다.

파티션은 순서의 단위이기도 하다. 같은 키(`device_id`)는 같은 파티션에 들어가고, 파티션 안에서는 들어간 순서대로 읽힌다(02장). 장비 하나의 로그가 순서대로 처리되는 것은 이 성질 덕분이다.

두 성질 때문에 파티션 수는 처음에 넉넉히 정한다. 늘릴 수는 있지만 줄일 수는 없고, 늘리면 순서 보장이 잠깐 흔들린다(3절).

## 2. 이번에 바꾼 것

```properties
# application.properties
app.kafka.topics.app-logs.partitions=6          # 3 → 6
spring.kafka.listener.concurrency=3             # 리스너 하나가 컨슈머 스레드 3개
app.kafka.consumer-groups.stats=log-stats       # 두 번째 그룹
```

`spring.kafka.listener.concurrency`는 Spring Boot가 만드는 기본 리스너 팩토리에 걸린다. 그래서 `log-printer`와 `log-stats` 리스너가 각각 스레드 3개, 즉 `KafkaConsumer` 3개를 띄운다. 파티션 6개를 스레드 3개가 나누면 하나에 2개씩이다.

두 번째 그룹은 `consumer/LogStatsConsumer.java`다. 메시지마다 레벨만 세고 로그를 찍지 않는다.

```java
@KafkaListener(topics = "${app.kafka.topics.app-logs.name}", groupId = "${app.kafka.consumer-groups.stats}")
public void onLogEvent(LogEvent event) {
    String level = event.level() == null ? "NONE" : event.level();
    byLevel.computeIfAbsent(level, k -> new LongAdder()).increment();
}
```

할당을 눈으로 보려고 `GET /api/logs/assignments`를 더했다. 리스너마다 컨슈머 스레드(client.id)가 지금 어떤 파티션을 맡고 있는지 돌려준다. 앱을 정상 종료하는 `POST /actuator/shutdown`도 열었다. Windows에는 리눅스의 SIGTERM에 해당하는 것이 없어 `Stop-Process`는 곧 강제 종료이므로, 정상 종료와 강제 종료를 나눠 보려면 이 엔드포인트가 필요하다. 인증 없이 앱을 끌 수 있으므로 운영에서는 열지 않는다.

## 3. 파티션을 늘리면 생기는 일

`app-logs`는 이미 파티션 3개로 있었다. 앱이 뜰 때 `KafkaAdmin`이 설정(6)과 실제(3)를 비교해 늘린다. 콘솔에 이렇게 찍힌다(2026-10-19 실측).

```
KafkaAdmin : Topic 'app-logs' exists but has a different partition count: 3 not 6, increasing if the broker supports it
```

늘린 직후의 그룹 상태를 보면 새 파티션 3~5는 늘린 뒤에 들어온 메시지만 담고 있어 오프셋이 작다(수백). 옛 파티션 0~2는 그동안 쌓인 수만 건이다.

늘리는 데에는 대가가 있다. 키가 어느 파티션으로 갈지는 `murmur2(key) % 파티션 수`로 정해진다. 파티션 수가 3에서 6이 되면 같은 장비가 다른 파티션으로 갈 수 있다. 그러면 늘리기 전에 0번 파티션에 쌓인 그 장비의 옛 로그와 늘린 뒤 4번 파티션에 들어간 새 로그가 서로 다른 컨슈머에게 동시에 처리될 수 있다. 그 짧은 구간 동안은 "장비 하나의 로그는 순서대로"가 깨진다. 옛 메시지를 다 소비한 뒤에는 다시 지켜진다. 운영에서는 파티션을 늘리기 전에 lag을 0으로 만들어 두거나, 처음부터 넉넉히 정한다.

## 4. 그룹이 다르면 같은 메시지를 따로 받는다

두 그룹은 오프셋을 따로 기억하므로 같은 메시지를 각자 전부 받는다. 1,000건을 보냈더니 `log-printer`도 1,000건, `log-stats`도 1,000건을 받았다(2026-10-19).

처음 뜬 `log-stats`는 그 전에 토픽에 쌓여 있던 메시지 121,403건까지 읽었다. 새 그룹은 커밋된 오프셋이 없고, `auto-offset-reset=earliest`라서 처음부터 읽기 때문이다(04장 3절). 같은 이유로 Step 4의 적재 그룹(`clickhouse-sink`)도 처음 뜨면 토픽에 남아 있는 과거분을 전부 적재한다. 새 소비자를 붙이면 과거 데이터까지 다시 처리할 수 있다는 것은 Kafka를 쓰는 큰 이유다. 반대로 원하지 않으면 `latest`로 두어야 한다.

## 5. 리밸런스를 시각으로 보기

리밸런스는 그룹의 멤버가 바뀔 때 파티션을 다시 나누는 일이다. 이번에는 네 상황을 콘솔의 `partitions revoked`와 `partitions assigned` 시각으로 쟀다. 모두 2026-10-19 이 PC의 실측이고, 기본 프로토콜(classic)이다.

| 상황 | 무엇이 보였나 | 걸린 시간 |
|---|---|---|
| 앱 B 합류 (A 혼자 6개를 읽던 중) | A의 스레드 셋이 파티션을 **전부** 내려놓은 뒤, A가 3개, B가 3개를 받았다 | A가 내려놓고(44.177) B가 받기까지(44.217) 약 40ms |
| 앱 B 정상 종료 (`/actuator/shutdown`) | B가 그룹을 떠난다고 알렸고, A가 6개를 다시 받았다 | B가 내려놓고(25.599) A가 받기까지(27.040) 약 1.4초 |
| 앱 B 강제 종료 (`Stop-Process -Force`) | B가 떠난다는 말 없이 사라졌다. 브로커는 B의 하트비트가 끊긴 것을 세션 타임아웃까지 기다린 뒤에야 A에게 넘겼다 | 종료(20:36.277)부터 A가 받기까지(21:20.414) **약 44초** |
| B를 스레드 6개로 띄움 (그룹 컨슈머 9개, 파티션 6개) | B의 스레드 셋은 빈 목록 `[]`을 받았다 | 3개는 아무 일도 하지 않는다 |

합류할 때 A가 파티션을 "전부" 내려놓은 것이 기본 프로토콜의 성격이다. 이것을 eager 리밸런스라 한다. 그룹 전체가 잠깐 멈추고 처음부터 다시 나눈다. 이번에는 40ms였지만, 컨슈머가 묶음 하나를 처리하는 데 오래 걸리면(Step 4의 ClickHouse INSERT처럼) 그만큼 모두가 기다린다.

강제 종료의 44초가 이 장에서 가장 중요한 숫자다. 기본 `session.timeout.ms`가 45초라서, 컨슈머가 죽은 뒤 그 파티션은 최대 45초 동안 아무도 읽지 않는다. 그동안 그 파티션의 로그는 Kafka에 쌓이기만 한다(유실은 아니다). 운영에서 컨슈머를 내릴 때는 반드시 정상 종료하고, 장애를 빨리 알아채야 하면 이 값을 낮춘다. 너무 낮추면 GC나 긴 처리 중에 살아 있는 컨슈머를 죽은 것으로 오해해 리밸런스가 잦아진다.

정상 종료에서 1.4초가 걸린 것은 남은 쪽(A)이 다음 하트비트(기본 3초 간격)에서야 리밸런스가 시작됐음을 알기 때문이다.

### 심화: 새 그룹 프로토콜 (지금은 넘어가도 된다)

Kafka 4에는 브로커가 할당을 정하는 새 프로토콜(KIP-848, `group.protocol=consumer`)이 있다. 클라이언트 기본값은 아직 `classic`이다. 두 앱을 `--spring.kafka.consumer.properties[group.protocol]=consumer`로 띄워 같은 합류를 봤다. B가 들어오자 A는 6개 중 **3개만**(1, 4, 5번) 내놓았고, 나머지 0, 2, 3번은 한 번도 멈추지 않았다. 대신 옮겨진 파티션 하나하나는 5~7초 쉬었다(1번: A가 45.201에 내놓고 B가 50.298에 받음). 새 프로토콜은 하트비트(5초 간격)마다 조금씩 옮기기 때문이다. 기본 프로토콜은 "모두가 짧게 멈춤", 새 프로토콜은 "일부만 몇 초 멈춤"이다. 처리 한 번이 길거나 파티션이 많을수록 새 쪽이 유리하다. Step 6 이후 운영 설정을 정할 때 다시 본다.

## 6. 파티션 수를 어떻게 정하는가

목표 처리량을 컨슈머 하나의 처리량으로 나눈 값에 여유를 곱한다. 이 프로젝트에서 가장 느린 소비자는 ClickHouse 적재 컨슈머다. `kafka-load-test` 브랜치의 측정(`docs/result/benchmark-transport.md` 7.3절, 이 저장소에서 다시 재지 않았다)에서 적재 컨슈머 하나가 초당 약 14.7만 행, 장비 약 2,400대 분량을 넣었고, 3개까지는 거의 정비례로, 그 뒤로는 ClickHouse가 바빠지며 덜 늘었다. 그러니 1,000대는 컨슈머 1개로 충분하고, 파티션 6개면 장비가 몇 배로 늘어도 컨슈머를 6개까지 늘릴 여지가 있다.

파티션이 많으면 공짜는 아니다. 프로듀서는 파티션마다 배치를 따로 만들므로, 같은 양이면 배치가 작게 쪼개진다. 브로커가 관리할 파일도 늘어난다. 로그 수집처럼 메시지가 작고 많은 경우 수십 개 수준이면 문제가 없고, 수천 개는 피한다. 이 저장소는 6개, 브랜치의 부하 테스트는 12개를 썼다.

## 확인 질문

1. 파티션 6개, `concurrency=3`인 앱을 3개 띄우면 그룹의 컨슈머는 몇 개이고, 몇 개가 노는가? 직접 띄워 `/api/logs/assignments`로 확인하라.
2. 파티션을 3개에서 6개로 늘린 직후, 같은 장비의 로그 순서가 깨질 수 있는 이유를 키와 파티션 계산으로 설명하라. 어떻게 하면 피할 수 있는가?
3. 컨슈머를 강제 종료하면 왜 약 45초 동안 그 파티션이 멈추는가? 정상 종료와 무엇이 다른가?
4. 새 그룹을 붙였더니 과거 메시지 12만 건을 처음부터 읽었다. 어떤 설정 때문이며, 적재 컨슈머(Step 4)에게 이것은 장점인가 위험인가?
5. 기본 프로토콜에서 합류 리밸런스는 40ms였다. 컨슈머가 묶음 하나를 처리하는 데 2초가 걸린다면 이 시간은 어떻게 달라질까? (힌트: 내려놓기 전에 하던 일을 마쳐야 한다)
