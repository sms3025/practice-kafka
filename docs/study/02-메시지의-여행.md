# 02. 메시지의 여행: 로그 한 줄이 파일에서 컨슈머까지 가는 길

이 장은 로그 한 줄을 붙잡고 파이프라인을 처음부터 끝까지 따라간다. 각 구간에서 **어떤 코드가, 어떤 설정을 보고, 무엇을 하는지**를 읽는다. 끝까지 읽으면 "코드가 왜 이렇게 나뉘어 있는지"와 "어디를 고치면 무엇이 바뀌는지"가 보인다.

따라갈 한 줄은 이것이다. (형식만 흉내 낸 가짜 내용이다)

```
[2026-10-12 14:03:21.1234],[SEQ_INFO],[INFORMATION],[316710],[msg => Driving Start]
```

이 줄은 장비 `OHT-0007`의 `OHTHandlerLogger/SEQ_INFO/20261012_14_SEQ_INFO.txt` 파일 1842번째 바이트에 적혀 있다고 하자.

## 구간 1. 파일 → Fluent Bit (에이전트)

`docker/fluent-bit/fluent-bit.conf`의 `[INPUT]` 블록이 이 구간이다.

```
[INPUT]
    Name              tail
    Path              /var/log/devices/*/OHTHandlerLogger/*/*.txt, ...
    Path_Key          source
    Offset_Key        offset
    DB                /fluent-bit/db/tail.db
    Read_from_Head    On
```

Fluent Bit은 `Path` 패턴에 맞는 파일을 5초(`Refresh_Interval`)마다 찾고, 각 파일을 `tail -f`처럼 끝에서부터 지켜본다. 새 줄이 생기면 레코드 하나를 만든다. 레코드는 키-값 맵이며, `tail` 입력은 기본적으로 `log` 키에 그 줄을 넣는다. 우리는 두 키를 더 넣으라고 했다. `Path_Key source`는 파일 경로를 `source`에, `Offset_Key offset`은 그 줄이 시작하는 파일 내 바이트 위치를 `offset`에 넣는다. 그리고 레코드에는 Fluent Bit이 읽은 시각이 붙는다. 이 시점의 레코드는 대략 이렇다.

```
time=2026-10-12T05:03:22.004Z
log="[2026-10-12 14:03:21.1234],[SEQ_INFO],[INFORMATION],[316710],[msg => Driving Start]\r"
source="/var/log/devices/OHT-0007/OHTHandlerLogger/SEQ_INFO/20261012_14_SEQ_INFO.txt"
offset=1842
```

`\r`이 붙어 있는 것에 주목하자. OHT 로그 파일은 CRLF 줄바꿈이고 Fluent Bit은 `\n`만 떼기 때문이다. 이런 사소한 것이 파서를 깨뜨린다.

`DB`는 "이 파일을 어디까지 읽었는지"를 SQLite에 기록한다. 컨테이너가 재시작돼도 이어서 읽고, 같은 줄을 두 번 읽지 않는다. `Read_from_Head On`은 처음 보는 파일을 끝이 아니라 처음부터 읽으라는 뜻이다. 생성기가 미리 만들어둔 파일도 전부 수집하기 위해서다.

## 구간 2. Fluent Bit → HTTP 요청

`[OUTPUT]` 블록이다.

```
[OUTPUT]
    Name              http
    Match             device.*
    Host              host.docker.internal
    Port              8080
    URI               /ingest/fluentbit
    Format            json
    Json_date_key     collected_at
    Json_date_format  iso8601
    Retry_Limit       False
```

`Flush 1`(SERVICE 블록)마다 그동안 쌓인 레코드를 묶어 `POST http://host.docker.internal:8080/ingest/fluentbit`로 보낸다. 본문은 JSON 배열이고, 레코드의 시각은 `Json_date_key`가 정한 이름 `collected_at`으로 들어간다. 즉 명세서의 `collected_at`은 Fluent Bit이 채운다. 요청 본문은 이렇다.

```json
[
  {"collected_at":"2026-10-12T05:03:22.004Z",
   "log":"[2026-10-12 14:03:21.1234],[SEQ_INFO],[INFORMATION],[316710],[msg => Driving Start]\r",
   "source":"/var/log/devices/OHT-0007/OHTHandlerLogger/SEQ_INFO/20261012_14_SEQ_INFO.txt",
   "offset":1842},
  ... (같은 1초 동안 쌓인 다른 줄들)
]
```

응답이 2xx가 아니면 Fluent Bit은 이 묶음을 버리지 않고 재시도한다. `Retry_Limit False`는 횟수 제한이 없다는 뜻이다. 수집 서버가 내려가 있으면 디스크 버퍼(`storage.type filesystem`)에 쌓아두고 계속 두드린다. 그래서 수집 서버 입장에서 **응답 코드가 곧 "받았다/못 받았다"의 계약**이 된다.

## 구간 3. HTTP 요청 → Spring 수집 서버

`ingest/FluentBitIngestController.java`가 받는다.

```java
@PostMapping("/ingest/fluentbit")
public ResponseEntity<Void> ingest(@RequestBody List<FluentBitRecord> records) {
```

Spring MVC가 JSON 배열을 `List<FluentBitRecord>`로 바꿔준다. `FluentBitRecord`는 필드 네 개짜리 record이고, `@JsonProperty("collected_at")`로 snake_case 키를 camelCase 필드에 연결한다. Fluent Bit이 모르는 키를 더 보내도 Jackson 3는 기본으로 무시한다.

```java
    CompletableFuture<?>[] futures = new CompletableFuture<?>[records.size()];
    for (int i = 0; i < records.size(); i++) {
        FluentBitRecord r = records.get(i);
        LogEvent event = normalizer.normalize(r.source(), r.offset(), r.log(), r.collectedAt());
        futures[i] = producer.send(event);
    }
    CompletableFuture.allOf(futures).join();   // 전부 브로커 ack 를 받을 때까지 대기
    return ResponseEntity.ok().build();
```

레코드마다 정규화(구간 4)하고 발행(구간 5)한 뒤, **묶음 전체의 ack를 기다렸다가** 200을 돌려준다. 발행이 하나라도 실패하면 `join()`이 예외를 던지고 `catch`에서 500을 돌려준다. 그러면 Fluent Bit이 같은 묶음을 다시 보낸다. 이 설계가 "수집 서버나 Kafka가 죽어도 로그가 유실되지 않는" 이유이고, 동시에 "같은 줄이 두 번 들어올 수 있는" 이유다. 200을 보내기 직전에 서버가 죽으면 Kafka에는 이미 들어갔는데 Fluent Bit은 실패로 알고 재전송하기 때문이다. 이것을 **at-least-once(최소 한 번)** 전달이라 한다.

## 구간 4. 정규화: 원문 → LogEvent

`log/LogNormalizer.java`의 `normalize()`다. 명세서가 "event_time은 필수 정규화"라고 못 박은 부분이 여기다.

```java
public LogEvent normalize(String source, long offset, String rawLine, Instant collectedAt) {
    String raw = stripLineEnding(rawLine);        // "\r" 제거
    String deviceId = deviceIdFrom(source);       // 경로에서 "OHT-0007"
    Matcher m = HANDLER.matcher(raw);             // (A) OHTHandlerLogger 형식 시도
    if (m.matches()) {
        return new LogEvent(deviceId, source, parseTime(m.group("time"), collectedAt), collectedAt, offset, raw,
                m.group("category"), unifyLevel(m.group("level")), m.group("message"));
    }
    m = UILOGGER.matcher(raw);                    // (B) UILogger 형식 시도
    ...
    return new LogEvent(deviceId, source, collectedAt, collectedAt, offset, raw, null, null, raw);  // 전부 실패
}
```

세 가지가 일어난다.

**device_id 추출.** 에이전트는 파일 경로만 안다. OHT 로그는 장비 ID가 파일명이 아니라 상위 폴더 이름(`OHT-0007`)에 있으므로 경로 전체에서 정규식 `([A-Z]{2,5}-[0-9]{3,5})`로 찾는다. 패턴은 `app.ingest.device-id-pattern`으로 바꿀 수 있다. 못 찾으면 파일명을 쓴다.

**형식 판별과 파싱.** 정규식 세 개를 위에서부터 시도한다. HANDLER는 `[시각],[카테고리],[레벨],[번호],[msg => 본문]`, UILOGGER는 `시각 [스레드] 레벨 로거 - 본문`, SIMPLE은 연습용 `시각 [레벨] 본문`이다. 명명 그룹(`(?<time>...)`)으로 각 조각을 꺼낸다. 레벨은 `INFORMATION`→`INFO`, `WARNING`→`WARN`으로 통일한다. 장비마다 표기가 다른 것을 한 기준으로 맞추는 것이 정규화의 뜻이다.

**시각 변환.** `2026-10-12 14:03:21.1234`는 타임존 표기가 없다. 장비는 한국 시각으로 찍는다고 가정하고(`app.ingest.device-zone=Asia/Seoul`), `LocalDateTime → ZonedDateTime(KST) → Instant(UTC)`로 바꾼다. 결과는 `2026-10-12T05:03:21.1234Z`다. 왜 UTC로 바꾸는가? 공장이 해외에도 있거나, 장비 시계가 서머타임을 따르거나, 분석가가 다른 시간대에 있을 때 "같은 순간"을 비교하려면 저장 기준이 하나여야 하기 때문이다. 표시할 때 현지 시각으로 바꾸는 것은 대시보드의 몫이다.

정규식이 전부 실패하면 시각을 `collected_at`으로 대신 넣고 본문은 raw 전체로 둔다. 버리지 않는다. raw가 그대로 남아 있으므로 나중에 정규식을 고쳐 재처리할 수 있다.

이 시점의 `LogEvent`는 이렇다.

```json
{"device_id":"OHT-0007",
 "source":"/var/log/devices/OHT-0007/OHTHandlerLogger/SEQ_INFO/20261012_14_SEQ_INFO.txt",
 "event_time":"2026-10-12T05:03:21.1234Z",
 "collected_at":"2026-10-12T05:03:22.004Z",
 "offset":1842,
 "raw":"[2026-10-12 14:03:21.1234],[SEQ_INFO],[INFORMATION],[316710],[msg => Driving Start]",
 "category":"SEQ_INFO","level":"INFO","message":"Driving Start"}
```

`LogNormalizer`는 Spring에 의존하지 않는 순수 Java라 `LogNormalizerTest`에서 docker 없이 테스트한다. 파서는 가장 자주 바뀌는 코드이므로 테스트가 먼저 깨지게 해 두는 것이 중요하다.

## 구간 5. 발행: LogEvent → Kafka

`producer/LogEventProducer.java`다.

```java
public CompletableFuture<SendResult<String, LogEvent>> send(LogEvent event) {
    return kafkaTemplate.send(topic, event.deviceId(), event)
            .whenComplete((result, ex) -> { ... 로깅 ... });
}
```

`kafkaTemplate.send(토픽, 키, 값)` 한 줄이지만 안에서 다섯 단계가 일어난다. 03장에서 자세히 보고 여기서는 흐름만 잡는다.

1. **직렬화.** `application.properties`의 `key-serializer`(StringSerializer)와 `value-serializer`(JacksonJsonSerializer)가 키 `"OHT-0007"`과 `LogEvent` 객체를 각각 `byte[]`로 바꾼다. 값은 위의 JSON이 된다. Kafka 브로커는 바이트만 다루며 내용을 전혀 해석하지 않는다.
2. **파티션 결정.** 토픽 `app-logs`는 파티션 3개다. 키가 있으므로 `murmur2("OHT-0007") % 3`으로 파티션 번호가 정해진다. 같은 키는 항상 같은 파티션이다. 그래서 `OHT-0007`의 모든 로그는 한 파티션에 발생 순서대로 쌓이고, 컨슈머도 그 순서로 읽는다. 키를 `deviceId`로 잡은 이유다.
3. **버퍼링.** 레코드는 메모리 버퍼(`RecordAccumulator`)의 해당 파티션 칸에 들어간다. **`send()`는 여기서 반환한다.** 아직 네트워크로 나가지 않았다.
4. **전송.** 별도 I/O 스레드가 `linger.ms`(5ms)가 지나거나 `batch.size`(16KB)가 차면 파티션별 배치를 브로커로 보낸다. 묶어 보내기 때문에 초당 수만 건도 요청 수는 수백 개에 그친다.
5. **ack.** 브로커가 디스크(정확히는 OS 페이지 캐시)에 쓰고 `acks=all` 조건을 만족하면 응답한다. 그제야 `CompletableFuture`가 완료되고, 구간 3의 `join()`이 풀린다.

브로커에서 이 메시지는 `app-logs` 토픽의 어느 파티션(예: 1번)의 끝에 붙고 **오프셋**(예: 4821)을 받는다. 이 오프셋은 파티션 안에서의 순번이며, 구간 1의 파일 오프셋 1842와는 전혀 다른 것이다. 둘 다 "offset"이라 불려 혼동하기 쉬우므로 컨슈머 로그에서는 파일 쪽을 `file_offset`으로 구분해 찍는다.

## 구간 6. 소비: Kafka → 컨슈머

`consumer/LogEventConsumer.java`다.

```java
@KafkaListener(topics = "${app.kafka.topics.app-logs.name}", groupId = "${app.kafka.consumer-groups.printer}")
public void onLogEvent(@Payload LogEvent event,
                       @Header(KafkaHeaders.RECEIVED_KEY) String key,
                       @Header(KafkaHeaders.RECEIVED_PARTITION) int partition,
                       @Header(KafkaHeaders.OFFSET) long offset) {
    log.info("[consume #{}] p{}@{} key={} | event_time={} level={} file_offset={} | {}", ...);
}
```

앱이 뜰 때 Spring은 이 메서드를 위한 **리스너 컨테이너**를 만들고 백그라운드 스레드를 하나 띄운다. 그 스레드는 영원히 `poll()` 루프를 돈다. 브로커는 메시지를 밀어주지(push) 않는다. 컨슈머가 "파티션 1의 오프셋 4821부터 줘"라고 당겨간다(pull). 그래서 컨슈머가 느려도 브로커는 영향받지 않고, 컨슈머는 자기 속도로 읽는다.

받은 바이트는 `value-deserializer`(JacksonJsonDeserializer)가 다시 `LogEvent`로 바꾼다. 어떤 클래스로 바꿀지는 `spring.json.value.default.type`이 알려준다. 프로듀서가 타입 헤더를 안 붙이도록 했기 때문이다(`add.type.headers=false`). 메서드 인자에 `@Header`를 붙이면 키, 파티션, 오프셋 같은 메타데이터도 받을 수 있다.

메서드가 정상 반환하면 컨테이너는 poll로 받은 묶음을 다 처리한 뒤 **오프셋을 커밋**한다. "파티션 1은 4822까지 읽었음"을 브로커의 내부 토픽 `__consumer_offsets`에 `groupId=log-printer` 이름으로 기록하는 것이다. 앱을 재시작하면 거기서부터 이어 읽는다. 메서드가 예외를 던지면 커밋하지 않고 재시도한다(기본 10회, 그 뒤 건너뜀. Step 5에서 DLT로 바꾼다).

`groupId`는 "누가 읽는가"의 이름이다. 같은 이름의 컨슈머가 여러 개면 파티션을 나눠 갖고(병렬 처리), 이름이 다르면 각자 전부 읽는다(브로드캐스트). Step 4에서 `clickhouse-sink`라는 두 번째 그룹을 추가하면 같은 메시지가 콘솔에도 찍히고 ClickHouse에도 들어간다. 04장에서 자세히 본다.

## 전체를 한 장으로

```
파일 (OHT-0007/.../SEQ_INFO.txt, 바이트 1842)
  │  Fluent Bit tail: log/source/offset/time 레코드 생성           ← fluent-bit.conf [INPUT]
  ▼
HTTP POST /ingest/fluentbit  [ {collected_at, log, source, offset}, ... ]   ← [OUTPUT], 1초마다 묶음
  │  FluentBitIngestController: 묶음 수신                           ← ingest/
  ▼
LogNormalizer: device_id 추출, 시각 UTC 변환, 레벨 통일 → LogEvent   ← log/
  │
  ▼
KafkaTemplate.send(app-logs, "OHT-0007", LogEvent)                 ← producer/, spring.kafka.producer.*
  │  직렬화(JSON) → 파티션 선택(해시) → 버퍼 → 배치 전송 → ack
  ▼
브로커: app-logs 파티션 1, 오프셋 4821 에 기록                         ← docker-compose.yml
  │
  ▼  (ack 를 받은 수집 서버가 Fluent Bit 에 200 응답. 여기까지가 "수집 완료")
  │
컨슈머 컨테이너 poll() → 역직렬화 → onLogEvent() → 오프셋 커밋         ← consumer/, spring.kafka.consumer.*
```

## 코드가 이렇게 나뉜 이유

패키지가 `ingest`, `log`, `producer`, `consumer`로 나뉜 것은 각각이 **독립적으로 바뀌는 이유**를 갖기 때문이다. 로그 형식이 바뀌면 `log/LogNormalizer`만, 에이전트가 Fluent Bit에서 다른 것으로 바뀌면 `ingest/`만, Kafka 설정이 바뀌면 `application.properties`만, 적재 대상이 바뀌면 `consumer/`만 손댄다. 실제 프로젝트에서 수집 서버와 적재기를 별도 서비스로 분리할 때도 이 경계를 따라 자르면 된다.
