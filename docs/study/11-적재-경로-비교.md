# 11. 적재 경로 비교: Kafka를 꼭 거쳐야 하는가

명세서의 기본 아키텍처는 "장비 → HTTP → 수집 서버 → ClickHouse"다. 이 저장소는 Step 2에서 수집 서버와 ClickHouse 사이에 Kafka를 넣었다. 저장소가 느려지거나 멈춰도 수집이 밀리지 않게 하려는 완충이라고 설명했지만(02장), 그 설명이 숫자로 맞는지는 아직 재지 않았다. 이 장은 같은 장비 로그를 네 경로로 동시에 ClickHouse에 넣고 비교한다. 따라 하는 절차는 `../practice/08-적재-경로-비교.md`, 결과 기록은 `../result/step4plus-적재경로-비교.md`와 `../result/benchmark-ingest-path.md`다.

## 1. 네 경로

| 경로 | INSERT를 만드는 곳 | INSERT 한 번의 크기를 정하는 것 | ClickHouse가 멈추면 로그가 기다리는 곳 | 지난 로그를 다시 넣으려면 |
|---|---|---|---|---|
| Kafka 경유 (Step 4) | 앱의 적재 컨슈머 | `poll()` 한 번의 묶음(`fetch.min.bytes` 1MB, `fetch.max.wait.ms` 0.5초, `max.poll.records` 2만) | Kafka (lag) | 컨슈머 그룹의 오프셋을 되돌린다 |
| Kafka 테이블 엔진 | ClickHouse 안의 Kafka 컨슈머 | 엔진이 묶음을 넘기는 주기(`kafka_flush_interval_ms`, 기본 7.5초) | Kafka (lag) | 엔진 그룹의 오프셋을 되돌린다 |
| 직접 적재 | 수집 서버(HTTP 요청마다) | Fluent Bit이 보낸 묶음 하나(1초마다, 파일마다) | 장비 쪽 Fluent Bit의 디스크 버퍼 | 장비의 원본 파일을 다시 읽게 해야 한다 |
| 직접 적재 + 비동기 INSERT | 수집 서버, 단 ClickHouse가 서버 쪽 버퍼에 모아 한 번에 기록 | ClickHouse의 버퍼 비우기 주기(최대 0.2초)와 크기 | 장비 쪽 Fluent Bit의 디스크 버퍼 | 직접 적재와 같다 |

표의 가운데 열이 이 장의 첫 번째 주제다. 08장에서 본 것처럼 INSERT 한 번은 part 하나를 만들고, part가 많으면 병합이 일을 더 한다. 경로마다 "INSERT 한 번"의 크기를 정하는 손잡이가 다르다. Kafka를 거치면 장비가 몇 대든 컨슈머가 묶음 크기를 정한다. 직접 적재에서는 장비 쪽 에이전트의 전송 단위가 그대로 INSERT 단위가 된다. 비동기 INSERT는 그 둘 사이에서 ClickHouse가 대신 모아 준다.

넷째 열과 다섯째 열이 두 번째 주제다. Kafka를 거치는 두 경로는 저장소가 멈춰도 수집 서버가 계속 200을 돌려주고, 밀린 양이 lag 하나로 보이고, 오프셋을 되돌리면 같은 로그를 다시 넣을 수 있다. 직접 적재는 저장소가 멈추면 수집 서버가 500을 돌려주고, 밀린 로그는 장비 1,000대의 디스크에 흩어져 기다린다.

## 2. 코드

### 직접 적재: `direct/DirectIngestController`

```java
@PostMapping("/ingest/direct")
public ResponseEntity<Void> ingest(@RequestBody List<FluentBitRecord> records,
                                   @RequestParam(defaultValue = "false") boolean async) {
    List<LogEvent> events = records.stream().map(r -> normalizer.normalize(...)).toList();
    ClickHouseWriter writer = async ? directAsync : direct;
    try {
        writer.insert(events);                    // 묶음 하나 = INSERT 한 번
    } catch (RuntimeException e) {
        return ResponseEntity.internalServerError().build();   // Fluent Bit 이 다시 보낸다
    }
    return ResponseEntity.ok().build();           // ClickHouse 가 기록한 뒤에만 200
}
```

응답 계약은 `/ingest/fluentbit`(02장)와 같다. 저장소가 기록한 뒤에 200을 주고, 실패하면 500을 줘서 에이전트가 다시 보내게 한다. 다른 점은 "기록"의 대상이 Kafka가 아니라 ClickHouse라는 것 하나다. 정규화(`LogNormalizer`)와 ClickHouse 쓰기(`ClickHouseWriter`)는 Kafka 경유 경로와 같은 코드를 쓴다. 그래서 두 경로의 차이는 "사이에 Kafka가 있는가"만 남는다. 이 컨트롤러는 `app.compare.enabled=true`일 때만 생긴다.

### 비동기 INSERT: 설정 두 개

```java
new ClickHouseWriter(client, "app_logs_direct_async", () -> new InsertSettings()
        .serverSetting("async_insert", "1")
        .serverSetting("wait_for_async_insert", "1"));
```

`async_insert=1`이면 ClickHouse는 INSERT를 받자마자 part를 만들지 않고 서버 메모리의 버퍼에 쌓는다. 같은 테이블로 오는 INSERT들이 한 버퍼에 모이고, 버퍼가 일정 크기가 되거나 일정 시간(이 버전은 상황에 따라 50~200ms 사이에서 스스로 조절한다)이 지나면 한 번에 part 하나로 쓴다. 수집 서버 코드는 그대로 두고 저장소 쪽에서 작은 INSERT를 모으는 방법이다.

`wait_for_async_insert`가 중요하다. 0이면 ClickHouse가 버퍼에 받기만 하고 바로 응답한다. 빠르지만, 버퍼를 디스크에 쓰기 전에 ClickHouse가 죽으면 그 묶음은 사라지는데 수집 서버와 Fluent Bit은 이미 성공으로 알고 있다. at-least-once 계약이 깨진다. 1이면 버퍼가 실제로 기록된 뒤에 응답하므로 계약이 지켜진다. 대신 요청마다 버퍼가 비워질 때까지 기다린다. 이 대기는 4절에서 잰다. 25.8의 기본값이 이미 1이지만, 서버 설정이 바뀌어도 계약이 깨지지 않도록 코드에 적어 두었다.

### Kafka 테이블 엔진: SQL 두 개 (`docker/clickhouse/compare/01-tables.sql`)

```sql
CREATE TABLE logs.app_logs_kafka_queue (device_id String, source String, event_time String, ...)
ENGINE = Kafka
SETTINGS kafka_broker_list = 'kafka:19092', kafka_topic_list = 'app-logs',
         kafka_group_name = 'clickhouse-kafka-engine', kafka_format = 'JSONEachRow', kafka_num_consumers = 1;

CREATE MATERIALIZED VIEW logs.app_logs_kafka_engine_mv TO logs.app_logs_kafka_engine AS
SELECT device_id, source, parseDateTime64BestEffort(event_time, 3, 'UTC') AS event_time, ... FROM logs.app_logs_kafka_queue;
```

큐 테이블은 데이터를 저장하지 않는다. ClickHouse 안에서 Kafka 컨슈머가 돌며 토픽을 읽고, 읽은 묶음을 구체화 뷰(MATERIALIZED VIEW)에 넘긴다. 구체화 뷰는 넘겨받은 묶음을 변환해 저장 테이블에 INSERT한다. 앱의 적재 컨슈머와 `ClickHouseWriter`가 하는 일을 SQL 두 문장으로 쓴 것이다. 그룹 이름이 앱의 그룹들과 다르므로 같은 메시지를 따로 전부 받는다(07장의 그룹 간 브로드캐스트). 큐 테이블의 컬럼 이름은 토픽 JSON의 필드 이름과 같아야 한다. 다르면 오류 없이 빈 값이 들어가므로 `ClickHouseWriterColumnsTest`가 둘을 맞춰 본다.

코드가 없어지는 대신 잃는 것이 있다. 변환 규칙은 SQL로만 쓸 수 있고, 형식이 깨진 메시지를 만나면 기본 설정에서는 그 자리에서 엔진이 멈춘다(`kafka_skip_broken_messages`, `kafka_handle_error_mode`로 바꾼다). 상태는 `system.kafka_consumers`로 본다. 컨슈머가 ClickHouse 프로세스 안에 살아서, 저장소를 늘리거나 재시작하는 일이 곧 적재를 멈추는 일이 된다.

## 3. 실험 설계

**같은 입력.** 시뮬레이터가 장비 100대의 로그 파일에 1대당 초당 60줄(OHT 차량의 peak 강도)을 10분 동안 쓴다. 360만 줄이다. Fluent Bit 세 개가 이 파일들을 같은 규칙으로 따로 읽는다. 첫째는 `/ingest/fluentbit`로 보내 Kafka에 넣고, 그 토픽을 앱의 적재 컨슈머와 Kafka 테이블 엔진이 각자 읽는다. 둘째와 셋째는 `/ingest/direct`와 `/ingest/direct?async=true`로 보낸다. 네 테이블은 구조가 같고(`CREATE TABLE ... AS logs.app_logs`) 들어오는 방법만 다르다. 시뮬레이터 로그는 형식만 흉내 낸 가짜 문장이다.

**무엇을 재는가.** part 수와 병합은 `system.part_log`(`NewPart`, `MergeParts`, 병합이 읽은 행 수와 걸린 시간), 지금의 part는 `system.parts`, 저장 지연은 테이블마다 `inserted_at - collected_at`, 앱이 보낸 INSERT의 응답 시간은 `system.query_log`에서 센다. 쿼리는 `docker/clickhouse/compare/02-compare.sql` 하나에 모았다.

**재지 않는 것.** 경로마다 초당 몇 행까지 버티는지(처리량의 한계)는 다시 재지 않았다. `kafka-load-test` 브랜치에서 같은 테이블, 같은 client-v2 RowBinary 설계로 잰 값이 있다. 적재 컨슈머 1개가 초당 약 14.7만 행, 3개가 29.3만 행, 6개가 39.8만 행을 넣었고, 장비 2,000대를 docker 안에서 흘렸을 때 저장 지연 p50은 57~73ms였다(`docs/result/benchmark-transport.md`). 이 장의 질문은 "같은 부하에서 경로가 무엇을 바꾸는가"다.

**공정성의 한계.** 네 경로가 한 ClickHouse와 한 앱을 함께 쓰므로 서로의 CPU를 나눠 쓴다. 초당 6,000줄은 이 PC에 가벼운 부하라(ClickHouse 평균 1.4코어) 간섭은 작다고 보지만, ClickHouse CPU를 경로별로 나눠 재지는 못했다. 대신 병합에 쓴 시간을 테이블별로 센다.

## 4. 평시 부하 결과 (2026-10-19)

| | Kafka 경유 | Kafka 테이블 엔진 | 직접 적재 | 직접 + 비동기 INSERT |
|---|---|---|---|---|
| 새 part 수 (10분) | 1,192 | 77 | 55,838 | 1,669 |
| part 하나의 평균 행 수 | 3,020 | 46,751 | 64 | 2,157 |
| 병합 횟수 | 229 | 13 | 5,393 | 335 |
| 병합이 다시 읽은 행 ÷ 넣은 행 | 4.6 | 1.7 | 15.9 | 6.2 |
| 병합에 쓴 시간 합계 | 14초 | 5초 | 197초 | 24초 |
| 도는 동안 본 active part 최대 | 11 | 9 | 62 | 12 |
| 저장 지연 p50 / p99 | 1.1초 / 2.3초 | 4.8초 / 9.1초 | 0.8초 / 1.9초 | 1.0초 / 2.2초 |
| 앱이 보낸 INSERT 응답 p50 / p99 | 10ms / 36ms | (ClickHouse 안) | 22ms / 97ms | 186ms / 227ms |

360만 줄은 네 경로 모두 결국 빠짐없이 들어갔고 중복도 없었다. 병합이 끝난 뒤의 디스크 크기도 넷 다 121.5~121.8MiB로 같았다. 경로가 바꾸는 것은 최종 결과가 아니라 그 결과에 이르기까지 ClickHouse가 하는 일과 걸리는 시간이다. ("결국"에는 단서가 붙는다. 6절)

**직접 적재는 part를 47배 만든다.** Fluent Bit은 파일마다 따로 묶어 1초마다 보내므로(02장의 태그 이야기), 장비 100대면 초당 요청이 약 93개, 요청 하나가 64행이다. 그것이 그대로 INSERT 93번, part 93개가 된다. 이 PC는 그것을 따라갔다. active part는 최대 62개였고 끝나자 5개로 줄었다. 대가는 병합이다. 작은 part를 큰 part로 합치는 일을 여러 단계 반복하므로 한 행이 평균 15.9번 다시 읽히고 쓰였고, 병합 스레드가 10분 동안 197초를 썼다. Kafka 경유의 14배다. 장비가 1,000대면 요청과 part가 열 배가 된다. 병합 일도 열 배라면 10분에 약 2,000초, 코어 3개 남짓을 병합만 하는 데 쓰는 셈이다(추정, 재지 않았다). 그 전에 active part가 파티션당 1,000개(`parts_to_delay_insert`)를 넘으면 ClickHouse가 INSERT를 늦추기 시작한다.

**비동기 INSERT는 서버 쪽에서 33배를 모은다.** 앱이 보낸 INSERT는 직접 적재와 거의 같은 55,385번인데 part는 1,669개다. 요청 약 33개가 한 part가 됐다. 저장 지연도 직접 적재와 비슷하다. 대가는 요청 하나가 응답을 받기까지의 시간이다. p50 186ms로, 버퍼가 비워질 때까지 기다리기 때문이다(`wait_for_async_insert=1`). 그동안 수집 서버의 요청 스레드와 ClickHouse 연결이 붙잡혀 있다. 초당 요청 약 93개가 각각 0.19초씩 붙잡으면 평균 17개쯤이 동시에 열려 있다(요청 수 × 머무는 시간으로 계산한 값). 앱의 연결 상한을 16에서 64로 올린 이유다. 장비 1,000대면 170개쯤이 된다.

**Kafka 경유는 장비 수와 무관하게 묶음을 키운다.** 적재 컨슈머가 1MB 또는 0.5초 단위로 묶어 part 하나에 3,020행을 넣었다. 장비가 1,000대가 되어도 INSERT 횟수는 늘지 않고 묶음이 커질 뿐이다. 저장 지연 p50 1.1초는 Fluent Bit의 1초 주기와 적재 컨슈머의 최대 0.5초 대기를 합친 값과 맞는다.

**Kafka 테이블 엔진은 가장 크게 묶고 가장 늦다.** 7.5초마다 넘기므로 part 하나에 약 4.7만 행, 병합도 거의 없다. 대신 저장 지연 p50이 4.8초, p99가 9.1초다. `kafka_flush_interval_ms`를 줄이면 지연은 줄고 part는 늘어난다. Kafka 경유의 `fetch.max.wait.ms`와 같은 손잡이를 ClickHouse 쪽에 둔 것이다.

## 5. ClickHouse가 3분 멈추면

같은 부하(장비 100대 × 초당 60줄)를 8분 흘리며, 2분째에 `docker stop clickhouse`, 5분째에 `docker start clickhouse`를 했다. 직접 적재 두 경로의 Fluent Bit은 무한 재시도(`Retry_Limit False`)이고, 재시도 대기 상한은 60초(`scheduler.cap`)로 줄여 두었다.

| | Kafka 경유 | Kafka 테이블 엔진 | 직접 적재 | 직접 + 비동기 INSERT |
|---|---|---|---|---|
| 멈춘 동안 로그가 기다린 곳 | Kafka (적재 컨슈머 lag 최대 1,121,952) | Kafka (엔진도 ClickHouse와 함께 멈춤) | Fluent Bit 디스크 버퍼 (청크 최대 1,810개) | Fluent Bit 디스크 버퍼 (청크 최대 2,054개) |
| 수집 서버의 응답 | 계속 200 | 계속 200 | 500 9,802번 | 500 11,621번 |
| 재시도한 쪽과 횟수 | 적재 컨슈머 156번(1초마다) | 없음 (다시 뜬 엔진이 커밋된 오프셋부터) | Fluent Bit 10,951번 | Fluent Bit 12,634번 |
| 다시 켠 뒤, 켜기 직전까지 쓰인 줄을 다 저장하기까지 | 22~28초 | 17~22초 | 33~39초 | 33~39초 |
| 진짜 중복 (같은 키, 같은 줄) | 0 | 0 | 0 | 0 |

네 경로 모두 결국 빠짐없이 들어갔고(6절의 단서를 빼면) 중복도 없었다. 다른 것은 기다리는 동안의 모습이다.

Kafka를 거치는 두 경로에서는 수집 서버가 아무 일 없다는 듯 200을 돌려줬다. Fluent Bit은 재시도 한 번 없이 보냈고, 밀린 110만 줄은 Kafka 디스크에 한 줄로 쌓였다가 lag 숫자 하나로 보였다. 다시 켜자 적재 컨슈머는 쌓인 것을 큰 묶음으로 읽어 빠르게 따라잡았다. Kafka 테이블 엔진이 가장 빨리 따라잡은 것은 가장 크게 묶어 넣기 때문으로 보인다.

직접 적재 두 경로에서는 장애가 장비 쪽까지 번졌다. 수집 서버는 3분 동안 1만 번 넘게 500을 돌려줬고, 에이전트는 파일마다 따로 묶은 청크를 2,000개 가까이 쌓으며 같은 청크를 거듭 다시 보냈다. 이 연습에서는 에이전트 하나가 장비 100대 몫이라 청크가 한곳에 쌓였지만, 실제로는 장비 1,000대가 각자 자기 디스크에 쌓고 각자 재시도한다. 다시 켠 뒤 따라잡는 시간은 Kafka 경로보다 10초 남짓 길었다. 재시도 간격이 무작위로 늘어나 있어 청크마다 다음 시도까지 기다리기 때문이다. 이 실험은 상한을 60초로 줄였지만 기본값(2,000초)이면 일부 청크는 몇십 분 뒤에야 다시 시도된다(재지 않았다). 반대로 상한을 너무 줄이면 장애 동안 장비 1,000대가 짧은 간격으로 계속 두드린다.

## 6. 다시 넣기, 그리고 측정에서 드러난 두 가지

**다시 넣기.** 적재 컨슈머 그룹의 오프셋을 처음으로 되돌리고(`kafka-consumer-groups --reset-offsets --to-earliest`) 앱을 다시 띄우자, 토픽에 남아 있던 648만 줄이 INSERT 353번(한 번에 약 18,400행)으로 82초 만에 다시 들어갔다. `count()`는 두 배(약 1,289만)가 됐지만 `count() FINAL`과 고유 멱등키 수는 그대로였다. 같은 키를 다시 넣었으므로 ReplacingMergeTree가 접는다. 파서를 고쳐 새 테이블에 다시 넣는 일도 같은 방법으로 된다. 직접 적재 경로에는 되돌릴 오프셋이 없다. 같은 일을 하려면 장비 1,000대의 원본 파일을 다시 읽게 해야 한다. 속도(초당 약 7.9만 행)는 앱이 Windows에서 돌며 docker의 포트 전달을 두 번 거친 값이다. docker 안에서의 적재 속도는 브랜치가 잰 초당 14.7만 행(컨슈머 1개)을 본다.

**디스크 버퍼에 남는 청크.** 부하가 끝나고 몇 분이 지나도 세 에이전트 모두 읽은 줄 수(`input.records`)보다 보낸 줄 수(`proc_records`)가 적었다. 평시 실험에서 242줄, 507줄, 160줄(청크 4개, 7개, 2개), 장애 실험 뒤에 584줄, 439줄, 410줄(청크 10개, 7개, 7개)이 저장 폴더에 청크 파일로 남아 있었다. 재시도 예약도 없었고, 저장 지표(`/api/v1/storage`)에서 이 청크들은 메모리에 올라온(up) 상태였다. 에이전트를 재시작하자 디스크 버퍼를 다시 읽어 2초 안에 모두 보냈다. 디스크 버퍼 덕분에 잃지는 않았지만, 재시작하기 전까지는 저장소에 없었다. 남은 청크는 부하가 시작된 순간(에이전트 셋이 파일 100개를 한꺼번에 보내다 연결이 거부된 때)과 장애 전후에 많이 생겼다. 원인은 확정하지 못했다. 세 경로가 같은 에이전트(Fluent Bit 4.2.8)를 쓰므로 경로의 차이는 아니다.

**재시작한 에이전트의 오프셋.** 장애 실험 앞에서 저장 지표를 켜려고 에이전트를 재시작했는데, 그 뒤에 읽은 줄의 `offset`이 파일 안의 실제 위치가 아니라 0부터 다시 매겨졌다. 장비 파일 하나를 보면 재시작 뒤의 줄은 실제로 2.30MB~4.13MB 자리에 있는데 `offset`은 0~1.83MB였다. 그래서 재시작 전의 다른 줄과 멱등키 `(device_id, source, offset)`가 겹쳤다. 겹친 줄은 약 4.6만 줄(재시작 뒤 줄의 1.6%)이었고, 줄 길이 평균 63바이트로 추정한 값(288만 ÷ 63)과 맞는다. ReplacingMergeTree는 이것을 중복으로 알고 병합 때 하나를 지운다. 네 테이블 모두 `count() FINAL`이 6,434,439로, 쓴 648만 줄보다 45,661줄 적었다. 수집은 빠짐없이 했는데 저장소가 서로 다른 로그를 지운 것이다.

원인은 Fluent Bit 4.2.8의 tail 입력이다. DB에서 읽던 위치를 되살릴 때 파일을 그 위치로 옮기기는 하지만, `Offset_Key`에 쓰는 값의 기준(`stream_offset`)을 그 위치로 맞추지 않는다. 줄 세 개를 쓰고, 에이전트를 재시작하고, 세 줄을 더 쓰는 최소 실험에서 4.2.8은 뒤 세 줄에 0, 8, 16을 붙였고 5.1.4는 실제 위치인 24, 32, 40을 붙였다(2026-10-19, 5.1.4 소스에는 DB 경로에서도 그 값을 맞추는 줄이 있다). 02장에서 정한 멱등키는 "같은 파일의 같은 위치는 같은 줄"이라는 전제 위에 있다. 장비의 에이전트는 장비가 재부팅될 때마다 재시작하므로, 이 전제가 깨지는 버전을 쓰면 중복 제거가 곧 유실이 된다. 이 문제는 경로를 가리지 않는다. 직접 적재든 Kafka 경유든 같은 키로 같은 테이블에 넣기 때문이다. 고치는 방법(에이전트 버전, 키 구성)은 계획서의 열린 항목으로 남겼다.

## 7. 그래서 무엇을 고르는가

이 실험이 숫자로 보여 준 것을 Log Collector에 옮기면 다음과 같다.

**Kafka 경유(지금 설계)를 유지할 이유가 셋 확인됐다.** 첫째, INSERT 크기가 장비 수와 무관하다. 직접 적재는 장비 100대에서 이미 part를 47배 만들었고, 그 차이는 장비 수에 비례해 커진다. 둘째, 저장소 장애가 장비 쪽으로 번지지 않는다. 3분 장애 동안 수집 서버는 계속 200을 돌려줬고 밀린 양은 lag 하나로 보였다. 직접 적재에서는 장비마다 재시도와 디스크 버퍼가 생긴다. 셋째, 다시 넣을 수 있다. 오프셋을 되돌리면 Kafka의 보존 기간 안의 로그를 저장소에 다시 넣을 수 있다. 대가는 브로커를 하나 더 운영하는 것과 1초 남짓의 저장 지연이다.

**비동기 INSERT는 "Kafka 없이 간다"면 고를 차선이다.** 수집 서버 코드는 그대로 두고 part 문제를 거의 Kafka 경유 수준(33배 감소)으로 풀었다. 그러나 장애 격리와 재처리는 직접 적재와 같고, 요청마다 0.2초 가까이 기다리므로 장비 1,000대에서는 수집 서버의 동시 요청이 170개쯤 붙잡힌다.

**Kafka 테이블 엔진은 앱 쪽 적재 코드를 없애는 선택지다.** part가 가장 적고 장애 뒤 가장 빨리 따라잡았다. 대신 기본 설정의 저장 지연이 5~9초이고, 변환과 오류 처리가 SQL과 ClickHouse 설정 안으로 들어가며, 적재가 ClickHouse 프로세스의 수명에 묶인다. 명세서의 대시보드가 몇 초 늦어도 되는지에 따라 후보가 된다.

**직접 적재(동기)는 장비 수가 늘수록 불리하다.** 지연은 가장 짧았지만(p50 0.8초) 그 차이는 Kafka 경유보다 0.3초다. 장비 1,000대에서 part와 병합이 감당되는지는 이 PC에서 재지 않았다(추정은 4절).

경로와 상관없이 새로 드러난 위험이 둘이다. 에이전트가 재시작하면 멱등키가 겹치는 문제(6절)는 경로 선택보다 먼저 정해야 한다. 디스크 버퍼에 청크가 남는 문제는 에이전트의 `input.records`와 `proc_records`, 저장 지표를 감시하면 드러난다. 둘 다 Fluent Bit 쪽의 일이라 Step 5(전송 최적화)에서 이어서 본다.

## 확인 질문

1. 직접 적재의 part 수를 줄이려면 수집 서버, Fluent Bit, ClickHouse 중 어디를 고칠 수 있는가? 각각 무엇을 잃는가?
2. 비동기 INSERT를 `wait_for_async_insert=0`으로 쓰면 무엇이 빨라지고 무엇이 깨지는가? 그 상태에서 ClickHouse가 죽으면 Fluent Bit은 그 로그를 다시 보내는가?
3. Kafka 테이블 엔진의 저장 지연을 1초 안쪽으로 줄이려면 어떤 설정을 바꾸는가? 그때 part 수는 어느 경로와 비슷해지겠는가?
4. 장비가 1,000대로 늘면 네 경로의 part 수는 각각 어떻게 변하겠는가? 표의 숫자로 추정해 보고, 어느 경로가 장비 수에 비례하는지 말하라.
5. 파서를 고친 뒤 지난 일주일치 로그를 새 테이블에 다시 넣어야 한다. 경로마다 무엇이 필요한가?
