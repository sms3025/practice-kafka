# 06. 실습 워크북

각 실습은 "할 것 → 기대 결과 → 확인 질문" 순서다. 체크박스를 채우며 진행한다. 기대 결과가 안 나오면 01장 7절(자주 나는 오류)을 먼저 본다.

이 워크북은 체크리스트이자 기록지다. 항목마다 어느 터미널에서 어떤 명령을 치고 무엇을 보고 넘어가는지는 [`../practice/`](../practice/README.md)에 같은 번호(A1, B2, ...)로 풀어 썼다. 처음 하는 사람은 그쪽을 따라 하고, 결과는 여기에 적는다.

이 워크북은 단계 상태를 올리는 근거이기도 하다. 루트 `README.md`의 진행 상황 표에서 Step 1·2는 "구현 완료, 실행 검증 전"이다. `./gradlew test`는 2026-10-13에 통과를 확인했다. 깨끗한 환경(`down -v` 후 `up -d`)에서 B절과 D절의 기대 결과가 그대로 나오면 두 단계를 "완료"로 올린다. 그래서 A~D절이 이 저장소의 첫 실습이다. 이후 단계의 절(G부터)은 단계를 마칠 때마다 여기에 붙는다. 절 이름과 순서는 `../plan/01-학습자료-제작-방침.md` 4절 표를 따른다.

## A. 환경 (Step 0)

- [ ] **A1. 인프라 기동.** `docker compose -f docker/docker-compose.yml up -d` 후 `ps`에서 kafka가 `healthy`, kafka-ui와 fluent-bit이 `running`.
- [ ] **A2. Kafka UI 접속.** http://localhost:8085 → Brokers 1개, Topics에 `__consumer_offsets`만 (또는 비어 있음).
- [ ] **A3. CLI로 토픽 만들고 주고받기.** `docs/result/step0-환경구성.md`의 명령을 그대로 실행. 같은 키(`order:`)의 메시지가 같은 파티션 번호로 찍힌다.
  - 질문: 키 없이(`parse.key=false`) 보내면 파티션이 어떻게 분포하는가?
- [ ] **A4. 토픽 삭제 후 `down -v`.** 다시 `up -d` 하면 토픽이 없는 것을 확인 (볼륨이 지워졌으므로).
- [ ] **A5. 명함 주소 바꿔 보기.** `docker-compose.yml`의 `KAFKA_ADVERTISED_LISTENERS`에서 `PLAINTEXT_HOST://localhost:9092`를 `PLAINTEXT_HOST://kafka:9092`로 바꾸고 `up -d`로 다시 띄운 뒤 앱을 기동한다. 기대 결과: 앱은 bootstrap 접속까지는 되지만 `kafka`라는 호스트를 찾지 못한다는 경고가 반복되고 전송이 타임아웃 난다. Kafka UI는 계속 정상이다. 확인 후 원래대로 되돌린다.
  - 질문: 같은 브로커인데 왜 Kafka UI는 되고 Spring 앱만 안 되는가? (01장 4절의 문과 명함 표로 설명)

## B. Producer / Consumer 기본 (Step 1)

- [ ] **B0. 그림으로 먼저 확인한다.** [Kafka 기초 HTML](../concepts/01-kafka-basics.html)을 브라우저로 연다. 3절의 컨슈머 수를 1 → 3 → 4로 바꾸고, 4절에서 두 건 처리 → 커밋 없이 재시작 → 다시 처리한다. 처음 상태로 돌린 뒤 두 건 처리 → 커밋 → 재시작도 비교한다. 5절에서 컨슈머 정지 → 세 턴 발행 → 재개 → 발행 없이 소비한다. 기대 결과: 네 번째 컨슈머는 대기하고, 커밋 전 장애는 재처리로 이어지며, 소비해도 Kafka의 기록 수는 줄지 않는다. 이 모형은 실제 Kafka에 연결하지 않는다.
  - 질문: 커밋 위치가 2이면 다음 읽을 오프셋은 무엇인가? 파일의 offset과 Kafka의 offset은 무엇이 다른가?

- [ ] **B1. 앱 기동.** 콘솔에 `partitions assigned: [app-logs-0, app-logs-1, app-logs-2]`. Kafka UI → Topics에 `app-logs`(파티션 3).
- [ ] **B2. 한 건 발행.** `POST /api/logs` (`http/step1.http`). 응답 본문이 정규화된 LogEvent(`event_time`이 `Z`로 끝남). 콘솔에 `[consume #1] ...`.
  - 질문: 응답 코드가 202인 이유는? 200과 무엇이 다른가?
- [ ] **B3. 1,000건 직접 발행.** `POST /api/logs/generate?count=1000&devices=50`. `elapsedMs` 기록: ______ ms. Kafka UI Messages에서 `device_id`별 파티션이 일정한지 확인.
- [ ] **B4. 재시작 후 오프셋.** 앱을 껐다 켠다. 이전 1,000건을 다시 소비하지 않는다. Kafka UI → Consumers → log-printer의 커밋 오프셋 확인.
  - 질문: `auto-offset-reset=earliest`인데 왜 처음부터 안 읽는가?
- [ ] **B5. 새 그룹.** `app.kafka.consumer-groups.printer=log-printer-2`로 바꾸고 재시작. 이번에는 처음부터 전부 다시 소비한다. 원복.

## C. Producer 설정 실험 (03장)

각 항목은 `application.properties` 수정 → 재시작 → `Run-C` → 기록. 끝나면 원복. `Run-C`는 워밍업 1회 뒤 `generate?count=20000&devices=200`을 3회 보내 가운데 값과 Actuator 프로듀서 지표, 브로커 디스크 증가분을 한 번에 보여 주는 PowerShell 함수다. 측정 전 로그 레벨 조정과 함수 정의는 `../practice/03-프로듀서-설정-실험.md` C0에 있다. Kafka UI의 Brokers → Metrics는 브로커 JMX가 꺼져 있어 쓰지 않는다.

| 실험 | 설정 | elapsedMs | requests | batchBytes | diskKB | 관찰 |
|---|---|---|---|---|---|---|
| C1 기준 | `linger.ms=5`, `batch-size=16384`, `acks=all` | | | | | 배치가 거의 꽉 차서 나감 |
| C2 | `linger.ms=0` | | | | | 요청 수 변화 |
| C3 | `linger.ms=50` | | | | | 몰아치는 부하에선 C1과 비슷? |
| C4 | `batch-size=1024` | | | | | 배치가 작아 요청 수 ↑ |
| C5 | `acks=1` | | | | | 단일 브로커에선 차이 거의 없음 (왜?) |
| C6 | `compression-type=lz4` | | | | | `compression` 값과 diskKB 감소 |

- [ ] **C7. 키 제거.** `LogEventProducer.send()`의 키를 `null`로. `generate?count=300&devices=3` 후 Messages에서 같은 device_id가 여러 파티션에 흩어짐. 원복.
- [ ] **C8. Kafka 정지 중 발행.** `docker stop kafka` → `POST /api/logs` → 60초 동안 응답 없다가 500, 콘솔에 `Topic app-logs not present in metadata after 60000 ms` → `docker start kafka`. 그 메시지는 들어갔는가? (답: 사라졌다. Kafka 4 클라이언트는 알던 브로커가 모두 끊기면 메타데이터를 버리고 bootstrap부터 다시 시작하므로, `send()`가 `max.block.ms`만큼 막힌 뒤 예외를 던진다. 호출자가 500을 받았고 다시 보낼 주체가 없다. 2026-10-15 실측)

## D. Fluent Bit 수집 경로 (Step 2)

- [ ] **D1. 단순 시뮬레이터.** `POST /api/logs/simulate?lines=200` → 수 초 뒤 `/api/logs/stats`의 `receivedFromFluentBit=200`, `consumed=200`. `docker/devices/sim/dev-00NN.log` 파일이 생겼는지 확인.
- [ ] **D2. 정규화 실패 경로.** 시뮬레이터 로그 중 약 3%는 시각이 없다. Kafka UI Messages에서 `level: null`이고 `event_time == collected_at`인 메시지를 찾는다.
- [ ] **D3. Fluent Bit 지표.** http://localhost:2020/api/v1/metrics 에서 `input.tail.0.records`, `output.http.0.proc_records`, `retries`.
- [ ] **D4. 수집 서버 다운.** 앱을 끄고 `simulate`는 못 부르니 파일에 직접 추가: `Add-Content -Path docker\devices\sim\dev-0001.log -Value "2026-10-15 15:00:00.000 [ERROR] manual" -Encoding ascii` (`echo >>`는 PowerShell 5.1에서 UTF-16으로 써서 깨진다). `docker logs fluent-bit`에 connection refused + retry. 앱을 켜면 들어온다. `retries`가 늘었다가 멈춘다. 재시도 간격이 길어져 안 들어오면 `docker restart fluent-bit`.
- [ ] **D5. Kafka 다운.** `docker stop kafka` → `simulate?lines=50` → 60초 뒤 앱 콘솔에 `Kafka 발행 실패. Fluent Bit 에 재전송을 요청한다` → Fluent Bit에 `HTTP status=500`과 retry → `docker start kafka` → 1분 안에 50건 전부 도착. **유실 0 확인.** C8과 같은 장애인데 왜 여기서는 안 사라지는가?
  - 질문: D5에서 같은 줄이 두 번 들어올 수 있는 시나리오를 설명하라. 그것을 어떻게 걸러낼 것인가?
- [ ] **D6. 직접 호출.** `http/step2.http`의 "Fluent Bit 이 보내는 것과 같은 형식" 요청을 보내 200과 소비 로그 확인. 본문의 `offset`을 같은 값으로 두 번 보내면? (지금은 두 번 다 들어간다. Step 4에서 중복 제거)

## F. 다음 단계로 넘어가기 전 스스로 설명하기

아래를 각각 다섯 문장 이내로 말로 설명할 수 있으면 Step 3으로 간다.

1. 토픽, 파티션, 오프셋, 컨슈머 그룹의 관계.
2. 같은 키가 같은 파티션에 가는 것이 이 프로젝트에서 왜 중요한가.
3. `send()`가 비동기라는 것이 수집 서버의 응답 코드 설계에 어떻게 반영됐는가.
4. at-least-once가 무엇이며, 이 파이프라인의 어느 두 구간에서 중복이 생길 수 있고, 무엇으로 걸러낼 것인가.
5. Fluent Bit, Kafka UI, ClickHouse, Grafana가 각각 파이프라인의 어디에 왜 들어가는가.
6. 장비가 보내는 양이 수집 서버의 처리량보다 많을 때 무슨 일이 일어나는가. 잠깐 몰릴 때와 계속 많을 때를 나눠, 이 파이프라인의 어느 설정이 버티게 해 주고 무엇을 더 해야 하는지 설명한다. (힌트: Fluent Bit 디스크 버퍼와 재시도, 서버의 빠른 거절, 압축과 필터링, 수집 서버 수평 확장)
7. 수집 서버가 1대뿐이어도 Kafka를 거치는 것과 ClickHouse에 바로 넣는 것은 다른가. 지금은 말로만 답하고, Step 4+에서 측정으로 확인한다. (힌트: ClickHouse의 part, DB 장애 때 로그가 기다리는 장소, 재처리)
