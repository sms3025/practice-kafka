# 00. 학습 가이드: 이 프로젝트로 Kafka를 배우는 방법

이 폴더(`docs/study`)는 Kafka를 처음 보는 사람이 이 프로젝트의 코드를 읽고, 직접 돌려 보고, 왜 그렇게 짰는지 이해하는 것을 목표로 한 교재다. 저장소 전체의 아키텍처와 네 문서 폴더의 지도는 `../README.md`에 있으므로 그것을 먼저 읽고 오면 좋다. `docs/concepts`가 개념 사전, `docs/result`가 단계별 작업 기록이라면, `docs/study`는 "처음부터 끝까지 따라가는 수업"이다. 각 장은 설명 → 코드 읽기 → 실습 → 스스로 확인하는 질문의 순서로 되어 있다.

## 무엇을 만들고 있는가

기업 연계 프로젝트는 **Log Collector**다. 공장 안을 달리는 OHT(Overhead Hoist Transport, 반도체 공장 천장 레일을 따라 웨이퍼를 나르는 무인 운반 차량) 1,000대 이상이 각자 로컬 디스크에 쌓는 로그를 한곳에 모아 저장하고 검색·시각화하는 시스템이다. 차량마다 로그 포맷과 시각 기준이 다르고, 지금은 장애가 나면 차량에 가서 파일을 꺼내 봐야 한다. 이것을 "차량 → 에이전트 → 중앙 수집 서버 → 완충(Kafka) → 저장소(ClickHouse) → 대시보드"로 바꾸는 것이 목표다.

연습 프로젝트는 그 구조를 축소판으로 만든다. 차량 대신 로그 생성기, 1,000대 대신 몇 대, 운영 서버 대신 docker 컨테이너를 쓰지만 **구성요소와 데이터 흐름은 같다.** 그래서 여기서 배운 것이 실제 프로젝트에 그대로 옮겨진다.

```
[차량 로컬 로그 파일] ─▶ [Fluent Bit 에이전트] ─HTTP─▶ [Spring 수집 서버] ─▶ [Kafka] ─▶ [컨슈머] ─▶ [ClickHouse] ─▶ [대시보드]
   ohtsim 생성기        docker 컨테이너            우리가 짜는 코드       docker     우리가 짜는 코드   docker(Step 4)   Grafana(Step 4)
```

## Kafka가 왜 들어가는가 (한 문단 요약)

차량 1,000대가 초당 60줄씩 보내면 초당 6만 줄, 하루 50억 줄이다. 수집 서버가 이것을 받자마자 DB에 쓰면 DB가 잠깐만 느려져도 수집 서버가 밀리고, 수집 서버가 밀리면 1,000대 에이전트가 동시에 재시도하며 상황이 악화된다. Kafka는 수집 서버와 DB 사이에서 "일단 디스크에 순서대로 적어두는" 역할을 한다. 수집 서버는 Kafka에 쓰고 즉시 응답하고, DB 적재는 뒤에서 자기 속도로 따라간다. 생산자와 소비자의 속도를 분리하는 것, 그것이 Kafka를 쓰는 첫 번째 이유다. 두 번째 이유는 같은 로그를 여러 곳(저장, 통계, 이상 탐지)에서 각자 읽을 수 있다는 것이고, 세 번째는 어느 구성요소가 죽어도 로그가 Kafka에 남아 있어 복구 후 이어서 처리할 수 있다는 것이다.

## 사전 지식

Java와 Spring Boot의 기본(`@Component`, 의존성 주입, `application.properties`)은 안다고 가정한다. Docker는 `docker compose up -d`, `docker ps`, `docker logs` 세 명령만 알면 된다. 네트워크는 "포트"가 무엇인지 알면 충분하다.

## 학습 태도에 대한 조언

Kafka는 설정 항목이 수백 개라 외우려 들면 끝이 없다. 이 프로젝트는 설정을 열몇 개만 쓰고, 그 각각을 "바꿔 보면 무엇이 달라지는지"로 익힌다. 문서를 읽기만 하지 말고 `application.properties`의 값을 바꾸고 재시작해 Kafka UI와 콘솔 로그가 어떻게 달라지는지 보는 것이 핵심이다. 06장 워크북에 그 실험 목록이 있다.
