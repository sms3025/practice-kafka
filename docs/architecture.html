1. 큰 그림: 무엇을 축소해서 만들고 있는가

기업 연계 프로젝트 Log Collector는 반도체 공장의 OHT 차량 1,000대 이상이 각자 로컬 디스크에 쌓는 로그를 중앙에 모아 저장하고 검색·시각화하는 시스템이다. 이 저장소는 그 구조를 축소판으로 만들면서 Kafka를 배운다. 차량 대신 로그 생성기, 1,000대 대신 몇 대, 운영 서버 대신 docker 컨테이너를 쓰지만 구성요소와 데이터 흐름은 같다.

Kafka가 가운데 들어가는 이유 한 문단. 수집 서버가 받은 로그를 바로 DB에 쓰면, DB가 잠깐만 느려져도 수집 서버가 밀리고, 수집 서버가 밀리면 에이전트 1,000대가 동시에 재시도하며 상황이 악화된다. Kafka는 "일단 디스크에 순서대로 적어두는" 완충 계층이다. 수집 서버는 Kafka에 쓰고 즉시 응답하고, DB 적재는 뒤에서 컨슈머가 자기 속도로 따라간다. 생산자와 소비자의 속도를 분리하는 것이 첫째 이유, 같은 로그를 여러 소비자가 독립적으로 읽을 수 있는 것이 둘째, 어느 구성요소가 죽어도 로그가 Kafka에 남아 복구 후 이어서 처리할 수 있는 것이 셋째 이유다.

2. 실행 구성도: 프로세스 넷과 포트

프로세스는 넷이다. 셋은 docker compose(docker/docker-compose.yml)가 띄우는 컨테이너이고, 하나는 호스트에서 띄우는 Spring Boot 앱이다. 호스트 폴더 docker/devices가 "차량의 로컬 디스크" 역할을 하며, 생성기가 여기에 쓰고 Fluent Bit 컨테이너가 읽기 전용으로 마운트해서 읽는다.

3. 데이터 흐름: 로그 한 줄이 지나는 여섯 구간

아래는 연습용 단순 형식 한 줄이 파일에서 컨슈머까지 가는 동안 각 구간에서 무엇이 바뀌는지다. 예시는 저장소 주석에 있는 가짜 문장이며, 실제 OHT 로그 형식 두 가지(UILogger, OHTHandlerLogger)도 4번 구간에서 같은 방식으로 파싱된다.

담당: Fluent Bit [INPUT] tail · docker/fluent-bit/fluent-bit.conf

파일 → Fluent Bit 레코드

Fluent Bit이 /var/log/devices/ 아래 파일을 5초마다 폴링해 새 줄을 읽는다. 설정의 Path_Key source, Offset_Key offset 때문에 원문 외에 파일 경로와 파일 내 바이트 위치가 레코드에 붙는다. 어디까지 읽었는지는 SQLite(tail.db)에 기록되어 재시작해도 이어서 읽는다.

들어오는 것 (파일의 새 줄)
2026-10-12 14:03:21.123 [WARN] ECU temperature high: 97C
나가는 것 (레코드)
log    = "2026-10-12 14:03:21.123 [WARN] ECU ..."
source = "/var/log/devices/sim/dev-0007.log"
offset = 1842
담당: Fluent Bit [OUTPUT] http

Fluent Bit → HTTP POST

1초(Flush 1)마다 모인 레코드를 JSON 배열로 묶어 host.docker.internal:8080/ingest/fluentbit에 POST 한다. Json_date_key collected_at으로 수집 시각이 추가된다. 응답이 2xx가 아니면 Retry_Limit False에 따라 무한 재시도하며, 그동안 레코드는 디스크 버퍼(storage.type filesystem)에 남는다. 수집 서버나 Kafka가 죽어 있어도 로그가 유실되지 않는 이유가 이것이다.

나가는 것 (HTTP 본문)
POST /ingest/fluentbit
Content-Type: application/json

[
  {"collected_at":"2026-10-12T05:03:21.123456Z",
   "log":"2026-10-12 14:03:21.123 [WARN] ECU temperature high: 97C",
   "source":"/var/log/devices/sim/dev-0007.log",
   "offset":1842},
  ...
]
실패 시
2xx 아님 → 같은 묶음 재전송 (중복 가능)
연결 거부 → 디스크 버퍼에 보관 후 재시도
→ /api/v1/metrics 의 retries 가 늘어난다
담당: ingest/FluentBitIngestController, ingest/FluentBitRecord

HTTP → 수집 서버

Spring MVC가 JSON 배열을 List<FluentBitRecord>로 역직렬화한다. 컨트롤러가 하는 일은 셋뿐이다. 받는다, 정규화한다, Kafka에 넣는다. 저장소 적재는 여기서 하지 않는다. 응답 코드가 곧 전송 보장이다. 묶음 안의 모든 메시지가 브로커 ack를 받은 뒤에야 200을 돌려주고, 하나라도 실패하면 500을 돌려 Fluent Bit이 재전송하게 한다.

핵심 코드 (요약)
for (record : records)
    futures[i] = producer.send(normalizer.normalize(...));
CompletableFuture.allOf(futures).join();   // 전부 ack 대기
return 200;                                 // 실패 시 500
왜 이렇게
Kafka 에 넣기 전에 200 을 주면
→ 그 사이 앱이 죽을 때 유실
ack 를 기다린 뒤 200 을 주면
→ 유실 없음, 대신 중복 가능 (at-least-once)
담당: log/LogNormalizer → log/LogEvent

정규화: 원문 한 줄을 명세서 스키마로

명세서가 요구하는 정규화는 둘이다. 첫째, 에이전트는 파일 경로만 알므로 경로에서 정규식(app.ingest.device-id-pattern)으로 device_id를 뽑는다. OHT 로그는 장비 ID가 파일명이 아니라 폴더 이름에 있다. 둘째, 장비가 찍은 로컬 시각(app.ingest.device-zone=Asia/Seoul)을 UTC event_time으로 바꾼다. 세 가지 형식을 위에서부터 차례로 시도하고, 어느 것도 맞지 않으면 시각을 collected_at으로 대체하고 본문은 raw 전체로 둔다. 버리지 않고 어떻게든 저장하는 것이 로그 파이프라인의 원칙이다.

발행: Kafka 토픽 app-logs로

KafkaTemplate.send(topic, key=device_id, value=LogEvent). 값은 JacksonJsonSerializer가 snake_case JSON으로 바꾼다. send()는 비동기다. 메시지는 내부 버퍼에 쌓였다가 I/O 스레드가 linger.ms=5, batch-size=16384 기준으로 배치 전송하고, 결과는 Future로 온다. acks=all이므로 브로커가 기록을 마쳐야 ack가 온다. 키가 device_id라서 같은 장비의 로그는 항상 같은 파티션에 발생 순서대로 쌓인다. 1,000대가 3개 파티션에 해시로 분산되므로 특정 파티션으로 쏠리지 않는다.

5. 핵심 설계 결정 네 가지

왜 Fluent Bit이 Kafka에 직접 쓰지 않고 HTTP로 수집 서버를 거치는가

Fluent Bit에는 kafka 출력 플러그인이 있어 직접 쓸 수도 있다. 그러나 1,000대 장비가 각자 Kafka 클라이언트가 되면 브로커 주소, 인증, 토픽 구조가 장비마다 배포되어야 하고, 형식 정규화와 device_id 추출을 할 곳이 없다. 수집 서버를 두면 장비 쪽 설정은 "HTTP 주소 하나"로 끝나고 Kafka 관련 변경은 서버 한 곳에서 처리한다. 명세서의 아키텍처도 이 구조다.

왜 브로커 ack를 기다린 뒤에 200을 주는가 (at-least-once)

Fluent Bit은 2xx가 아니면 재전송한다. 수집 서버가 Kafka에 쓰기 전에 200을 주면 그 사이 서버가 죽을 때 로그가 사라진다. ack를 기다리면 유실은 없지만, ack 직후 응답 전에 죽으면 같은 묶음이 두 번 온다. 그래서 "유실 0, 중복 허용"을 택하고 중복은 멱등키로 저장소에서 걸러낸다. 로그 파이프라인에서는 중복이 유실보다 훨씬 싸다.

왜 메시지 키가 device_id인가

같은 키는 항상 같은 파티션으로 간다. 그래서 한 장비의 로그는 발생 순서대로 한 파티션에 쌓이고, 컨슈머도 그 순서대로 읽는다. 장애 분석에서 "이 차량에서 무슨 일이 순서대로 일어났나"가 핵심 질문이므로 장비 단위 순서가 중요하다. 키를 없애면 처리량은 비슷하지만 순서가 깨진다(워크북 C7 실험).

왜 수집 서버와 컨슈머가 한 프로세스에 있는가

학습 편의다. 실제 프로젝트에서는 수집 서버(쓰기)와 적재 컨슈머(읽기)를 별도 서비스로 나눠 각각 독립적으로 늘리고 재배포한다. Step 3에서 앱을 두 개 띄워 파티션이 나뉘는 것을 보고, Step 4에서 컨슈머가 ClickHouse 적재를 맡으면서 자연스럽게 역할이 분리된다.

수집 서버가 1대여도 Kafka가 필요한가 (Step 4+에서 측정)

Kafka는 서버를 늘리려고 쓰는 것이 아니라 서버와 DB 사이를 떼어 놓으려고 쓰므로 서버 대수와는 상관이 없다. 차이는 세 군데서 난다. ClickHouse는 INSERT마다 part를 만들어 작은 INSERT가 많으면 병합이 못 따라가는데, Kafka가 있으면 컨슈머가 큰 배치로 모아 넣을 수 있다. DB 장애 때 직접 적재는 로그가 장비 디스크에 흩어져 기다리고, Kafka 경유는 중앙에 쌓여 lag으로 보인다. Kafka에 원문이 남으므로 파서를 고친 뒤 다시 적재할 수 있다. 반대로 운영 요소와 지연이 늘어나는 비용이 있다. 명세서가 Kafka를 "대규모 대비" 추가 기능으로 둔 이유이며, Step 4+에서 같은 입력으로 두 경로를 재서 확인한다.

7. 지금 어디까지, 다음은 무엇

Step 2까지 구현됐다. 파일에서 Kafka까지의 수집 경로와 실제 OHT 로그 형식 파서가 코드와 문서로 있다. Step 1·2의 Spring 코드는 컴파일 검증 없이 작성됐다가 2026-10-13에 ./gradlew clean test로 컴파일과 테스트 통과를 확인했다. 아직 docker로 실행 절차를 재현하지 않았으므로 상태는 "구현 완료, 실행 검증 전"이다. result/step2의 실행 절차를 깨끗한 환경에서 재현하면 "완료"가 된다. 그 뒤에도 없는 것은 셋이다.

  • 컨슈머는 콘솔에 찍기만 하고 저장소가 없다 (Step 4).
  • 컨슈머가 하나뿐이라 파티션을 나눠 읽는 효과를 못 본다 (Step 3).
  • 브로커가 하나라 복제와 장애 복구를 못 본다 (Step 6).
