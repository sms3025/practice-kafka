# 학습자료 제작 방침: 앞으로 무엇을 어떻게 만들 것인가

> 작성: 2026-10-12. 이 문서는 `00-학습계획서.md`가 정한 단계 계획을 "어떤 자료를, 어떤 순서와 형식으로 만들 것인가"로 구체화한 것이다. 단계 계획 자체가 바뀌면 00을 먼저 고치고 이 문서의 산출물 표를 맞춘다. 저장소 전체의 구조와 읽는 순서는 `../README.md`에 있다.

## 1. 자료의 목적과 원칙

이 저장소의 산출물은 동작하는 코드가 아니라 **"왜 이렇게 짰는지"를 처음 보는 사람이 이해할 수 있게 쓴 문서**다. 코드는 그 문서의 예제다. 따라서 자료를 만들 때 지키는 원칙은 다음 넷이다.

**실행으로 검증된 것만 적는다.** 문서에 적힌 명령은 실제로 실행한 것이고, 기대 출력은 실제로 본 것이다. 수치(처리량, 지연, 디스크 사용량)는 실측치만 적고 측정 환경(장비, 건수, 설정)을 함께 적는다. 추측이면 "추측"이라고 쓴다. 이 저장소가 만들어진 세션에서는 Maven Central에 접근할 수 없어 Spring 연동 코드가 컴파일 검증 없이 작성됐는데, 그 사실을 `CLAUDE.md`에 남기고, 2026-10-13에 실제로 컴파일과 테스트를 돌린 뒤에야 문구를 고친 것이 이 원칙의 예다.

**설정 항목마다 "왜"를 적는다.** `acks=all`이라고만 쓰지 않고, 0과 1과 all이 무엇을 성공으로 보는지와 이 프로젝트가 all을 택한 이유를 쓴다. `application.properties`, `docker-compose.yml`, `fluent-bit.conf`의 주석이 이 원칙을 따르고, 교재는 그 주석을 풀어 쓴 것이다.

**바꿔 보면 무엇이 달라지는지로 가르친다.** Kafka 설정은 수백 개라 외울 수 없다. 교재는 설정 열몇 개를 골라 "값을 바꾸고 재시작하면 Kafka UI와 콘솔에서 이것이 달라진다"로 익히게 한다. 모든 새 설정은 워크북의 실험 항목이 하나 이상 따라붙는다.

**기업 프로젝트와의 대응을 끊지 않는다.** 각 단계는 명세서의 어느 항목(완충, 무손실, 멱등키, 보존 정책, 압축, 이상 탐지, 벤치마크)을 다루는지 밝힌다. 연습에서 배운 것이 실제 프로젝트의 어느 결정으로 옮겨지는지가 보여야 한다.

## 2. 단계 하나의 순환

모든 단계는 같은 순환을 돈다. 순서를 바꾸지 않는다. 문서를 먼저 쓰고 코드를 맞추면 "실행으로 검증된 것만 적는다"가 깨진다.

```
결정 질문 ─▶ 코드 ─▶ docker로 실행 ─▶ Kafka UI·로그·지표로 확인 ─▶ 문서 ─▶ 커밋
   (사용자)   (+테스트)                    (측정값 기록)              (4종 갱신)  (코드와 문서 같은 커밋)
```

### 2.1 단계를 시작하기 전: 결정 질문

새 단계를 시작하기 전에 사용자가 정해야 할 선택지를 먼저 묻는다. 결정과 근거는 `00-학습계획서.md`의 "결정 사항" 표에 날짜와 함께 적는다. 단계별로 미리 보이는 질문은 다음과 같다.

| 단계 | 물어야 할 것 |
|---|---|
| Step 3 | 파티션 수를 3에서 바꿀 것인가(장비 1,000대 기준 산정 근거를 어디까지 다룰지). `concurrency` 값. 두 번째 앱 인스턴스를 포트만 바꿔 띄울지 docker 이미지로 띄울지. 두 번째 컨슈머 그룹의 용도(통계용 등) |
| Step 4 | ClickHouse 테이블 설계: `ORDER BY` 키, 파티션 키(일 단위 등), ReplacingMergeTree의 버전 컬럼. 보존 기간 N일(압축)·M일(삭제)의 연습용 값. 배치 크기와 flush 주기. ClickHouse 접속 방식(HTTP 인터페이스 직접 호출 또는 JDBC·공식 Java 클라이언트). Grafana 대시보드 패널 범위 |
| Step 4+ | 비교할 경로의 범위(직접 적재, 비동기 INSERT, Kafka 경유, Kafka 테이블 엔진 중 어디까지). 경로마다 테이블을 따로 둘지. 부하 크기(장비 수, 줄 수, 지속 시간). ClickHouse 장애 실험의 정지 시간과 직접 적재 쪽 에이전트의 재시도 상한 |
| Step 5 | DLT 토픽 이름과 재시도 횟수·간격. 수동 ack로 바꿀지. gzip 전송을 Fluent Bit 쪽에서 켤지 Kafka 압축으로 할지, 둘 다 할지. 멱등 프로듀서와 트랜잭션 중 어디까지 다룰지 |
| Step 6 | 브로커 수(3). `min.insync.replicas`. 기존 compose와 분리할지 프로파일로 둘지. 장애 실험의 범위(브로커 1대 정지, 리더 이동, 디스크 볼륨 삭제) |
| Step 7 | 할지 말지. 집계 창(1분) 과 임계치. Streams와 ClickHouse 집계 쿼리 중 어느 쪽이 이 프로젝트에 맞는지 비교를 포함할지 |

### 2.2 코드

코드는 `../README.md` 2.4절의 패키지 책임을 지킨다. 새 책임이 생기면 패키지를 새로 만든다(Step 4의 `sink/` 등). 스키마 `LogEvent`를 바꾸면 `LogNormalizerTest`와 `study/02`를 같은 커밋에서 고친다. Lombok은 쓰지 않고 record를 쓴다. 설정은 `application.properties` 하나에 두고 항목마다 주석을 단다.

### 2.3 실행과 확인

docker로 띄우고 Kafka UI, 앱 콘솔, Fluent Bit 지표, `/api/logs/stats`로 확인한다. 이때 본 숫자와 화면이 문서의 "확인해야 할 것"이 된다. 측정이 들어가는 단계(Step 3의 리밸런스 시간, Step 4의 적재 처리량과 압축비, Step 4+의 경로별 part 수·지연·장애 복구 시간, Step 5의 압축 전후 전송량, Step 6의 장애 복구 시간)는 측정 방법을 먼저 정하고, 같은 입력(생성기 시드와 대수, 건수)으로 전후를 비교한다.

### 2.4 문서 4종 갱신

단계 하나가 끝나면 네 폴더를 모두 손본다. 어느 하나를 빼먹지 않도록 표로 둔다.

| 폴더 | 반드시 | 필요하면 |
|---|---|---|
| `result/` | `stepN-*.md` 신규 | 이전 단계 문서의 "다음 단계로 넘어가기 전 실험"이 이번 단계로 흡수됐으면 그 사실 표기 |
| `study/` | 새 장 신규, `06-실습-워크북.md`에 절 추가, `00-학습-가이드.md` 읽는 순서 표에 행 추가 | 기존 장에서 "Step N에서 한다"고 미뤄 둔 문장을 새 장 링크로 교체 |
| `practice/` | 워크북에 새로 붙인 절과 같은 이름의 따라 하기 파일 신규, `practice/README.md`의 파일 표와 검증 상태(7절) 갱신 | 앞 파일의 "다 됐으면"이 새 파일을 가리키게 수정 |
| `concepts/` | 새 도구가 들어오면 `03-주변-도구.md`에 절 추가 | 새 Kafka 개념(복제, ISR, 트랜잭션 등)은 `01-kafka-basics.md`, 새 Spring 추상화(배치 리스너, 에러 핸들러)는 `02-spring-kafka.md` |
| `plan/` | `00-학습계획서.md`의 단계 상태("완료"/"현재 단계")와 결정 사항 표 | 이 문서의 산출물 표에서 예정 파일명이 바뀌었으면 수정 |

그리고 루트 `README.md`의 진행 상황 표와 빠른 시작(새 컨테이너나 포트가 생겼으면)을 갱신하고, `../README.md`의 2.1절 구성도와 2.5절 "지금 어디까지"를 맞춘다.

### 2.5 커밋

코드와 문서를 같은 커밋에 넣는다. 커밋 메시지는 `Step N: 한 줄 요약` 형식에 본문으로 만든 것과 문서 목록을 적는다. 커밋 전 `git status`로 `tools/`, `docker/devices/`, `*.pyz`, `사용법.md`가 보이지 않는지 확인한다.

## 3. 문서 4종의 형식

### 3.1 `result/stepN-*.md`: 단계 기록

절 순서를 고정한다. "만든 것"은 파일 표로, "설계에서 눈여겨볼 것"은 결정 하나당 한 문단으로 쓰고 문단 첫 문장을 굵게 해 결정을 선언한다. "실행 절차"는 그대로 복사해 실행할 수 있는 명령 블록 하나에 번호 주석을 단다. "확인해야 할 것"은 콘솔 로그, Kafka UI 화면, 지표 값을 구체적으로 적는다. "배운 점"은 그 단계에서 처음 분명해진 것 한두 가지를 산문으로 쓴다. 대안을 검토했으면 "결정 비교" 절을 끝에 둔다.

```
# Step N. 제목 결과
## 만든 것                 (구조도 + 파일 표)
## 설계에서 눈여겨볼 것     (결정별 한 문단)
## 실행 절차               (명령 블록)
## 확인해야 할 것          (기대 로그·화면·수치)
## 실험 (해볼 것)          (장애·설정 변경 실험)
## 테스트                  (./gradlew test 와 각 테스트가 고정하는 것)
## 배운 점
## 결정 비교 (있으면)
```

### 3.2 `study/NN-*.md`: 교재의 장

장 하나는 하나의 주제를 "설명 → 코드 → 실습 → 확인 질문" 순서로 다룬다. 설명은 왜 이 개념이 이 프로젝트에 필요한지에서 시작한다. 코드는 저장소의 실제 코드를 짧게 인용하고 파일 경로를 적는다. 실습은 워크북으로 보내되 장 안에서도 "바꿔 보면 이렇게 된다"를 한 가지는 보여 준다. 확인 질문은 셋에서 다섯 개, 답이 본문에 직접 나오지 않고 실행해 봐야 알 수 있는 것을 하나 이상 넣는다. 자주 나는 오류가 새로 생기면 `01`의 표에 추가한다.

장 번호는 추가 순서대로 붙인다. 번호를 바꿔 끼워 넣지 않는다. 예정 번호는 4절 표에 있다.

### 3.3 `concepts/`: 개념 사전

코드와 무관하게 읽을 수 있어야 한다. 한 항목은 "무엇인가 → 왜 이 프로젝트에 들어왔는가 → 이 프로젝트에서 한 번에 외울 것"으로 끝낸다. 도구는 03, Kafka 자체는 01, Spring 추상화는 02에 둔다. 비교가 필요한 선택(ClickHouse 대 Elasticsearch처럼)은 표로 마무리하고, 실측치가 생기면 그 표의 빈칸을 채운다.

### 3.4 `plan/`: 계획과 결정

00은 단계 계획과 결정 이력, 01(이 문서)은 제작 방침이다. 결정 사항 표에는 날짜, 결정, 근거 세 칸을 채운다. 번복된 결정은 지우지 않고 새 행으로 번복 사실을 적는다.

### 3.5 문체

한국어 평서문("~한다")으로 쓴다. 존댓말과 이모지는 쓰지 않는다. 산문이 기본이고 리스트는 병렬 항목에만 쓴다. 영어 용어는 처음 나올 때 한국어 설명을 붙이고 이후에는 원어를 쓴다. 코드와 명령은 fenced block에 넣고 산문 안에서는 파일명이나 설정 키 하나만 인라인으로 적는다. 인터넷 자료가 Spring Boot 3.x 기준이라 다른 부분(`spring-boot-starter-webmvc`, `JacksonJsonSerializer`)은 그때마다 명시한다.

### 3.6 대외비

문서, 테스트, 주석, 커밋 메시지에 생성 로그의 실제 내용(장비 상태 메시지, MAC/IP, 좌표)을 넣지 않는다. 형식 설명이 필요하면 `LogNormalizerTest`의 예시처럼 형식만 같은 가짜 문장을 만든다. 생성기의 옵션 이름은 적어도 되지만 사용법 문서를 옮겨 적지 않는다.

### 3.7 `practice/`: 따라 하는 실습

워크북(`study/06`)은 체크리스트와 기록지로 짧게 두고, 같은 항목 번호로 손 연습 절차를 `practice/NN-*.md`에 풀어 쓴다. 파일 하나가 워크북 절 하나에 대응한다. 항목은 "왜 하는가 → 할 것 → 보여야 하는 것 → 안 될 때 → 생각해 볼 것" 다섯 칸으로 쓴다. "할 것"의 명령은 사용자 환경(Windows PowerShell, 프로젝트 루트)에서 복사해 그대로 실행되는 형태로 적는다. HTTP는 `Invoke-RestMethod`, 여러 줄 본문은 `@' '@`를 쓴다. "보여야 하는 것"에는 실측이면 날짜와 함께 실제 출력을 적는다. 이론상 예상이면 "아직 실측하지 않았다"고 밝힌다. 파일 첫머리에 "시작 전 상태"를, 끝에 "다 됐으면"(워크북 기록과 다음 파일)을 둔다.

## 5. 학습자가 하는 일

교재는 읽는 것으로 끝나지 않는다. 학습자는 다음을 저장소에 남긴다.

- 워크북의 체크박스를 채우고 빈칸에 측정값을 적는다. 커밋해도 된다. 이것이 "이 환경에서 이 값이 나왔다"는 기록이 된다.
- 확인 질문의 답을 각 장 끝에 "내 답" 절로 적는다. 틀린 답을 지우지 않고 나중에 고친 이유를 덧붙인다.
- 새로 겪은 오류와 해결을 `study/01` 7절 표에 추가한다.
- 문서가 코드와 다르거나 설명이 부족한 곳을 발견하면 그 자리에서 고친다. 문서의 정확성은 코드의 정확성과 같은 무게다.

## 6. 단계 완료 체크리스트

단계를 "완료"로 표시하기 전에 아래를 모두 확인한다.

- [ ] 문서에 적힌 수치는 모두 실측이고 측정 환경이 적혀 있다.
- [ ] 새 설정 항목마다 `application.properties` 주석과 교재 설명이 있고, 워크북 실험이 하나 이상 있다.
