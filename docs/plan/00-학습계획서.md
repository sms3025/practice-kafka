# Apache Kafka 학습 계획서

> 목표: 기업 연계 프로젝트 **Log Collector**(1,000대 이상 다중 하드웨어 디바이스 통합 로그 수집·저장·조회)에 Kafka를 "완충(buffer)" 계층으로 적용하기 전에, 같은 구조의 작은 데모를 직접 만들어 돌려 보면서 핵심 개념을 몸으로 익힌다.
> 방식: 단계마다 "코드 작성 → docker로 실행 → Kafka UI/로그로 동작 확인 → docs/result에 정리"를 반복한다.
>
> 개정 이력: 2026-10-12 명세서 반영 (저장소 Elasticsearch → ClickHouse, Fluent Bit 수집 경로 추가, 공통 스키마 적용)

## 1. 기업 프로젝트 명세서 요약 (연습 프로젝트가 따라갈 기준)

명세서의 아키텍처는 `.txt 로컬 로그 → Fluent Bit 수집 에이전트(설정 기반) → HTTP 전송 → 수집 서버(Java/Spring) → ClickHouse 적재 → 자체 대시보드`이며, Kafka는 "대규모 대비 완충(메시지 큐 등)" 추가 기능으로 수집 서버와 저장소 사이에 들어간다. 로그 공통 JSON 스키마는 `device_id`(장비 식별자), `source`(원본 파일 경로), `event_time`(원문에서 추출한 이벤트 시각, 필수 정규화), `collected_at`(에이전트 수집 시각), `offset`(무중복 멱등키 구성 요소), `raw`(원문 원형, 전문 검색 대상)의 여섯 필드다. 추가 기능으로 본문 상세 파싱(level 등), 전송 최적화(압축), 중복·노이즈 필터링, 이상 탐지·알림, 보존 정책(N일 후 압축 보관, M일 후 삭제)이 있다. 운영 환경은 망분리 Full-Offline이며 산출물에 기술 스택 비교·벤치마크(수집/완충/압축)가 포함된다.

연습 프로젝트는 이 중 Kafka와 직접 맞닿는 부분(수집 서버 → Kafka → 적재)을 중심으로 하되, 앞뒤 구성요소(Fluent Bit, ClickHouse)를 실제 도구로 붙여 전체 흐름이 한 번에 돌아가게 한다.

## 3. 시나리오

기업 제공 OHT 차량 로그 생성기가 `docker/devices/<장비ID>/...`에 실제 형식(OHTHandlerLogger 계열 .txt, UILogger 계열 .log, 1시간 단위 파일)으로 로그를 쌓는다. 생성기가 없는 환경을 위해 연습용 단순 시뮬레이터(`docker/devices/sim/dev-NNNN.log`, `yyyy-MM-dd HH:mm:ss.SSS [LEVEL] message`)도 둔다. Fluent Bit이 이 파일들을 tail해 HTTP로 Spring 수집 서버에 보내고, 수집 서버는 명세서 스키마로 정규화(device_id 추출, event_time UTC 변환, level 파싱)한 뒤 `app-logs` 토픽에 `device_id`를 키로 발행한다. 컨슈머 그룹이 이를 읽어 ClickHouse에 적재하고 Grafana로 본다.

```
docker/devices/*.log ─Fluent Bit(tail→http)─▶ POST /ingest/fluentbit ─▶ [app-logs: 3 partitions, key=device_id]
                                                 (LogNormalizer)              ├─▶ log-printer 그룹 (콘솔)         Step 1~3
                                                                               ├─▶ clickhouse-sink 그룹 → ClickHouse → Grafana   Step 4
                       (비교용) Fluent Bit ─▶ POST /ingest/direct ─▶ ClickHouse (Kafka 없음)                    Step 4+
                                                                               └─▶ Kafka Streams: 장비별 1분 ERROR 집계   Step 7(선택)
```

Fluent Bit을 거치지 않고 Kafka에 직접 밀어 넣는 부하 생성기(`POST /api/logs/generate`)도 두어, 수집 경로의 병목과 Kafka 자체 처리량을 분리해 볼 수 있게 한다.

### Step 4. ClickHouse 적재 + Grafana — 완료 (2026-10-19)
`clickhouse-sink` 컨슈머 그룹이 배치 리스너로 로그를 묶어 ClickHouse에 bulk INSERT한다. 멱등키로 중복을 제거하는 방법(ReplacingMergeTree)과 TTL 보존 정책을 적용한다. Grafana에서 장비별/레벨별 대시보드를 만든다.

ClickHouse는 이 저장소에서 처음 다루는 데이터베이스이므로, 한 번에 붙이지 않고 네 묶음으로 나눠 천천히 간다. 각 묶음은 그 자체로 돌려 보고 확인한 뒤 다음으로 넘어간다.

1. **ClickHouse 단독 체험.** 컨테이너만 띄우고 Kafka 없이 손으로 INSERT와 SELECT를 해 본다. 브라우저 SQL 창(`http://localhost:8123/play`)과 `clickhouse-client`를 쓴다. INSERT 한 번이 part 하나를 만들고 백그라운드 병합이 part를 합친다는 것을 `system.parts`와 `system.part_log`로 직접 본다. 열 지향 저장과 압축비도 여기서 확인한다.
2. **테이블 설계.** 명세서 스키마를 DDL로 옮긴다. `ORDER BY`(정렬 키), `PARTITION BY`(파티션 키), `LowCardinality`, `DateTime64`의 의미를 하나씩 익힌다. 정렬 키를 멱등키 `(device_id, source, offset)`로 두면 ReplacingMergeTree가 중복을 지운다는 것을, 같은 행을 두 번 넣어 보고 확인한다. TTL 보존 정책을 선언한다.
3. **Spring 배치 리스너로 적재.** `sink/` 패키지에 `clickhouse-sink` 그룹의 배치 리스너를 만든다. `max.poll.records`와 `fetch.max.wait.ms`로 배치 크기를 조절하고, INSERT가 성공한 뒤에 오프셋을 커밋하는 순서와 ClickHouse가 죽었을 때 재시도하는 방법을 다룬다.
4. **Grafana.** ClickHouse 데이터 소스를 붙이고 장비별·레벨별 패널을 만든다.

- 배우는 것: MergeTree의 part와 병합, 정렬 키와 파티션 키, 배치 소비, 처리량 vs 지연, 외부 저장소 실패 시 오프셋 커밋 전략, 압축비 측정

2026-10-19에 네 묶음을 모두 진행했다. 적재 코드는 `kafka-load-test` 브랜치의 것을 공부용으로 다듬어 가져왔고(client-v2, RowBinaryWithDefaults), 적재 처리량은 그 브랜치의 측정을 인용해 다시 재지 않았다. 새로 잰 것은 중복 없는 실제 로그의 저장 크기(LZ4와 ZSTD(9))다. 실제 로그 35만 줄의 끝에서 끝 적재, 중복 제거, 1분 TTL, ClickHouse 장애 중 2만 줄의 무손실을 확인했다. 기록은 `../result/step4-clickhouse-적재.md`, `../result/benchmark-storage.md`, 교재는 `study/08`~`10`. 같은 날 깨끗한 환경에서 H절을 재현했다.

### Step 4+. 적재 경로 비교: Kafka 경유 vs 직접 적재 — 완료 (2026-10-19)
Step 4로 ClickHouse 적재가 돌아가면, 같은 입력을 여러 적재 경로로 동시에 흘려 결과를 비교한다. 답하려는 질문은 "수집 서버가 1대뿐이어도 Kafka를 거치는 것과 ClickHouse에 바로 넣는 것이 다른가"이다. 명세서는 기본 아키텍처를 직접 적재로 두고 Kafka를 "대규모 대비" 추가 기능으로 두었으므로, 이 단계의 측정값이 Kafka 도입 여부의 근거가 된다.

비교할 경로는 넷이다.

| 경로 | 흐름 | INSERT 단위 |
|---|---|---|
| 직접 적재 | Fluent Bit → `/ingest/direct` → ClickHouse | HTTP 묶음 하나마다 INSERT 한 번 |
| 직접 적재 + 비동기 INSERT | 위와 같되 ClickHouse의 `async_insert`를 켬 | ClickHouse 서버가 모아서 기록 |
| Kafka 경유 (Spring) | Fluent Bit → `/ingest/fluentbit` → Kafka → `clickhouse-sink` 배치 리스너 → ClickHouse | poll 한 번마다 INSERT 한 번 |
| Kafka 테이블 엔진 | Kafka → ClickHouse가 토픽을 직접 구독 | ClickHouse가 정한 블록 단위 |

공정한 비교를 위해 입력과 저장 구조를 고정한다. 같은 파일을 읽는 Fluent Bit 에이전트를 경로마다 따로 두고, 각자 읽은 위치와 디스크 버퍼를 가지게 한다. 구조가 똑같은 테이블을 경로마다 하나씩 만들고, 행이 들어간 시각을 기록하는 `inserted_at` 컬럼을 둔다. 이 설계는 compose 프로필(`compare`)과 앱 설정 `app.compare.enabled`로 켜고 꺼서, 기존 단계의 실행은 그대로 둔다. Kafka 경유 경로의 처리량 한계는 브랜치에서 잰 값을 인용하고, 같은 부하에서 경로가 바꾸는 것만 새로 잰다.

실험은 셋이다.

1. **평시 부하.** 시뮬레이터로 장비 100대 × 1대당 초당 60줄 × 10분(360만 줄)을 흘린다(사용자 선택). 경로별로 INSERT 횟수와 INSERT당 행 수, 새로 생긴 part 수와 병합 횟수(`system.part_log`), 살아 있는 part 수(`system.parts`), 수집에서 저장까지의 지연(`inserted_at - collected_at`)을 잰다. 필요하면 테이블의 `parts_to_throw_insert`를 일부러 낮춰 직접 적재가 "Too many parts"로 거부되는 모습을 본다.
2. **ClickHouse 장애.** 부하 중에 ClickHouse를 몇 분 멈췄다 켠다. 직접 적재는 밀린 로그가 장비 쪽 디스크 버퍼에 쌓이고 에이전트 재시도 간격에 따라 복구된다. Kafka 경유는 Kafka에 쌓이고 lag 숫자 하나로 보이며 컨슈머가 바로 따라잡는다. 두 경로의 복구 시간과 유실 여부를 비교한다.
3. **재처리.** 파서를 고친 뒤 이미 들어간 로그를 다시 적재해야 하는 상황을 가정한다. Kafka 경유는 컨슈머 오프셋을 되돌려 다시 넣을 수 있고, 직접 적재는 원본을 다시 받을 방법이 없다는 것을 확인한다.

- 배우는 것: ClickHouse가 큰 배치를 원하는 이유, 완충 계층이 장비 디스크에 있을 때와 중앙(Kafka)에 있을 때의 차이, Kafka가 지연과 운영 요소를 늘리는 비용, 측정으로 기술 선택을 정당화하는 방법
- 산출물: 명세서가 요구하는 "기술 스택 비교·벤치마크" 중 완충 계층 항목의 근거 문서

2026-10-19에 세 실험을 모두 했다. 새 part는 직접 적재 55,838개, 비동기 INSERT 1,669개, Kafka 경유 1,192개, Kafka 테이블 엔진 77개였고 저장 지연 p50은 0.8초, 1.0초, 1.1초, 4.8초였다. ClickHouse 3분 정지 동안 Kafka 경유는 수집 서버가 계속 200을 돌려줬고(lag 최대 112만), 직접 적재는 500을 1만 번 안팎 돌려주며 에이전트에 청크가 2,000개 안팎 쌓였다. 다시 켠 뒤 따라잡기는 17~39초였고 넷 다 유실과 진짜 중복이 없었다. 재처리는 오프셋을 되돌려 648만 행을 82초에 다시 넣었다. 측정 중에 Fluent Bit 쪽 문제 둘을 찾았다. 디스크 버퍼에 청크 몇 개가 남아 재시작 전까지 보내지지 않는 것, 그리고 4.2.8이 재시작 뒤 `Offset_Key`를 0부터 다시 세어 멱등키가 겹치는 것이다. 기록은 `../result/step4plus-적재경로-비교.md`, `../result/benchmark-ingest-path.md`, 교재는 `study/11`.

### Step 5. 신뢰성: 멱등 프로듀서, 재시도, Dead Letter Topic
일부러 예외를 던지는 컨슈머로 `DefaultErrorHandler`의 재시도와 DLT(`app-logs.DLT`)를 본다. `enable.idempotence`, 수동 ack, at-most/at-least/exactly-once 정리. 전송 최적화(Fluent Bit gzip 압축)도 여기서 켠다.

### Step 6. 3브로커 클러스터와 복제
`docker/docker-compose.cluster.yml`로 브로커 3개, `replicas=3`, `min.insync.replicas=2`. 브로커 하나를 죽여도 수집이 계속되는지, 리더가 어떻게 옮겨가는지 본다.

### Step 7 (선택). Kafka Streams 실시간 집계 / 이상 탐지
장비별 1분당 ERROR 건수 집계, 임계치 초과 시 알림 토픽 발행. 명세서의 "이상 탐지 및 알림"의 가장 단순한 형태.
