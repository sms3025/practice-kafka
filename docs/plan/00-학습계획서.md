# Apache Kafka 학습 계획서

> 목표: 기업 연계 프로젝트 **Log Collector**(1,000대 이상 다중 하드웨어 디바이스 통합 로그 수집·저장·조회)에 Kafka를 "완충(buffer)" 계층으로 적용하기 전에, 같은 구조의 작은 데모를 직접 만들어 돌려 보면서 핵심 개념을 몸으로 익힌다.
> 방식: 단계마다 "코드 작성 → docker로 실행 → Kafka UI/로그로 동작 확인 → docs/result에 정리"를 반복한다.
>
> 개정 이력: 2026-10-12 명세서 반영 (저장소 Elasticsearch → ClickHouse, Fluent Bit 수집 경로 추가, 공통 스키마 적용)

## 1. 기업 프로젝트 명세서 요약 (연습 프로젝트가 따라갈 기준)

명세서의 아키텍처는 `.txt 로컬 로그 → Fluent Bit 수집 에이전트(설정 기반) → HTTP 전송 → 수집 서버(Java/Spring) → ClickHouse 적재 → 자체 대시보드`이며, Kafka는 "대규모 대비 완충(메시지 큐 등)" 추가 기능으로 수집 서버와 저장소 사이에 들어간다. 로그 공통 JSON 스키마는 `device_id`(장비 식별자), `source`(원본 파일 경로), `event_time`(원문에서 추출한 이벤트 시각, 필수 정규화), `collected_at`(에이전트 수집 시각), `offset`(무중복 멱등키 구성 요소), `raw`(원문 원형, 전문 검색 대상)의 여섯 필드다. 추가 기능으로 본문 상세 파싱(level 등), 전송 최적화(압축), 중복·노이즈 필터링, 이상 탐지·알림, 보존 정책(N일 후 압축 보관, M일 후 삭제)이 있다. 운영 환경은 망분리 Full-Offline이며 산출물에 기술 스택 비교·벤치마크(수집/완충/압축)가 포함된다.

연습 프로젝트는 이 중 Kafka와 직접 맞닿는 부분(수집 서버 → Kafka → 적재)을 중심으로 하되, 앞뒤 구성요소(Fluent Bit, ClickHouse)를 실제 도구로 붙여 전체 흐름이 한 번에 돌아가게 한다.

## 3. 시나리오

20대(설정으로 조절)의 가상 장비가 각자 `docker/devices/dev-NNNN.log`에 `yyyy-MM-dd HH:mm:ss.SSS [LEVEL] message` 형식으로 로그를 쌓는다. 일부 줄은 시각이 없는 지저분한 로그다. Fluent Bit이 이 파일들을 tail해 HTTP로 Spring 수집 서버에 보내고, 수집 서버는 명세서 스키마로 정규화(device_id 추출, event_time UTC 변환, level 파싱)한 뒤 `app-logs` 토픽에 `device_id`를 키로 발행한다. 컨슈머 그룹이 이를 읽어 ClickHouse에 적재하고 Grafana로 본다.

```
docker/devices/*.log ─Fluent Bit(tail→http)─▶ POST /ingest/fluentbit ─▶ [app-logs: 3 partitions, key=device_id]
                                                 (LogNormalizer)              ├─▶ log-printer 그룹 (콘솔)         Step 1~3
                                                                               ├─▶ clickhouse-sink 그룹 → ClickHouse → Grafana   Step 4
                                                                               └─▶ Kafka Streams: 장비별 1분 ERROR 집계   Step 6(선택)
```

Fluent Bit을 거치지 않고 Kafka에 직접 밀어 넣는 부하 생성기(`POST /api/logs/generate`)도 두어, 수집 경로의 병목과 Kafka 자체 처리량을 분리해 볼 수 있게 한다.

## 4. 단계별 계획

각 단계는 독립적으로 실행·확인할 수 있고, 끝나면 `docs/result/stepN-*.md`에 "무엇을 만들었고, 어떻게 확인했고, 무엇을 배웠는지"를 적는다.

### Step 0. 환경 구성 — 완료
단일 브로커(KRaft) + Kafka UI를 docker compose로 띄우고 CLI로 토픽을 만들어 메시지를 주고받는다.

### Step 1. Producer / Consumer 기본 — 완료
`KafkaTemplate`로 JSON 발행, `@KafkaListener`로 소비. 토픽/파티션/오프셋, 키의 역할, 직렬화, 비동기 전송, acks.

### Step 2. 명세서 스키마 + Fluent Bit 수집 경로 — 현재 단계
`LogEvent`를 명세서 스키마로 바꾸고 `LogNormalizer`로 정규화한다. Fluent Bit 컨테이너가 장비 로그 파일을 tail해 `/ingest/fluentbit`로 보내고, 수집 서버가 Kafka에 넣는다. 장비 로그 시뮬레이터로 파일을 만든다.

- 배우는 것: at-least-once와 멱등키의 관계, "수집 서버는 Kafka에 넣고 끝낸다"는 완충의 의미, 에이전트 재시도와 HTTP 응답 코드의 계약, 시각 정규화

### Step 3. 파티션과 컨슈머 그룹
`concurrency`를 올려 컨슈머 스레드를 늘리고, 앱을 포트만 바꿔 두 번 띄워 리밸런스를 본다. 다른 groupId 컨슈머를 추가해 그룹 간 브로드캐스트를 확인한다. 장비 1,000대 기준 파티션 수를 어떻게 정할지 정리한다.

### Step 4. ClickHouse 적재 + Grafana
`clickhouse-sink` 컨슈머 그룹이 배치 리스너로 로그를 묶어 ClickHouse에 bulk INSERT한다. 멱등키로 중복을 제거하는 방법(ReplacingMergeTree)과 TTL 보존 정책을 적용한다. ClickHouse Kafka 테이블 엔진으로 "Spring 없이 직접 구독"하는 방식도 만들어 둘을 비교한다. Grafana에서 장비별/레벨별 대시보드를 만든다.

- 배우는 것: 배치 소비, 처리량 vs 지연, 외부 저장소 실패 시 오프셋 커밋 전략, 압축비 측정

### Step 5. 신뢰성: 멱등 프로듀서, 재시도, Dead Letter Topic
일부러 예외를 던지는 컨슈머로 `DefaultErrorHandler`의 재시도와 DLT(`app-logs.DLT`)를 본다. `enable.idempotence`, 수동 ack, at-most/at-least/exactly-once 정리. 전송 최적화(Fluent Bit gzip 압축)도 여기서 켠다.

### Step 6. 3브로커 클러스터와 복제
`docker/docker-compose.cluster.yml`로 브로커 3개, `replicas=3`, `min.insync.replicas=2`. 브로커 하나를 죽여도 수집이 계속되는지, 리더가 어떻게 옮겨가는지 본다.

### Step 7 (선택). Kafka Streams 실시간 집계 / 이상 탐지
장비별 1분당 ERROR 건수 집계, 임계치 초과 시 알림 토픽 발행. 명세서의 "이상 탐지 및 알림"의 가장 단순한 형태.
