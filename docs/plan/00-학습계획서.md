# Apache Kafka 학습 계획서

> 목표: 기업 연계 프로젝트(대용량 로그 처리)에 Kafka를 적용하기 전에, 작은 데모를 직접 만들어 돌려 보면서 핵심 개념을 몸으로 익힌다.
> 방식: 단계마다 "코드 작성 → docker로 실행 → Kafka UI/로그로 동작 확인 → docs/result에 정리"를 반복한다.

## 1. 기술 스택

| 구분 | 선택 | 비고 |
|---|---|---|
| 언어 / 런타임 | Java 25 | Gradle toolchain + foojay 플러그인이 JDK를 자동 다운로드 (로컬 설치 불필요) |
| 프레임워크 | Spring Boot 4.1.x, Spring for Apache Kafka 4.1.x | Jackson 3 기반 `JacksonJsonSerializer` 사용 |
| 빌드 | Gradle 9.8 (Wrapper) | `./gradlew` 로 실행, 설정은 `application.properties` |
| 브로커 | apache/kafka 4.2 (KRaft 모드) | ZooKeeper 없음 |
| 모니터링 | Kafbat Kafka UI | 토픽/파티션/컨슈머 그룹/메시지 시각 확인 |
| 저장소 | Elasticsearch 9.x + Kibana | Step 4에서 추가 |
| 인프라 | Docker Compose | 단일 브로커용 / 3브로커 클러스터용 파일 분리 |

## 2. 시나리오: 다중 서비스 애플리케이션 로그 수집 파이프라인

여러 서비스(order-api, payment-api, inventory-api, user-api, notification-worker)가 여러 호스트에서 쏟아내는 로그를 Kafka로 모아 처리한다. 로그 한 건은 `LogEvent(id, timestamp, service, level, message, host)` 구조이며, 메시지 키는 `service` 이름이다. 기업 명세서를 받으면 로그 형식과 처리 요구사항을 여기에 맞춰 조정한다.

```
[REST / 생성기] --produce--> [topic: app-logs (3 partitions)] --consume--> [log-printer 그룹]  (Step 1~3)
                                                              --consume--> [es-indexer 그룹] → Elasticsearch → Kibana (Step 4)
                                                              --streams--> [error-count-per-minute]  (Step 6, 선택)
```

## 3. 단계별 계획

각 단계는 독립적으로 실행·확인할 수 있고, 끝나면 `docs/result/stepN-*.md`에 "무엇을 만들었고, 어떻게 확인했고, 무엇을 배웠는지"를 적는다.

### Step 0. 환경 구성
단일 브로커(KRaft) + Kafka UI를 docker compose로 띄우고, CLI(`kafka-topics.sh`, `kafka-console-producer.sh`, `kafka-console-consumer.sh`)로 토픽을 만들어 메시지를 주고받아 본다. Spring 없이 Kafka 자체의 감을 먼저 잡는 단계다.

- 산출물: `docker/docker-compose.yml`, `docs/concepts/01-kafka-basics.md`
- 확인: Kafka UI(localhost:8085)에서 브로커 1개, 토픽 목록 확인

### Step 1. Producer / Consumer 기본  ← 현재 단계
Spring Boot에서 `KafkaTemplate`로 JSON 메시지를 발행하고 `@KafkaListener`로 소비한다. REST 엔드포인트와 무작위 로그 생성기로 메시지를 넣는다.

- 산출물: `LogEvent`, `LogEventProducer`, `LogEventConsumer`, `LogController`, `LogGenerator`, `KafkaTopicConfig`
- 확인: `POST /api/logs/generate?count=1000` → 콘솔 로그에 파티션/오프셋 출력, Kafka UI에서 메시지 내용 확인
- 배우는 것: 토픽/파티션/오프셋, 키의 역할, 직렬화, 비동기 전송, acks

### Step 2. 파티션과 컨슈머 그룹
`concurrency`를 올려 컨슈머 스레드를 늘리고, 같은 앱을 포트만 바꿔 두 번 띄워 파티션이 재분배(rebalance)되는 과정을 본다. 다른 groupId 컨슈머를 추가해 "같은 메시지를 두 그룹이 각각 받는" 것을 확인한다.

- 확인: Kafka UI → Consumers 탭에서 파티션 할당과 lag 변화 관찰
- 배우는 것: 파티션 = 병렬성 단위, 그룹 내 분배 vs 그룹 간 브로드캐스트, 리밸런스, consumer lag

### Step 3. 신뢰성: 멱등 프로듀서, 재시도, Dead Letter Topic
일부러 예외를 던지는 컨슈머를 만들어 `DefaultErrorHandler`의 재시도(backoff)와 DLT(`app-logs.DLT`) 전송을 본다. 프로듀서는 `enable.idempotence=true`, 컨슈머는 수동 ack(`MANUAL_IMMEDIATE`)로 바꿔 "최소 한 번(at-least-once)"의 의미를 정리한다.

- 배우는 것: at-most/at-least/exactly-once, 오프셋 커밋 시점, poison pill 처리

### Step 4. Elasticsearch 적재 + Kibana
`es-indexer` 컨슈머 그룹이 배치 리스너(`batch=true`)로 로그를 묶어 Elasticsearch bulk 색인한다. Kibana에서 data view를 만들어 레벨별/서비스별 로그를 검색·시각화한다.

- 산출물: `docker/docker-compose.elastic.yml`, `LogDocument`, `LogIndexer`
- 배우는 것: 배치 소비, 처리량 vs 지연, 외부 저장소 연동 시 실패 처리

### Step 5. 3브로커 클러스터와 복제
`docker/docker-compose.cluster.yml`로 브로커 3개를 띄우고 `replicas=3`, `min.insync.replicas=2`로 토픽을 만든다. 브로커 하나를 `docker stop` 해도 발행/소비가 계속되는지, 리더가 어떻게 옮겨가는지 Kafka UI로 본다.

- 배우는 것: 리더/팔로워, ISR, `acks=all`의 실제 의미, 가용성과 내구성의 트레이드오프

### Step 6 (선택). Kafka Streams로 실시간 집계
서비스별 1분당 ERROR 건수를 집계해 별도 토픽으로 내보낸다.
