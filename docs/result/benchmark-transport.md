# 부하 테스트 결과: 로그는 어디에서 먼저 밀리는가

> 측정 2026-10-16, 브랜치 `kafka-load-test`. 이 브랜치는 공부 진도와 별개로 기업 프로젝트의 전송 구간에서 어디가 먼저 막히는지를 보는 곳이다. 수치는 모두 아래 2절의 PC에서 한 번씩 잰 실측이다. 반복 측정은 하지 않았으므로 계단 하나의 값에는 수 퍼센트의 잡음이 있다. 추정은 추정이라고 밝혔다. 전날의 Kafka 처리량 측정(`benchmark-kafka-throughput.md`)은 앱을 호스트에서 띄워 Docker Desktop 포트 전달에 막혔는데, 이번에는 모든 구간을 docker 네트워크 안에 두어 그 천장을 없앴다.

## 먼저 읽을 결론

**이 노트북에서 1,000대 분량의 로그를 받아 ClickHouse에 저장하는 데 성공했다. 지금 설정으로는 2,000대 분량까지 시험 기준을 통과했고, 3,000대 분량부터 기준을 통과하지 못했다.** 여기서 대수는 실제 장비 수가 아니라, 테스트 도구가 만든 로그 양을 장비 수로 환산한 값이다.

장비가 늘어날 때 먼저 밀린 곳은 수집 서버였다. 수집 서버는 요청을 받으면 로그를 Kafka에 보내고, Kafka가 “받았다”는 응답을 줄 때까지 기다린다. 이 기다림 동안 요청을 처리할 작업자도 묶여 있다. CPU에 여유가 있어도 새 요청을 받을 작업자가 부족해질 수 있다는 뜻이다. 이것이 주요 원인이라는 해석은 비교 실험으로 뒷받침했지만, 작업자가 모두 바빴는지를 직접 측정하지는 않았다.

효과가 컸던 변경은 **로그를 더 크게 묶어 보내는 것**이었다. 같은 로그 양이라도 파일마다 따로 요청하는 대신 장비별로 모아 보내자, 수집 구간만 잰 실험에서는 5,000대 분량까지 통과했다. 전체 저장 경로가 5,000대까지 통과했다는 뜻은 아니다.

결과만 이해하려면 아래 용어와 요약 표를 읽고 7절로 넘어가면 된다. 2~6절은 측정 조건과 다시 실행하는 방법이다. 원인 해석은 8절, 기업 프로젝트에 적용할 때 생각할 점은 11절에 있다. 전날 측정과 비교하려면 [Kafka 처리량 결과](benchmark-kafka-throughput.md)를 본다.

## 표를 읽는 데 필요한 말

| 표현 | 쉬운 뜻 |
|---|---|
| 처리량, `줄/s`, `행/s` | 1초 동안 처리한 로그 수다. 입력에서는 줄, ClickHouse에 저장한 뒤에는 행이라고 부른다 |
| 요청, `req/s` | 장비가 서버로 보내는 HTTP 묶음과 초당 묶음 수다. 요청 하나에 로그 여러 줄이 들어가므로 요청 수와 로그 줄 수는 다르다 |
| 목표·실제·달성률 | 보내려던 양, 실제 처리한 양, 둘의 비율이다. 목표가 초당 10만 줄인데 실제가 8만 줄이면 달성률은 80%다 |
| p50·p99 | p50은 절반이 이 시간 안에 끝났다는 뜻이고, p99는 100건 중 약 99건이 이 시간 안에 끝났다는 뜻이다. p99는 가장 느린 1건의 최대 시간은 아니다 |
| ms | 1,000ms가 1초다. 100ms는 0.1초다 |
| CPU 1.0 | CPU 코어 하나를 계속 쓴 정도다. CPU 사용률 1%라는 뜻이 아니다 |
| ack | Kafka가 메시지를 받았다고 보내는 응답이다. ClickHouse 저장 완료를 뜻하지는 않는다 |
| 프로듀서·브로커·컨슈머 | 각각 Kafka에 보내는 쪽, 메시지를 받아 보관하는 Kafka 서버, Kafka에서 읽는 쪽이다. 이 실험의 컨슈머는 읽은 로그를 ClickHouse에 저장한다 |
| 정규화·직렬화 | 로그에서 시각·장비 ID 등을 뽑아 공통 형식으로 만드는 일과, 그 결과를 전송할 JSON 같은 형태로 바꾸는 일이다 |
| lag | 컨슈머가 아직 처리하지 못한 Kafka 메시지 수다. 계속 늘면 저장이 입력을 따라가지 못하고 있다는 신호다 |
| 배치·INSERT·part·병합 | 로그를 묶은 것이 배치, DB에 넣는 작업이 INSERT다. ClickHouse는 저장할 때 part라는 데이터 조각을 만들고, 나중에 여러 조각을 합친다 |
| 계단·버팀·병목 | 계단은 부하를 한 단계 높여 시험한 구간이다. 버팀은 정해 둔 시험 기준 통과, 병목은 전체 속도를 먼저 제한하는 구간을 뜻한다 |

**‘버팀’은 30초 안팎의 시험을 통과했다는 뜻이다.** 장시간 운영이나 실제 장비 수천 대의 동작까지 검증한 것은 아니다. 통과하려면 목표 처리량의 95% 이상, 실패 0건, p99 1초 이하를 모두 만족해야 한다.

## 구간별 결과 요약

장비 1대는 1초에 실제 로그 60.3줄을 쓴다. 명세서의 1,000대는 초당 약 6만 줄이다. 구간별로 그 몇 배까지 버티는지를 쟀다.

| 구간 | 무엇으로 쟀나 | 이 PC의 천장 | 1,000대 대비 | 천장을 만든 것 |
|---|---|---|---|---|
| 2-1 장비 → 수집 서버 (지금 Fluent Bit 설정) | vegeta가 Fluent Bit 요청을 흉내 | 2,000대 버팀, 3,000대에서 p99 173ms에 연결 끊김이 섞임 (초당 약 1.3만 요청, 18만 줄) | 2~3배 | 요청마다 Kafka ack를 기다리며 Tomcat 스레드를 붙잡음 |
| 2-1 같은 경로, 장비당 1요청으로 묶은 설정 | 위와 같음 | 5,000대 (초당 30만 줄) | 5배 | 수집 서버 CPU |
| 2-2 수집 서버 → Kafka (프로듀서 하나) | 앱 안의 실행기가 실제 로그를 정규화해 발행 | 초당 35만~45만 줄 (설정에 따라) | 6~7배 | 프로듀서 하나가 브로커로 내보내는 속도 |
| 2-2 같은 구간, 프로듀서 둘 | 위와 같음 | 초당 65만 줄 | 11배 | 앱 CPU (정규화·직렬화) |
| 2-3 Kafka → ClickHouse (컨슈머 1 / 3 / 6 / 12) | 1,000만 건을 쌓아 두고 비우는 속도 | 초당 14.7만 / 29.3만 / 39.8만 / 47.3만 행 | 2.4 / 4.9 / 6.6 / 7.8배 | 3개까지는 컨슈머 수, 그 뒤로는 ClickHouse와 PC 전체 CPU |
| 끝에서 끝 (세 구간 동시, 컨슈머 3) | 장비 흉내 + 적재까지 | 2,000대 (초당 12만 줄), 저장까지 p99 102~163ms | 2배 | 수집 서버 (2-1과 같은 곳) |

이 표에서 가장 먼저 볼 행은 마지막 행이다. 전체를 함께 돌렸을 때는 2,000대 분량까지 통과했다. 각 구간을 따로 돌려 얻은 최고 속도를 전체 시스템의 속도로 볼 수는 없다. 모든 프로그램이 같은 노트북의 CPU를 나눠 쓰기 때문이다.

## 1. 무엇을 쟀나

사용자가 정한 세 구간이다.

1. **장비 → 스프링 서버(2-1).** 장비의 Fluent Bit이 보내는 HTTP 요청을 수집 서버가 초당 얼마나 받는가. 실제 경로(`POST /ingest/fluentbit`, Kafka ack까지 기다린 뒤 200)를 재고, 그 비용을 나누려고 HTTP와 JSON 읽기까지만 하는 엔드포인트와 정규화까지 하는 엔드포인트도 같은 부하로 쟀다.
2. **스프링 서버 → Kafka(2-2).** 수집 서버의 프로듀서가 초당 얼마나 보낼 수 있는가. HTTP를 빼고, 앱 안에서 실제 로그를 정규화해 발행하는 실행기(전날 만든 `LoadTestRunner`)를 docker 안에서 돌렸다.
3. **컨슈머 → 데이터 웨어하우스(2-3).** 적재 컨슈머가 `poll()`로 읽어 ClickHouse에 넣는 속도. Kafka에 쌓아 둔 메시지를 비우는 데 걸린 시간으로 쟀다.

마지막으로 세 구간을 함께 돌려 끝에서 끝으로 버티는 대수와 저장까지 걸리는 지연을 쟀다.

## 3. 입력: 실제 로그로 만든 장비 요청

부하의 재료는 전날과 같은 대외비 생성기 로그 1대분(351,327줄)이다. 이번에는 이것을 Fluent Bit이 실제로 보냈을 HTTP 요청으로 바꿨다(`loadtest/FluentBitBatches`).

Fluent Bit은 레코드를 태그별 묶음(chunk)에 모으고, Flush 주기(1초)마다 묶음 하나를 요청 하나로 보낸다. 지금 `fluent-bit.conf`는 `Tag device.*`라서 파일 경로가 곧 태그다. 그러니 장비 한 대는 1초에 "그 1초에 새 줄이 생긴 파일 수"만큼 요청을 보낸다. 실제 로그의 이벤트 시각을 1초 단위로 잘라 (초, 파일)마다 요청 하나를 만들었더니 다음과 같았다.

| 묶는 방식 | 장비 1대의 1초 | 요청 1건 | 요청 본문 | gzip 하면 |
|---|---|---|---|---|
| 파일별 (`per-file`, 지금 설정) | 요청 4.34건, 60.3줄 | 13.9줄 | 3.7KB | 16% |
| 장비별 (`per-device`, 태그를 하나로 고정했을 때) | 요청 1건, 60.3줄 | 60.3줄 | 15.9KB | 13% |

그러니 지금 설정에서 1,000대는 초당 약 4,340건의 요청이다. 질문을 정할 때 "1,000대는 초당 약 1,000건"이라고 적은 것은 이 동작을 빠뜨린 것이었다. 실제 Fluent Bit 에이전트를 수천 개 띄워 확인한 것은 아니며, 묶음 동작은 Fluent Bit의 태그·chunk·flush 규칙에서 이끌어 낸 것이다(9절).

로그는 1대분이므로 실제 1대의 "1초"를 가상 장비 한 대의 "1초"로 썼다. 줄이 있는 초가 5,828개라 가상 장비-초도 5,828개이고, k초째 묶음은 장비 `OHT-((k % 20000) + 1)`의 것이 된다. 레코드에는 `collected_at`을 넣지 않아 수집 서버가 받은 시각이 들어가게 했다. 그러면 저장소의 `inserted_at - collected_at`이 "수집 서버가 받은 뒤 저장되기까지" 걸린 시간이 된다.

## 4. 방법

**부하 발생기는 vegeta다.** 처음에는 PC에 이미 있던 k6를 썼다. 그런데 가장 가벼운 엔드포인트(HTTP 수신만)에 초당 4,336건을 보내는 동안 k6 자신이 CPU 코어 9.3개를 썼다. 수집 서버는 1.2개를 쓰고 있었다. 요청마다 자바스크립트 런타임이 3.7KB 본문을 다루는 비용으로 보인다. 이대로는 수천 대를 흉내 내기 전에 부하 발생기가 PC를 먼저 차지한다. 같은 조건에서 vegeta는 코어 0.77개를 썼고 서버 지연 p99는 0.58ms였다(k6로 잰 값은 13.9ms였다. 대부분 k6 자신의 지연이었다). vegeta는 정해진 속도로 새 요청을 시작하는 열린 모델이다. 장비는 서버를 기다려 주지 않고 1초마다 새 묶음을 만들기 때문에 이 모델이 맞다. 요청 본문 파일은 vegeta의 JSON 대상 형식(본문 base64)으로 바꿔 쓰고, gzip은 장비 쪽(Fluent Bit)이 하는 일이므로 미리 압축해 `Content-Encoding: gzip`을 붙였다. 수집 서버에는 gzip 요청 본문을 푸는 필터(`ingest/GzipRequestFilter`)를 더했다. Spring MVC는 요청 본문 압축을 저절로 풀지 않는다.

**계단과 판정은 전날과 같은 규칙이다.** 2-1은 1,000대에서 시작해 1,000대씩, 계단 하나 30초(분해 측정 둘은 20초), 첫 계단 전에 15초 워밍업을 했다. 성공한 요청 속도가 목표의 95% 이상이고, 실패 0건이며, p99가 1초 이하이면 버틴 것으로 본다. 두 계단 연속 못 버티면 멈춘다. 실패 0건 조건이 엄격해서, 처리량과 지연은 괜찮은데 연결 끊김 몇 건(0.001% 안팎)으로 실패한 계단이 있다. 그런 계단은 표에 그대로 적었다. 2-2는 10만 줄/s에서 5만씩, 30초(앞 5초 제외)로 전날과 같다.

**2-3은 쌓아 두고 비운다.** 생산 속도와 상관없이 컨슈머가 낼 수 있는 최대치를 보려고, 먼저 수집 서버 컨테이너의 실행기로 토픽에 9,999,860건을 쌓았다. 키는 가상 차량 ID라서 멱등키 `(device_id, source, offset)`가 대부분 겹치지 않는다. 그다음 컨슈머 수마다 적재 컨테이너를 멈추고, 테이블을 비우고, 그룹 오프셋을 처음으로 되돌린 뒤, 컨슈머 수를 바꿔 다시 띄웠다. lag가 0이 되고 적재한 행이 쌓인 건수에 닿을 때까지 2초마다 상태를 읽었다. 적재 속도는 첫 INSERT 시작부터 마지막 INSERT 끝까지의 평균이다.

**적재 컨슈머의 모양.** 배치 리스너가 `poll()` 한 번에 받은 묶음 전체를 RowBinaryWithDefaults로 바꿔 INSERT 한 번으로 보낸다. `inserted_at`은 비워 보내 ClickHouse가 기록하는 순간의 시각(`DEFAULT now64(3)`)이 들어가게 했다. 오프셋은 INSERT가 성공한 뒤에만 커밋되고, 실패하면 같은 묶음을 1초 간격으로 끝없이 다시 시도한다. Spring Kafka의 기본 에러 핸들러는 10번 실패하면 그 묶음을 건너뛰는데, 저장소가 잠깐 멈추는 동안 로그를 버리게 되므로 쓰지 않았다. 테이블은 ReplacingMergeTree, `ORDER BY (device_id, source, offset)`, 일 단위 파티션이다.

**CPU는 옆에서 잰다.** 스크립트가 `docker stats`를 계속 돌려 컨테이너별 CPU를 모으고 계단 구간으로 잘라 평균을 낸다. 1.0은 코어 하나를 꽉 쓴 것이다.

## 7. 결과

### 7.1 장비 → 수집 서버 (2-1)

**파일마다 따로 보내는 현재 설정은 2,000대까지 통과했다.** 압축하지 않았으며, Kafka의 수신 확인을 받은 뒤 HTTP 응답을 돌려주는 실제 수집 경로를 쟀다. 표의 목표·실제는 초당 요청 수다. MB/s는 요청 본문의 초당 크기, p50·p99는 ms, CPU는 사용한 코어 수다.

| 대수 | 목표 | 실제 | 달성% | 줄/s | MB/s | p50 | p99 | 실패 | 수집 서버 CPU | 브로커 CPU | 발생기 CPU | 판정 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 1,000 | 4,336 | 4,336 | 100.0 | 60,285 | 15.6 | 10.3 | 24.3 | 0 | 1.36 | 0.29 | 0.86 | 버팀 |
| 2,000 | 8,672 | 8,672 | 100.0 | 120,571 | 31.2 | 8.7 | 25.1 | 0 | 3.35 | 0.63 | 1.81 | 버팀 |
| 3,000 | 13,007 | 13,000 | 99.9 | 180,747 | 46.7 | 10.4 | 172.9 | 연결 끊김 0.0005% 미만 | 5.32 | 0.67 | 2.45 | 못 버팀 |
| 4,000 | 17,343 | 14,132 | 81.5 | 196,485 | 50.8 | 141.4 | 192.5 | 0 | 4.60 | 0.66 | 1.97 | 못 버팀 |

3,000대 행의 ‘못 버팀’은 서버가 멈췄다는 뜻이 아니다. 보낼 양의 99.9%를 처리했고 p99도 약 0.173초였지만, 연결이 끊긴 요청이 조금이라도 있어 ‘실패 0건’ 조건을 통과하지 못했다. 실패율은 0.0005% 미만이라 반올림하면 0으로 보일 정도였다. 4,000대에서는 보낼 양의 81.5%만 처리했다. 초당 약 1.4만 요청에서 처리 속도가 더 올라가지 않았다. 수집 서버 CPU는 코어 5개 안팎이어서, CPU를 전부 써서 막힌 모습은 아니었다.

**어느 작업을 붙일 때 느려지는지 확인했다.** 같은 양을 보내되, 요청을 읽기만 하는 경우, 로그 형식까지 바꾸는 경우, Kafka에 보내고 확인까지 기다리는 경우로 나눴다. 엔드포인트는 각 작업을 실행하는 서버 주소다.

| 엔드포인트 | 하는 일 | 버틴 최대 | 그 계단의 p99 | 그 계단의 수집 서버 CPU |
|---|---|---|---|---|
| `/loadtest/ingest/receive` | HTTP 수신 + JSON 배열 읽기 | 6,000대 (26,015 req/s, 36만 줄/s) | 10.1ms | 3.57 |
| `/loadtest/ingest/normalize` | 위 + 레코드마다 정규화 | 6,000대 (26,003 req/s) | 46.7ms | 5.81 |
| `/ingest/fluentbit` (실제) | 위 + Kafka 발행과 ack 대기 | 2,000대 | 25.1ms | 3.35 |

요청을 읽고 로그 형식을 바꾸는 데까지는 6,000대 분량을 받았다. Kafka에 보내고 확인을 기다리는 작업까지 붙이면 통과한 대수가 2,000대로 줄었다. 따라서 요청을 읽거나 로그를 해석하는 일만으로는 현재의 한계를 설명하기 어렵다. receive와 normalize도 7,000대(초당 3만 요청)에서는 연결 끊김 0.003~0.018% 때문에 탈락했다. 이때 처리량 달성률은 99.8~100%였다.

**보내는 방식과 서버 설정을 바꿔 봤다.** 아래는 모두 Kafka의 수신 확인까지 기다리는 수집 경로다. gzip은 HTTP 본문 압축, 가상 스레드는 기다리는 요청이 많을 때 쓸 수 있는 Java 실행 방식이다. keep-alive는 TCP 연결을 여러 요청에 재사용하는 기능이고, 무제한은 연결 하나에서 처리할 요청 수 제한을 없앴다는 뜻이다.

| 변형 | 버틴 최대 | 그 계단 | 그 다음 계단 | 비고 |
|---|---|---|---|---|
| gzip | 3,000대 | 13,007 req/s, p99 207.5ms, 전송 7.5MB/s, 수집 서버 CPU 7.77 | 4,000대 → 13,597 req/s (78.4%) | 전송량은 압축 없을 때(3,000대 46.7MB/s)의 6분의 1. 압축을 푸는 만큼 CPU가 늘었다(1,000대에서 1.36 → 1.87) |
| 장비별 1요청 (`per-device`) | 5,000대 | 4,937 req/s (98.7%), 30만 줄/s, p99 563ms, CPU 5.39 | 6,000대 → 5,285 req/s (88.1%) | 같은 줄을 4분의 1 요청으로 나른다 |
| 가상 스레드 + keep-alive 무제한 | 3,000대 | p99 116.8ms, CPU 5.70 | 4,000대 → 17,339 req/s (100%), p99 517ms, 연결 끊김 0.001% | 처리량 천장이 약 1.4만에서 1.7만 req/s로 올랐다. 5,000대에서는 14,431 req/s(66.6%)로 무너졌다 |
| 장비별 1요청 + 가상 스레드 | 4,000대 | p99 31.6ms | 5,000대 → 4,856 req/s (97.1%), p99 1,345ms | 플랫폼 스레드일 때(5,000대 버팀)보다 나아지지 않았다 |

### 7.2 수집 서버 → Kafka (2-2)

**HTTP 요청을 받는 일을 빼면, 프로듀서 하나로 초당 35만~45만 줄을 보냈다.** 앞 실험보다 여유가 있다. Kafka로 보내는 기능 자체보다 HTTP 수집 경로에서 먼저 속도가 제한된다는 근거다.

docker 안에서 프로듀서 설정과 보내는 작업자(스레드) 수, 프로듀서 수를 바꿨다. 파티션은 Kafka 토픽을 나눈 저장·처리 단위이며, 이번에는 12개다. ‘배치 128KB / 20ms’는 파티션별로 최대 128KB까지 모으고, 덜 차면 최대 20ms 기다리는 설정이다. lz4는 Kafka에 보내는 데이터를 압축하는 방식이다.

| 설정 | 스레드 | 프로듀서 | 버틴 최대 (줄/s) | 그 계단의 p99 | 다음 계단 (못 버팀) | 다음 계단의 앱 CPU | 다음 계단의 버퍼 대기 |
|---|---|---|---|---|---|---|---|
| 기준선 16KB / 5ms | 8 | 1 | 350,000 (184.8MB/s) | 405ms | 400,000 → 378,051 (94.5%) | 5.56 | 1.63 |
| 배치 128KB / 20ms (1회차) | 8 | 1 | 450,000 (238.9MB/s) | 598ms | 500,000 → 448,862 (89.8%) | 5.7 | 2.31 |
| 배치 (2회차) | 8 | 1 | 400,000 (350,000 계단만 94.6%로 실패) | 533ms | 450,000 → 397,935 (88.4%) | 5.4 | 2.52 |
| 배치 | 16 | 1 | 400,000 (390,351, 97.6%) | 934ms | 450,000 → 411,840 (91.5%) | 5.8 | 8.2 |
| 배치 + lz4 | 8 | 1 | 450,000 (436,863, 97.1%) | 33ms | 500,000 → 458,841 (91.8%) | 5.46 | 0 |
| 배치 | 16 | 2 | 650,000 (343.5MB/s) | 122ms | 700,000 → 656,621 (93.8%) | 11.2 | 2.06 |

프로듀서 하나를 그대로 둔 채 보내는 작업자만 8개에서 16개로 늘려도 최대 처리량은 초당 40만~45만 줄 부근이었다. 작업자는 늘었지만 메시지를 쌓아 둘 빈자리를 기다리는 수치만 8~10까지 올랐다. 이는 여러 작업자가 동시에 버퍼를 기다렸다는 뜻이다. 로그를 더 빨리 만들어도 밖으로 내보내는 속도가 따라가지 못한 것이다.

프로듀서를 둘로 나누자 초당 65만 줄까지 통과했다. 그다음에는 앱이 코어 11개를 써 CPU가 다음 제한 요인으로 보였다. lz4 압축은 빈 버퍼를 기다리지 않고 45만 줄 목표를 통과했으며, p99는 33ms였다. 다만 CPU 사용량은 약 5.5코어 부근에서 더 늘지 않았다. 압축 계산이 보내는 작업자에게 부담을 준 것으로 추정한다.

전날 호스트에서는 기준선(스레드 4)이 초당 10만 줄도 못 버텼고, 배치 설정은 스레드를 16개, 프로듀서를 4개까지 늘려도 약 10만에 머물렀다. docker 안에서는 기준선(스레드 8)이 35만, 배치가 40만~45만을 버텼다. 스레드 수가 달라 기준선끼리 바로 비교할 수는 없지만, 배치 설정이 스레드와 프로듀서를 늘려도 10만을 못 넘던 것이 docker 안에서 4배가 됐으므로, 전날의 천장이 Kafka가 아니라 Docker Desktop의 포트 전달이었다는 해석이 확인됐다.

### 7.3 Kafka → ClickHouse (2-3)

**저장하는 컨슈머를 늘리면 더 빨리 넣었지만, 개수에 비례해 계속 빨라지지는 않았다.** 약 1,000만 건을 넣는 데 컨슈머 1개는 68.0초, 3개는 34.1초, 12개는 21.1초가 걸렸다.

정확한 입력은 9,999,860건이다. 컨슈머 수를 바꿀 때마다 같은 데이터를 처음부터 다시 넣었다. 매번 테이블에 9,999,860행이 들어갔고 실패는 0건이었다. 아래 ‘대수 환산’은 저장 속도를 장비 1대의 로그 발생 속도로 나눈 값이다. 장비에서부터 전 구간을 그 대수로 시험했다는 뜻은 아니다.

| 컨슈머 | 적재 행/s | 대수 환산 | 걸린 초 | INSERT 수 | 행/INSERT | INSERT p50 | INSERT p99 | 서버 안 시간/INSERT | sink CPU | ClickHouse CPU | 새 part | 병합 | 끝에 남은 part |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 1 | 146,994 | 2,438 | 68.0 | 545 | 18,348 | 47ms | 72ms | 44.6ms | 0.82 | 1.09 | 545 | 102 | 12 |
| 3 | 293,285 | 4,864 | 34.1 | 521 | 19,193 | 68ms | 111ms | 66.5ms | 2.32 | 2.72 | 521 | 97 | 9 |
| 6 | 397,957 | 6,600 | 25.1 | 684 | 14,619 | 69ms | 193ms | 71.9ms | 4.43 | 4.62 | 684 | 129 | 17 |
| 12 | 473,142 | 7,846 | 21.1 | 692 | 14,450 | 119ms | 269ms | 116.5ms | 7.73 | 7.10 | 692 | 133 | 14 |

컨슈머 1개는 약 1.8만 행을 한 번에 넣었다. INSERT 시간의 p50은 47ms였고, ClickHouse가 보고한 서버 내부 처리 시간은 평균 44.6ms였다. 중앙값과 평균값이므로 정확히 빼서 비교할 수는 없지만, 비슷한 크기여서 DB 내부 작업이 큰 몫을 차지한 것으로 보인다.

컨슈머를 늘리면 여러 묶음을 동시에 저장할 수 있다. 하지만 1개에서 3개로 늘렸을 때 처리량은 약 2배, 6개에서 12개로 늘렸을 때는 약 1.2배였다. 수가 많아질수록 ClickHouse 내부의 평균 처리 시간도 약 72ms, 117ms로 길어졌다. 12개일 때 저장 앱(sink)과 ClickHouse가 합쳐 코어 15개 가까이를 썼다. 같은 PC에서 CPU를 나눠 쓰는 영향이 커진 것으로 해석한다.

INSERT 한 번마다 part가 하나씩 생겼지만, ClickHouse가 이 조각들을 합쳤다. 측정 끝에 남은 part는 9~17개였고, 조각이 너무 많다는 오류(`Too many parts`)는 나오지 않았다.

### 7.4 끝에서 끝 (세 구간 동시, 컨슈머 3)

**전체 경로도 2,000대까지 통과했다. 1,000대일 때 로그의 약 99%는 서버 수신 후 0.163초 안에 저장됐다.** 2,000대일 때 저장 지연 p99는 0.102초였다. 부하가 적은 쪽이 항상 빠르게 나오지는 않았으며, 구성별 반복 측정은 하지 않았다.

저장 컨슈머 3개를 켜 둔 채 2-1의 기본 설정으로 다시 보냈다. HTTP 지연은 요청을 보내고 Kafka 수신 확인을 거쳐 응답을 받기까지의 시간이다. 저장 지연은 그 단계에서 저장된 로그의 `inserted_at - collected_at`, 즉 수집 서버가 받은 뒤 ClickHouse에 기록되기까지의 시간이다. 장비에서 로그가 생긴 뒤 수집 서버에 도착하기 전의 시간은 포함하지 않는다.

|---|---|---|---|---|---|---|---|---|---|---|
| 1,000 | 4,336 | 100.0 | 60,286 | 12.3 | 33.1 | 0 | 73ms | 163ms | 1.95 | 버팀 |

전체를 함께 돌리자 수집 속도는 초당 약 1.13만 요청에서 더 늘지 않았다. 수집 구간만 돌렸을 때의 1.3만~1.4만 요청보다 낮았다. 저장 앱과 ClickHouse도 같은 CPU를 써 영향을 준 것으로 보인다. 반면 Kafka에 남은 미처리량(lag)은 각 단계 끝에서 0 근처였다. 따라서 저장이 계속 밀리는 것보다 수집 서버에서 요청을 받는 일이 먼저 제한된 것으로 해석한다.

저장 지연이 약 60~70ms 나온 이유는 컨슈머가 로그를 모아 읽는 시간과 ClickHouse에 한 묶음을 넣는 시간이 합쳐졌기 때문으로 보인다. 컨슈머는 1MB가 모이거나 최대 500ms가 지나면 읽는 설정이다(`fetch.min.bytes=1MB`, `fetch.max.wait.ms=500`). 앞 실험의 INSERT p50은 47~68ms였다. 다만 모아서 읽는 시간과 DB에 넣는 시간을 이 실행에서 따로 재지는 않았다.

실행 후 테이블에 남은 행은 607,745개였다. 이것을 전송 유실로 해석하면 안 된다. 테스트 도구가 준비한 요청 본문 25,269개를 반복해서 보냈기 때문에 같은 로그가 여러 번 들어갔다. 테이블은 `(device_id, source, offset)`이 같으면 같은 로그로 취급한다. 이 조합을 멱등키라고 하며, ReplacingMergeTree가 데이터 조각을 합치는 과정에서 중복을 정리했다.

중복 제거 동작을 확인한 결과지만, 중복이 드문 실제 환경보다 조각을 합치는 부담이 컸다는 한계도 있다(9절). 남은 데이터는 행당 압축 후 63.5바이트였다. 압축 전은 388바이트이고, 압축률 0.164는 원래 크기의 16.4%가 됐다는 뜻이다. 같은 로그를 Kafka로 보낼 때의 JSON은 평균 546바이트였다.

## 8. 왜 수집 서버에서 먼저 밀렸는가

**Kafka의 응답을 기다리는 동안 요청 처리 작업자도 기다린다.** 수집 서버는 요청에 든 로그를 Kafka에 보낸 뒤, Kafka의 수신 확인을 받아야 HTTP 성공 응답(200)을 돌려준다. 확인 전에 성공이라고 답하면, 이후 Kafka 전송이 실패했을 때 장비가 다시 보낼 기회를 잃기 때문이다. 이렇게 재전송을 허용해 최소 한 번 전달하려는 방식을 at-least-once라고 한다.

현재 Tomcat의 요청 처리 작업자(스레드)는 200개다. 작업자 하나가 요청을 맡아 10~15ms 동안 처리하고 기다린다고 가정하면, 초당 처리량은 대략 `200 ÷ 0.01~0.015초`, 즉 1.3만~2만 요청이다. 배치를 모으는 설정(`linger.ms=20`)과 Kafka 응답 대기가 이 시간에 영향을 준다. 실제로 속도가 더 늘지 않은 지점도 초당 1.3만~1.4만 요청이었다.

Kafka 응답을 기다리지 않는 실험에서는 초당 2.6만 요청을 받았고, 가상 스레드 등을 적용한 실험에서는 약 1.7만 요청까지 올라갔다. 따라서 ‘응답을 기다리는 작업자가 부족하다’는 해석이 유력하다. 다만 작업자 200개가 실제로 모두 바빴는지를 직접 잰 것은 아니다. 위 계산은 처리량과 지연으로 원인을 추정한 것이다.

**기다리는 작업자 문제를 줄이면, 다음에는 CPU로 처리하는 일이 한계가 된다.** 가상 스레드 등을 적용하자 초당 1.7만 요청(24만 줄)에서 수집 서버가 코어 7.4개를 썼다. 로그 한 줄에 CPU 시간 약 31µs를 쓴 셈이다(7.4코어 ÷ 24만 줄). 장비별로 묶어 보내는 실험도 초당 24만~30만 줄 부근에서 더 늘지 않았다. 시험한 설정에서는 이 정도가 수집 서버 한 대의 다음 한계로 보인다. 로그를 읽고, 시각 등을 해석하고, JSON을 만들어 보내는 계산이 필요하기 때문이다. 전날 Java 실행 분석 도구인 JFR로 확인했을 때, 정규화 안에서는 시각 문자열을 해석하는 일이 CPU를 가장 많이 썼다.

**같은 로그도 적은 요청에 나눠 담으면 서버가 덜 바쁘다.** 현재는 장비 한 대가 초당 평균 4.34번 요청한다. 이를 초당 1번으로 묶자 통과한 대수가 2,000대에서 5,000대로 늘었다. 로그 줄 수는 같아도 요청을 접수하고 응답하는 횟수, Kafka에 보낸 뒤 확인을 기다리는 요청 수가 약 4분의 1로 줄기 때문이다. 이 실험에서는 요청을 묶는 변경이 서버 실행 방식 변경보다 효과가 컸다.

**gzip은 네트워크를 6분의 1로 줄이고 CPU를 더 쓴다.** 1,000대에서 전송량이 15.6MB/s에서 2.5MB/s로 줄었고, 수집 서버 CPU는 1.36에서 1.87코어로 늘었다. 천장은 스레드에서 막히는 것이 그대로라 압축 없을 때와 비슷했다.

**Kafka에 보내는 기능만 따로 보면, 프로듀서 하나가 내보내는 속도에 한계가 있었다.** 이 구성은 브로커가 하나이며, 프로듀서 하나의 I/O 스레드가 모인 로그를 전송한다. 로그를 만들어 보내는 작업자를 늘려도 초당 40만~45만 줄 부근에서 전송 대기 공간(버퍼)을 기다리는 일만 늘었다. 프로듀서를 둘로 나누자 초당 65만 줄까지 올라갔다. 다만 프로듀서 하나의 속도도 HTTP를 포함한 수집 경로의 18만~30만 줄/s보다 높다. 현재 전체 경로에서는 프로듀서 수부터 늘릴 이유가 적다.

**2-3은 컨슈머를 늘리는 만큼 오르다가 ClickHouse에 닿는다.** 컨슈머 1개가 이미 2,400대 분량을 넣는다. INSERT 시간의 대부분이 ClickHouse 서버 안의 시간이므로, 컨슈머를 늘리면 동시에 여러 INSERT가 서버에서 처리되며 3개까지는 거의 정비례로 오른다. 그 뒤로는 서버가 바빠져 INSERT 한 번이 길어진다.

**연결이 끊긴 정확한 이유는 아직 모른다.** 한계 근처에서는 처리량과 응답 시간이 기준 안에 있어도 0.001~0.02%의 연결 끊김(`connection reset by peer`)이 섞였다. 처음에는 Tomcat이 연결 하나에서 요청 100건을 처리한 뒤 닫는 동작을 의심했다. 하지만 이 제한을 없애도(`-1`) 끊김은 남았다. 요청이 몰려 접속 대기열이 넘쳤을 가능성을 생각하고 있지만 확인하지 않았다. 실제 Fluent Bit은 실패한 요청을 다시 보내도록 동작하므로 재전송으로 복구할 수 있다. 다만 이 실험은 Fluent Bit의 재시도까지 검증한 것이 아니므로, 연결 끊김 결과만으로 유실 여부를 단정할 수는 없다. 재전송이 생기면 서버가 받을 부하도 늘어난다.

## 9. 이 측정의 한계

- 부하 발생기, 수집 서버, 브로커, 컨슈머, ClickHouse가 한 노트북의 CPU를 나눠 썼다. VM의 CPU 20개는 하이퍼스레딩과 효율 코어를 포함한 수라, 코어 10개 남짓을 쓰면 이미 PC의 실질 여유가 바닥에 가깝다.
- 실제 Fluent Bit을 수천 개 띄운 것이 아니다. 요청 묶음은 태그·chunk·flush 규칙대로 만들었지만, 에이전트의 재시도, 버퍼, 동시 출력 수는 흉내 내지 않았다.
- vegeta는 동시 연결을 응답 대기 중인 요청 수(최대 2,000)만큼만 연다. 실제로는 장비마다 keep-alive 연결이 하나씩 열려 있으므로 1만 대면 연결도 1만 개다. Tomcat의 기본 최대 연결 수(8,192)가 그 규모에서 또 하나의 천장이 될 수 있는데, 재지 않았다.
- 장비와 서버가 같은 기계에 있어 네트워크 왕복이 거의 없다. 실제 망에서 왕복이 길어지면 요청 하나가 스레드를 붙잡는 시간이 늘어 2-1의 천장이 더 낮아진다(추정).
- 끝에서 끝 측정은 같은 요청 본문을 몇 초마다 반복해 보내므로 중복이 많다. ClickHouse 병합 부담이 실제보다 무겁고, 테이블에 남는 행 수가 보낸 수와 다르다.
- 브로커 하나, 복제 1이다. 복제를 켜면 `acks=all`이 복제본까지 기다리므로 2-1의 ack 대기가 길어진다(Step 6).
- 구성마다 한 번씩 쟀다. 같은 배치 설정으로 두 번 잰 2-2는 천장이 40만과 45만으로 달랐다.

## 10. 측정 중 발견해 고친 것

- **k6의 자기 부하.** 초당 4,336건에 k6가 코어 9.3개를 써서 vegeta(0.77코어)로 바꿨다. k6로 잰 지연에는 k6 자신의 지연이 섞여 있었다.
- **기준선 프리셋이 컨테이너 설정을 물려받았다.** `baseline`은 "아무것도 덮어쓰지 않음"이었는데, ingest 컨테이너는 128KB/20ms로 뜨므로 첫 기준선 실행은 사실상 배치 설정이었다(평균 배치 56~103KB). 프리셋에 16KB/5ms/압축 없음을 직접 적고 다시 쟀다. 7.2의 "배치 1회차"가 그 첫 실행이다.
- **제어 API 연결이 부하 중에 끊겼다.** 스크립트가 호스트에서 포트 전달로 상태를 묻는데, 부하가 가장 높을 때 그 요청이 끊겨 스크립트가 실행이 끝난 것으로 판단했다. 그 바람에 한 번은 실행 중인 토픽을 지워 lz4 45만 계단에 전송 오류 219건이 났다. 그 계단은 버리고 다시 쟀다. 상태 조회에 재시도를 넣었다(`common.ps1`의 `Get-Json`).
- **서버 시간의 단위.** client-v2의 `getServerTime()`은 나노초다. ms로 읽어 4,597만으로 나왔던 것을 고쳤다.
- **디스크.** 브로커의 보존 검사 주기를 부하 구성에서만 30초로 줄였다. 그래도 고속 계단에서 Kafka와 ClickHouse가 순간적으로 많이 써서 Docker 가상 디스크가 13.6GB에서 115.5GB로 다시 커졌다. 줄이는 방법은 `benchmark-kafka-throughput.md` 10절과 같다. ClickHouse는 TRUNCATE와 병합으로 버린 옛 part(이번에 15.3GiB)를 8분쯤 뒤에 지운다.

## 11. 기업 프로젝트에 주는 의미

**이번 시험에서는 1,000대 분량을 수집하고 저장할 수 있었다.** 노트북 한 대에 모두 올린 상태에서 2,000대 분량까지 기준을 통과했고, 1,000대와 2,000대의 저장 지연 p99는 각각 163ms와 102ms였다. 장비가 1만 대처럼 늘어날 상황을 검토한다면, 이번에 먼저 막힌 수집 서버의 대수와 요청 처리 방식을 우선 살펴볼 근거가 된다. 실제 운영 용량은 운영 장비와 망에서 다시 확인해야 한다.

**Fluent Bit의 태그를 장비 단위로 묶는 것을 권한다.** 지금 `Tag device.*`는 파일마다 요청을 따로 만들어 1,000대가 초당 4,340건이 된다. 태그를 고정하면(예: `Tag device`) 요청이 4분의 1로 줄고, 같은 수집 서버가 2,000대에서 5,000대로 버텼다. 원본 경로는 `Path_Key source`로 레코드 안에 남으므로 잃는 정보가 없다. 다만 이 효과는 흉내로 잰 것이라 실제 에이전트로 한 번 확인해야 한다.

**수집 서버는 ack 대기가 스레드를 붙잡는다는 점을 설계에 넣는다.** at-least-once 계약 때문에 ack를 기다리는 것은 바꿀 수 없다. 대신 가상 스레드(`spring.threads.virtual.enabled=true`)로 스레드 상한을 없애거나, 수집 서버 대수를 "초당 요청 × 요청 하나가 붙잡는 시간 ÷ 스레드 수"로 산정한다. 망을 건너면 왕복이 길어지므로 이 식의 분자가 커진다.

**gzip은 통신량을 줄이는 대신 서버에서 압축을 푸는 계산이 든다.** 1,000대 기준 전송량은 압축 없이 초당 15.6MB, gzip을 쓰면 2.5MB였다. 네트워크에 여유가 있으면 압축 없이 보내는 쪽을, 전송 용량이 부족하면 압축하는 쪽을 검토한다. 사내 LAN이라는 이유만으로 여유가 있다고 단정할 수는 없다. gzip을 켜려면 수집 서버에 이번에 만든 압축 해제 필터도 필요하다.

**적재 쪽은 컨슈머 1개로 시작해 파티션을 넉넉히 둔다.** 컨슈머 1개가 2,400대 분량을 넣는다. 늘어날 때 컨슈머를 늘릴 수 있도록 파티션은 예상 컨슈머 수 이상(이번 12개)으로 둔다. INSERT 한 번에 1.5만~2만 행이 실리도록 `max.poll.records`와 fetch 설정을 키운 것이 part 수를 낮게 유지했다. 기본값(`max.poll.records=500`)이면 INSERT가 수십 배 잦아진다(계산).

**프로듀서는 하나로 충분하다.** 수집 서버 하나가 낼 수 있는 양(18만~30만 줄/s)보다 프로듀서 하나의 천장(40만~45만 줄/s)이 높다.

## 배운 점

병목은 겹쳐 있었다. 2-1에서 스레드 상한을 풀자 CPU가 드러났고, 2-2에서 스레드를 늘리자 프로듀서 하나의 천장이 드러났다. 하나를 풀고 처리량이 따라 오르는지를 볼 때마다 다음 천장이 보였다. 반대로 같은 줄 수를 더 적은 요청으로 보내는 것처럼 일의 양 자체를 줄이는 변경은 어느 천장이든 함께 낮춰 주었다.

두 번째로 분명해진 것은 측정 도구도 부하라는 점이다. k6는 서버보다 CPU를 많이 썼고, 그 상태로 잰 지연의 대부분은 k6 자신의 것이었다. 부하 발생기의 CPU를 함께 재지 않았다면 수집 서버가 초당 4,000건에서 막힌다고 잘못 결론 냈을 것이다.
