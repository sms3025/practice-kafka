# Kafka 부하 테스트 결과: 로그를 묶어 보내면 얼마나 달라지는가

> 먼저 읽을 후속 결과(2026-10-16): 현재 프로젝트의 전체 처리 능력은 [장비부터 ClickHouse 저장까지의 결과](benchmark-transport.md)를 먼저 본다. 이 문서는 전날 Kafka에 보내는 구간을 따로 잰 기록이다. 당시 Windows에서 실행한 앱은 Docker 안의 Kafka로 들어가는 통신 경로에서 속도가 제한됐다. 다음 날 앱도 docker 안에서 실행하자 기준선 설정은 초당 35만 줄, 배치 설정은 40만~45만 줄까지 통과했다(후속 문서 7.2절). 따라서 아래의 ‘앱 경유 약 10만 줄’은 이 PC의 당시 실행 방식에서 나온 값이며, 운영 서버의 한계로 사용하면 안 된다.
>
> 측정 2026-10-15, 브랜치 `kafka-load-test`. 이 문서의 수치는 모두 아래 2절의 PC에서 한 번씩 잰 실측이다. 반복 측정은 하지 않았으므로 계단 하나의 값에는 수 퍼센트의 잡음이 있다(6.1절의 45만·50만 계단이 그 예다). 추정이나 계산으로 낸 값은 그렇다고 밝혔다.

## 먼저 읽을 결론

**Kafka가 로그를 받아 보관하는 속도에는 여유가 있었다. 한 번에 조금씩 보내기보다 여러 줄을 모아 보내는 설정이 처리량과 지연 모두에서 좋았다.** 같은 도구 하나로 보냈을 때 기본 설정은 초당 40만 줄, 묶음 크기를 키운 설정은 초당 90만 줄까지 시험 기준을 통과했다. 이 수치는 Kafka까지 보내는 속도이며, ClickHouse에 저장하는 속도는 아니다.

반면 우리 앱에서 로그를 읽고 가공해 보내면 초당 약 10만 줄 부근에서 더 늘지 않았다. 원인을 나눠 보니 로그를 가공하는 CPU 작업과 Windows에서 Docker로 들어가는 통신 경로가 함께 영향을 줬다. 다음 날 앱을 docker 안으로 옮긴 후 속도가 크게 올라갔으므로, 이 결과만 보고 “우리 앱은 초당 10만 줄이 최대”라고 결론 내리면 안 된다.

결과를 이해하려면 아래 용어와 요약 표를 읽고 6절로 넘어가면 된다. 2~5절은 실험 조건과 실행 방법이다. 7절은 왜 이런 차이가 났는지, 8절은 기업 프로젝트에서 무엇을 검토할지 설명한다.

## 표를 읽는 데 필요한 말

| 표현 | 쉬운 뜻 |
|---|---|
| 브로커 | 메시지를 받아 보관하는 Kafka 서버다 |
| 프로듀서 | Kafka에 메시지를 보내는 프로그램이나 객체다. 이 문서에서는 로그 한 줄이 메시지 한 건이 된다 |
| 브로커 단독·앱 경유 | 미리 만든 메시지를 성능 도구로 보내는 실험과, 우리 앱이 로그를 가공해 보내는 실험이다. 브로커 단독 실험도 보내는 도구의 성능에 영향을 받는다 |
| 처리량·줄/s | 1초 동안 Kafka의 수신 확인을 받은 로그 줄 수다 |
| 목표·실제·달성률 | 보내려던 속도, 실제 처리한 속도, 둘의 비율이다. 목표 10만에 실제 8만이면 달성률은 80%다 |
| ack | Kafka가 메시지를 받았다고 보내는 응답이다. 최종 저장소에 넣었다는 뜻은 아니다 |
| p50·p99 | 절반, 약 99%의 메시지가 각각 이 시간 안에 확인 응답을 받았다는 뜻이다. p99 20ms라면 약 99%가 0.02초 안에 끝났다는 뜻이며, 최대 지연은 아니다 |
| CPU 1.0 | CPU 코어 하나를 계속 쓴 정도다. 1%라는 뜻은 아니다 |
| 정규화·직렬화 | 로그에서 시각·장비 ID 등을 뽑아 공통 형식으로 만드는 일과, 그 결과를 전송할 JSON으로 바꾸는 일이다 |
| 배치·버퍼 | 여러 메시지를 모은 묶음과, 보내기 전 잠시 쌓아 두는 메모리 공간이다. 버퍼 대기가 늘면 보내는 속도가 만드는 속도를 따라가지 못한다는 신호다 |
| 파티션 | Kafka 토픽을 나눈 저장·처리 단위다. 프로듀서는 파티션별로 메시지를 모아 보낸다 |
| 계단·버팀·천장 | 부하를 한 단계 높인 시험 구간, 시험 기준 통과, 더 보내려 해도 처리 속도가 더 늘지 않는 지점을 뜻한다 |

여기서 ‘버팀’은 목표의 95% 이상 처리, 지연 p99 1초 이하, 전송 오류 0건을 모두 만족했다는 뜻이다. 짧은 시험의 판정이므로 장시간 운영이 보장됐다는 의미는 아니다.

장비 1,000대가 가장 많은 로그를 내는 조건(peak)은 초당 약 6만 줄이다. 이에 비해 이 PC의 Kafka 전송 시험은 기본 설정으로 약 7배, 배치 설정으로 보수적으로 잡아도 20배 이상의 양을 받았다. 이번에 먼저 속도가 제한된 곳은 로그를 가공해 보내는 쪽과 통신 경로였다. 장비 1,000대의 전체 수집·저장 가능 여부는 이 시험만으로 알 수 없으며, 다음 날의 전체 경로 시험에서 확인했다.

## 1. 무엇을 알고 싶었나

질문은 "실제 OHT 로그를 초당 10만 줄부터 서서히 늘려 보내면 어디까지 버티는가"다. 버틴다는 말이 모호하므로 두 가지를 먼저 정했다. 하나는 "무엇이" 버티는지다. Kafka 브로커만의 한계와, 수집 서버가 실제로 하는 일(정규화, JSON, 키를 붙여 발행)을 포함한 한계는 다르다. 둘을 같은 계단으로 재면 차이가 곧 Kafka 앞쪽의 몫이 된다. 다른 하나는 "버틴다"의 기준이다. 아래 3절의 세 조건으로 정했다.

이 측정은 계획서의 단계 순서와 별개로, 기존 코드(Step 2까지)로 할 수 있는 범위에서 했다. HTTP 수집 경로 전체와 컨슈머 쪽은 재지 않았다(9절).

## 2. 측정 환경과 입력

| 항목 | 값 |
|---|---|
| PC | Intel i7-13700H (14코어 20스레드), 메모리 31.6GB, Windows 11 Enterprise 10.0.26200, 내장 SSD |
| Docker | Docker Desktop 4.88 (엔진 29.7.2), WSL2 VM에 CPU 20개·메모리 15.4GiB |
| Kafka | `apache/kafka:4.2.2` 단일 브로커(KRaft), `docker/docker-compose.yml` 그대로. 토픽 `loadtest-logs` 파티션 3, 복제 1 |
| 앱 | Spring Boot 4.1.1, kafka-clients 4.2.1, JDK 25(IntelliJ 내장 JBR 25.0.4), 호스트(Windows)에서 `gradlew bootRun` |
| 함께 떠 있던 것 | Kafka UI, Fluent Bit(입력 없음, 유휴). 다른 무거운 프로그램은 끄지 않았다 |

입력은 대외비 생성기가 만든 1대분 약 3시간(peak) 로그다. 23개 파일, 351,327줄, 원문 평균 169바이트다. 이것을 `LogNormalizer`로 정규화해 앱과 같은 직렬화기로 만든 JSON은 메시지 하나에 평균 546바이트다. 원문보다 세 배 넘게 큰 것은 `message`가 원문 대부분을 한 번 더 담고, 경로(`source`)와 시각 두 개, 필드 이름이 붙기 때문이다. 그래서 초당 10만 줄은 Kafka에 초당 약 52MB(1MB = 1,048,576바이트)가 된다. 로그 내용 자체는 대외비이므로 이 문서에는 크기와 개수만 적는다.

## 3. 방법

**두 층을 같은 메시지로 잰다.** 브로커 단독 층은 Kafka에 들어 있는 성능 도구 `kafka-producer-perf-test`를 브로커와 같은 docker 네트워크의 별도 컨테이너에서 돌린다. 앱도, 호스트에서 docker로 들어가는 포트 전달도 거치지 않는다. 앱 프로듀서 경유 층은 앱 안의 `LoadTestRunner`가 실제 로그 한 줄마다 `LogNormalizer.normalize()`를 부르고, 앱과 같은 `JacksonJsonSerializer`로 JSON을 만들어 `device_id`를 키로 `KafkaTemplate.send()`한다. 수집 서버의 `FluentBitIngestController`가 레코드 한 건마다 하는 일과 같고, HTTP만 빠졌다. 두 층이 같은 바이트를 보내도록, perf-test가 쓰는 메시지 파일(`payload.jsonl`)도 앱이 같은 정규화와 직렬화로 만든다. 그러면 두 층의 차이는 보내는 쪽의 차이(우리 코드, 키, 네트워크 경로)만 남는다.

**1대분 로그로 수천 대를 흉내 낸다.** 로그가 1대분뿐이라 그대로 `device_id`를 키로 보내면 모든 메시지가 한 파티션으로 간다. 그래서 계단마다 목표 처리량을 1대 peak(60줄/s)로 나눈 수만큼 가상 차량(`OHT-0001`~)을 두고, 줄마다 차량 ID만 바꿔 Fluent Bit이 붙였을 법한 `source`를 다시 만든다. 10만 줄/s 계단은 1,667대, 90만 줄/s 계단은 15,000대가 키가 된다. 줄 순서는 고정 시드로 섞어서, 어느 구간을 잘라도 메시지 크기 분포가 같게 했다. perf-test는 키 없이 보낸다(도구에 키 옵션이 없다). 이것이 두 층 사이의 차이 하나다.

**계단과 판정.** 10만 줄/s에서 시작해 5만씩 올린다. 계단 하나는 30초이고, 앞 5초는 연결 수립·JIT·버퍼 채우기가 섞이므로 집계에서 뺀다. 집계 구간에서 다음 세 조건을 모두 만족하면 그 계단을 버텼다고 본다. 못 버틴 계단이 두 번 연속되면 멈춘다. 한 번은 우연일 수 있기 때문이다.

1. 실제 처리량(브로커 ack를 받은 줄 수 ÷ 집계 시간)이 목표의 95% 이상
2. `send()` 호출 직전부터 ack 콜백까지의 지연 p99가 1초 이하
3. 전송 오류 0건

**한 번에 모아 보내는 양을 바꿨다.** 기준선은 측정 당시 `application.properties`의 설정이다(`acks=all`, `batch.size=16384`, `linger.ms=5`, 압축 없음). 최대 16KB까지 모으고, 덜 차면 최대 5ms 기다린다. 배치 설정은 `batch.size=131072`(128KB), `linger.ms=20`으로 더 크게 모아 보낸다. 배치 + lz4는 여기에 `compression.type=lz4`를 더해 데이터를 압축한다. 세 설정은 `loadtest/ProducerPreset.java`와 `scripts/loadtest/common.ps1`에 같은 이름과 값으로 있다.

**목표 속도는 "보냈어야 할 건수"로 맞춘다.** 보내는 스레드는 1ms마다 "시작 후 지금까지 보냈어야 할 건수"를 계산해 모자란 만큼 보낸다. 프로듀서가 밀려 `send()`가 버퍼 자리를 기다리며 막히면 그만큼 덜 보내게 되고, 그것이 달성률 하락으로 드러난다. 지연은 `send()`를 부르기 직전부터 재므로 막힌 시간이 포함된다. perf-test도 같은 기준으로 잰다.

**계단마다 꼬리를 털고, 실행마다 빈 토픽에서 시작한다.** 앱 층은 계단이 끝나면 `flush()`로 남은 레코드를 다 보내고 ack를 기다린 뒤 다음 계단으로 간다. perf-test는 계단마다 컨테이너를 새로 띄운다. 두 스크립트 모두 실행을 시작할 때 토픽을 지우고 새로 만들어, 앞 실행의 데이터가 디스크와 페이지 캐시에 남지 않게 했다.

**옆에서 재는 숫자.** 스크립트가 `docker stats`를 계속 돌려 브로커 컨테이너(와 perf-test 컨테이너)의 CPU를 모으고, 계단의 집계 구간으로 잘라 평균을 낸다. 앱 층에서는 Docker Desktop이 호스트 쪽에서 9092 포트를 받는 `com.docker.backend` 프로세스의 CPU도 잰다. 앱 JVM의 CPU는 앱이 직접 잰다. 프로듀서 내부 지표(배치 크기, 요청당 레코드 수, 압축률, 버퍼 대기 비율, 버퍼 대기 시간)는 평균 창을 최근 30초로 줄여(`metrics.sample.window.ms=5000`, `metrics.num.samples=6`) 계단 하나의 값이 되게 했다.

## 6. 결과

먼저 ‘목표·실제·p99·판정’ 네 칸을 보면 된다. 목표만큼 처리하면서 느린 메시지의 지연도 기준 안에 들었는지를 보여 준다. 나머지 칸은 왜 느려졌는지 설명하는 근거다.

MB/s는 압축 전 메시지 크기로 계산한다. 압축을 켠 행도 실제 통신량은 이 값보다 작을 수 있다. p50·p99의 단위는 ms, CPU는 코어 수다. ‘배치’는 파티션별 묶음 하나의 평균 크기(압축 후 바이트), ‘요청당’은 Kafka 요청 하나에 실린 메시지 수다.

‘버퍼 대기’는 `send()`가 빈 버퍼 자리를 기다린 시간의 비율이다. 여러 스레드가 동시에 기다린 시간을 합치므로 1을 넘을 수 있다. ‘대기 ms’는 메시지가 버퍼에 들어간 뒤 전송되기까지 기다린 평균 시간이다. 둘 다 커지면, 보낼 메시지가 앞에서 줄을 서고 있다는 뜻이다.

압축 전 MB/s × 압축률(0.23)로 계산한 실제 전송량은 초당 17MB 남짓이다. 50MB/s의 길이 더는 막히지 않으므로 줄 수가 10만을 넘어 13.9만까지 올랐다. 이번에는 스레드가 16개인데 CPU가 코어 6.3개에서 멈췄다. 이유는 측정하지 않았다. Kafka 프로듀서는 레코드를 파티션별 배치에 붙일 때 그 파티션의 잠금을 잡고 그 안에서 압축 스트림에 쓴다. 그러니 파티션이 3개면 동시에 압축하는 스레드도 3개를 넘기 어렵다는 것이 지금의 추정이다(파티션 수를 바꾸는 Step 3에서 확인할 수 있다).

**브로커 단독의 천장은 브로커 것인가.** 6.1의 90만이 브로커의 한계인지 perf-test 하나의 한계인지 보려고, perf-test 컨테이너 두 개가 목표를 반씩 나눠 동시에 보내게 했다(배치 설정, 계단 20초, 90만부터 10만씩).

정해 둔 상한 150만까지 버텼고 브로커 CPU는 코어 2개 남짓이었다. 그러니 6.1의 90만은 보내는 perf-test 하나의 한계였다. 다만 이 표의 합계는 정밀하지 않다. 두 컨테이너는 1~2초 어긋나게 시작하고, 각자 자기 집계 구간의 처리량을 잰다. 구간이 완전히 겹치지 않는 두 값을 더했으므로 동시 처리량보다 크게 나올 수 있다. 달성률이 104~112%로 나온 계단이 그 흔적이다. 100만 계단의 63.5%도 같은 어긋남이나 브로커의 보존 정리(5분마다)가 겹친 잡음으로 보이며, 원인을 따로 확인하지는 않았다. 보수적으로 말할 수 있는 것은 "이 PC의 브로커 하나는 적어도 초당 120만 줄(약 620MB/s)을 p99 52ms로 받았다"까지다.

## 7. 왜 묶어 보내는 설정이 더 빨랐는가

**기준선의 천장은 "요청 수"다.** 프로듀서는 브로커 연결 하나에 응답을 기다리지 않은 요청을 최대 5개(`max.in.flight.requests.per.connection` 기본값)까지 보낸다. 그러므로 처리량은 대략 "5 × 요청당 레코드 수 ÷ 요청 하나가 끝나는 시간"을 넘을 수 없다. 16KB 배치에는 546바이트 메시지가 30건 가까이 들어가고, 파티션 셋의 배치가 한 요청에 실리면 요청당 80~90건이다. 브로커 단독 층의 40만 계단(요청당 86건)에서 이 식을 거꾸로 풀면 요청 하나가 약 1.1ms에 끝났다는 뜻이 된다. 앱 층의 10만 계단에서는 7.5만 줄/s ÷ 77건으로 초당 약 980개 요청이므로 요청 하나에 약 5ms가 걸렸다. 같은 브로커인데 호스트에서 docker로 들어가는 길을 지나면 요청 한 번이 다섯 배 느려지고, 작은 배치로는 그 왕복 수를 감당하지 못한다. 이 1.1ms와 5ms는 측정한 처리량과 레코드 수로 역산한 값이지, 요청 지연을 직접 잰 값은 아니다.

**큰 묶음으로 보내자 줄을 서서 기다리는 시간이 줄었다.** ‘더 모으려면 더 기다려야 하니 느려지지 않을까’라고 생각할 수 있다. 하지만 로그가 많이 들어오면 묶음은 금방 찬다. 같은 횟수로 보내도 서너 배의 로그를 실을 수 있어, 전송을 기다리는 줄이 짧아진다.

실제로 기본 설정은 초당 40만 줄에서 버퍼 안의 평균 대기가 149ms였다. 배치 설정은 평균 대기가 1ms 안팎이었다. 그래서 이 시험에서는 더 많이 보내면서도 더 빨리 응답을 받았다. `linger.ms=20`은 항상 20ms 기다리라는 뜻이 아니다. 덜 찬 묶음을 얼마나 기다릴지 정한 값이며, 부하가 높아 먼저 차면 바로 보낸다.

**앱 경유의 천장은 두 겹이었고 둘 다 Kafka 밖에 있다.** 첫 겹은 보내는 스레드의 CPU다. 정규화와 JSON 만들기가 스레드당 초당 약 2.5만 줄에서 꽉 찬다. 둘째 겹은 Docker Desktop의 포트 전달이다. 호스트의 앱이 `localhost:9092`로 보내는 바이트는 `com.docker.backend`를 거쳐 WSL2 VM 안의 브로커로 들어가는데, 연결 수와 관계없이 합계 약 50MB/s에서 막혔다. `com.docker.backend`의 CPU는 코어 0.3~0.5개라 이 프로세스가 CPU에 묶인 것은 아니다. VM 경계를 넘는 경로 어딘가의 한계로 보이며, 어느 부분인지는 이 실험으로 가릴 수 없다. 4스레드에서는 두 겹이 우연히 거의 같은 높이(약 10만 줄/s)라서 하나를 풀어도 다른 하나에 걸렸다.

**압축은 바이트가 좁은 곳에서 처리량을 올리고, 넓은 곳에서는 CPU 비용만 남는다.** 브로커 단독 층처럼 길이 넓으면 lz4는 보내는 스레드의 CPU만 더 써서 천장을 90만에서 70만으로 낮췄다. 대신 디스크에 쓰는 바이트는 4분의 1 아래로 줄고 지연도 가장 낮았다. 앱 층처럼 길이 좁으면 lz4가 바이트를 4.3분의 1로 줄여, 낼 수 있는 처리량을 약 10만에서 13.9만으로 올렸다(스레드 16). 다만 판정 기준으로 버틴 계단은 둘 다 10만이다. 15만 계단에서 13.6만으로 95%에 조금 못 미쳤다.

## 8. 기업 프로젝트에 주는 의미

**이번 조건에서는 Kafka가 1,000대 분량보다 많은 로그를 받았다.** 1,000대 peak는 초당 약 6만 줄이며, 메시지 하나가 546바이트면 약 31MB/s다. 이 노트북의 Kafka 브로커 하나는 기본 설정으로 초당 40만 줄, 배치 설정으로 보수적으로 잡아도 120만 줄 이상을 받았다. 따라서 이 조건에서 Kafka의 수신 속도에는 여유가 있었다. 다만 운영 서버 성능을 이 시험으로 보장할 수는 없다. 다른 서버에 복제본을 두는 비용(Step 6)과 최종 저장소가 따라가는 속도(Step 4)는 별도로 확인해야 한다.

**먼저 무너지는 곳은 수집 서버의 CPU다.** 정규화와 JSON만으로 스레드 하나가 초당 2.5만 줄이다. 1,000대면 코어 2.5개 남짓을 이 일에 쓴다. 실제 수집 서버는 여기에 HTTP 요청을 받고 Fluent Bit이 보낸 JSON 배열을 읽는 일(이번에 재지 않았다)이 더해진다. 수집 서버의 대수와 코어 수를 정할 때 이 숫자를 출발점으로 쓸 수 있다. 줄이려면 시각 파싱(정규화 CPU의 43%)이 첫 후보다.

**운영에서 먼저 비교해 볼 후보는 128KB·20ms 배치 설정이다.** `batch.size=131072`, `linger.ms=20`으로 더 크게 묶어 보내는 설정이다. 이 시험의 앱 경유 경로에서 기본값(16KB, 5ms)은 초당 10만 줄을 통과하지 못했고, 배치 설정은 통과했다. 서버가 분리돼 왕복 시간이 길어지면 묶음 크기의 영향이 더 커질 수 있다(추정). 운영에 그대로 적용하기 전에는 실제 로그 양과 응답 시간 목표로 확인한다.

**압축은 네트워크 대역에 따라 정한다.** 이 PC의 50MB/s 천장은 Docker Desktop 때문이라 운영에는 없다. 하지만 1Gbps 네트워크도 약 119MB/s(= 1,000,000,000 ÷ 8 ÷ 1,048,576)이므로 압축 없이 546바이트 메시지라면 초당 약 23만 줄이 상한이다(계산). lz4로 4.3분의 1이 되면 같은 선으로 약 100만 줄을 나를 수 있다(계산). 망분리 환경의 수집 서버와 브로커 사이 대역을 알면 압축 여부는 이 계산으로 정할 수 있고, 디스크 사용량이 4분의 1로 주는 것은 덤이다. Step 5의 압축 결정에 이 결과를 쓴다.

## 9. 이 측정의 한계

- 브로커, perf-test, 앱, Docker VM이 한 PC의 CPU와 SSD를 나눠 썼다. 앱 층에서는 앱(호스트)과 브로커(VM)가 같은 코어를 놓고 다퉜다.
- 브로커가 하나이고 복제가 1이다. `acks=all`이 리더 하나의 기록만 기다리므로 운영(복제 3)보다 유리하다.
- Kafka는 ack 전에 디스크에 fsync하지 않고 페이지 캐시에 쓴다. 30초 계단은 페이지 캐시가 디스크로 밀려나는 압박을 충분히 보여 주지 못했을 수 있다.
- 컨슈머가 동시에 읽지 않았다. 읽는 쪽이 붙으면 브로커의 디스크와 네트워크를 나눠 쓴다.
- 파티션은 3개로 고정했다.
- 앱 층은 HTTP 수집 경로(Spring MVC가 Fluent Bit JSON 배열을 읽는 일)를 빼고 쟀다. 실제 수집 서버의 처리량은 6.2보다 낮다.
- 입력은 1대분 3시간 로그를 가상 차량 수천 대에 나눠 쓴 것이다. 차량마다 내용이 다른 실제 운영과 압축률이 다를 수 있다.
- 각 구성을 한 번씩만 쟀다. 브로커 단독 perf-test 2개의 합계는 6.3절에 적은 이유로 과대 추정될 수 있다. perf-test 층의 CPU 집계 구간은 끝난 시각에서 거슬러 어림한 것이고, `docker stats` 표본은 1~2초 간격이다.

## 10. 부작용: Docker 가상 디스크가 커졌다

이 실험은 디스크에 많이 쓴다. 브로커 단독 배치 설정은 계단 19개 동안 약 3.1억 건(목표 × 30초의 합)을 보냈으므로 계산으로 약 160GB를 썼고, 실행이 끝날 때 토픽에 69GB가 남아 있었다. 토픽에 파티션당 1GB 보존 제한을 걸었지만, 브로커가 보존 규칙을 검사하는 주기(`log.retention.check.interval.ms`, 기본 5분)가 실행 중에 바꿀 수 없는 설정이라, 검사 사이 5분 동안 초당 수백 MB씩 쌓인 뒤에야 지워진다. 그 결과 Docker Desktop의 가상 디스크 `%LOCALAPPDATA%\Docker\wsl\disk\docker_data.vhdx`가 14.3GB에서 100.9GB로 커졌다. 가상 디스크는 안에서 파일을 지워도 저절로 줄지 않는다. 측정이 끝난 뒤 VM 안에서 쓰는 공간은 다시 13GB 안팎으로 돌아왔으므로, 늘어난 약 87GB는 반납할 수 있는 빈 공간이다.

2026-10-16에 아래 절차로 줄였다. 가상 디스크는 100.9GB에서 13.5GB가 됐고, 압축 자체는 6초 걸렸다. 컨테이너를 내렸다 올렸지만 볼륨은 그대로라 `app-logs` 토픽과 데이터는 남아 있다.

먼저 VM 안의 빈 블록을 가상 디스크에 반납해야 한다. Docker의 데이터 디스크는 `discard` 옵션 없이 마운트되어 있어서(`docker exec kafka grep /var/lib/kafka/data /proc/mounts`로 보면 `rw,relatime`뿐이다), 파일을 지워도 그 블록이 가상 디스크 쪽에는 여전히 "쓰는 중"으로 남는다. 권한 있는 임시 컨테이너에서 `fstrim`을 돌리면 그 파일 시스템 전체의 빈 블록이 반납된다. 볼륨과 이미지가 모두 같은 파일 시스템에 있으므로 Kafka 볼륨 하나를 붙여 돌리면 된다. 데이터는 지우지 않는다. 그다음 Docker Desktop과 WSL을 끄고, 관리자 권한으로 `Optimize-VHD`(Hyper-V 모듈. Windows 11 Enterprise에 있다)를 돌린다. 이번에는 `fstrim`을 먼저 했으므로, `fstrim` 없이 압축하면 얼마나 줄어드는지는 확인하지 않았다.

```powershell
# 1. 빈 블록 반납 (관리자 권한 불필요). 로컬에 있는 alpine 계열 이미지면 무엇이든 된다 (busybox 의 fstrim)
docker run --rm --privileged --entrypoint sh -v practice-kafka_kafka-data:/data redis:7-alpine -c "fstrim -v /data"

# 2. Docker Desktop 과 WSL 을 끈다. 컨테이너가 모두 멈추고, 다른 WSL 배포판도 함께 꺼진다
docker desktop stop
wsl --shutdown

# 3. 압축. 관리자 권한 확인 창에서 "예"를 누른다 (계정이 관리자 그룹이어야 한다)
Start-Process powershell.exe -Verb RunAs -Wait -ArgumentList '-NoProfile', '-Command', "Optimize-VHD -Path '$env:LOCALAPPDATA\Docker\wsl\disk\docker_data.vhdx' -Mode Full"

# 4. 다시 켜고 컨테이너를 올린다 (compose 서비스에 재시작 정책이 없어 저절로 뜨지 않는다)
docker desktop start
docker compose -f docker/docker-compose.yml up -d
```

`Optimize-VHD`를 쓸 수 없는 Windows(Home 등)에서는 3을 관리자 `diskpart`의 `select vdisk file="..."`, `attach vdisk readonly`, `compact vdisk`, `detach vdisk`로 대신할 수 있다. 이 방법은 이 저장소에서 해 보지 않았다. 다시 측정할 때 디스크가 걱정되면 계단을 20초로 줄이거나(`-StepSeconds 20`) lz4 설정을 쓰면 쓰는 양이 준다.

## 11. 다음에 해 볼 것

- HTTP 수집 경로 전체를 같은 계단으로 잰다. `/ingest/fluentbit`에 Fluent Bit 형식 묶음을 동시에 보내 6.2와의 차이(HTTP와 JSON 배열 읽기의 몫)를 본다.
- 컨슈머 따라잡기. 계단마다 lag가 쌓이는지 본다. Step 4의 배치 적재와 함께 하면 "적재가 수집을 따라가는가"가 된다.
- 파티션 수를 3에서 6, 12로 바꿔 lz4의 CPU 정체(6.3)가 파티션별 잠금 때문인지 확인한다(Step 3).
- 앱을 docker 네트워크 안에서 띄워 포트 전달 천장을 없애고 앱 층의 CPU 천장만 본다.
- 정규화의 시각 파싱을 고친 뒤 같은 계단으로 다시 잰다.
- 3브로커 복제(Step 6)에서 같은 계단을 돌려 복제 비용을 본다.
- 브로커 단독 perf-test를 3개 이상으로 늘려 이 PC 브로커의 진짜 천장을 찾는다. 6.3의 집계 오차를 없애려면 컨테이너들의 시작 시각을 맞추거나 브로커 쪽 지표(JMX)로 재야 한다.

## 배운 점

"Kafka가 얼마나 버티는가"를 물으면 Kafka를 재고 싶어지지만, 실제로 잰 것은 대부분 Kafka 바깥이었다. 브로커는 가장 바쁠 때도 CPU 코어 2개 남짓을 썼고, 천장은 매번 요청 수, 보내는 스레드, 네트워크 경로 중 하나에서 생겼다. 천장을 찾으면 그 원인을 하나 풀어 보고, 처리량이 따라 오르는지 확인해야 그것이 진짜 병목인지 알 수 있다. 스레드를 늘렸는데 처리량은 그대로이고 버퍼 대기만 늘었다면 병목은 스레드 다음에 있다. 이 차례를 지키지 않았다면 "앱 층은 4스레드 CPU가 한계"라는 절반만 맞는 결론으로 끝났을 것이다.

두 번째로 분명해진 것은 기본값의 의미다. `batch.size` 16KB는 같은 기계 안의 짧은 왕복을 기준으로 하면 넉넉하지만, 왕복이 다섯 배 길어지자 10만 줄/s에서 무너졌다. 프로듀서 설정은 처리량 목표와 함께 "브로커까지 왕복이 얼마나 걸리는가"를 알아야 정할 수 있다.
